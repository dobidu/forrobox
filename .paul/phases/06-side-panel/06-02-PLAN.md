<objective>
## Goal
Fill the 280 px region `04-01` reserved and has painted as a bare raised rectangle ever since:
`REGIONAL PROFILES` with its `CUSTOM` tag, the four profile buttons, `TIMBRE / CONVOLUTION` with its
three rows and LEDs, the `MIX` knob, `LOAD IR…`, and the bundle footer.

## Purpose
It is the last empty region of the chassis. Everything else the user can see is real.

Two of its controls are already fully backed and have been since Phase 3 — `ids::timbre` selects the
character and `ids::charMix` sets its wet/dry, both live in `MixBus` — so the timbre rows and the
`MIX` knob are not stubs here, they are the first UI those parameters have ever had.

## Output
- `SidePanel`, its own component owning its own layout
- Profile descriptions in C++ at last, cross-checked against `data.js`
- Timbre sub-labels likewise
- The `CUSTOM` tag, following the dirty flag
- `/code-review` after Task 2 — it binds two parameters
</objective>

```gherkin
Given the side panel
Then it carries REGIONAL PROFILES, four profile buttons, TIMBRE / CONVOLUTION, three timbre rows,
```

**Every new constant must be enrolled or excused.** 06-01 added `check_enrolment_coverage`, so a
constant in an enrolled header that no expectation compares now FAILS the build's cross-check. This

## AC-2: The profile list shows which profile is active, and says what it is

```gherkin
Given the stored activeProfile
Then exactly one button is active: `--active` ground, its name in `--bg`, a `--c-zabumba` dot
And ONLY the active button shows its three-line description — css:400 hides it otherwise
And the descriptions are data.js's own, cross-checked, not retyped
And clicking a button does nothing yet
```

**The descriptions do not exist in C++.** `ids::profileInfos` carries id, display name, short name and
code; `data.js` carries a three-line `desc` per profile that `PLANNING.md:743+` also quotes. Add them
to the SAME array of structs — `ids::channelInfos` states the rule in its own comment, "one array of
structs makes divergence impossible instead of detectable" — and extend `verify-profiles.py`, which
already cross-checks the other three identity fields against `data.js`.

**Clicking does nothing, deliberately, and settled with the user.** 06-03 owns the reload, and its
seven-way fan-out (bpm, swing, cachaça, patterns, bateria sub-patterns, mutes, timbre) is one law that
belongs in one plan with its own `/code-review`. A half-reload would leave BPM and timbre disagreeing
with the highlighted profile, which is worse than a button that plainly does not act yet. Same shape
as 05-01 reserving the STEPS boxes for 05-03.

## AC-4: The CUSTOM tag follows the dirty flag

```gherkin
Given a pattern edit through any view
Then the CUSTOM tag appears — `--c-pandeiro`, mono 9px, fading in over 0.2s (css:411)
And it is read from State::dirty rather than from a second flag the UI keeps
And a state with dirty false shows no tag
```

**Read it directly; do not invent a publication.** I told you at 06-01's close that this needed the
state's revision counter widened, because `publishIfChanged` compares only `lanes`. Having looked, I
do not think that any more, and the plan should say so rather than quietly change course: `dirty` sits
behind `lockPatternState()`, and taking that handle costs about 29 ns including the publisher's
256-byte compare — roughly 1.7 µs per second at 60 Hz. That is the same judgement that dropped 06-01's
Task 2: read the truth where it lives unless there is a measured reason not to. **MEASURE it in this
plan and record the number**; if it is not what I have claimed, widen the counter and say so.
