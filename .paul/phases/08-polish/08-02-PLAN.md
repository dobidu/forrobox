<objective>
## Goal

A gear beside the logo opens a menu. Theme, corner radius, accent intensity and default step count
change the plugin immediately and survive a restart — **globally, not per project**. The same menu
opens an ABOUT panel naming both authors and linking the repository.

## Purpose

`PLANNING.md:850-864` specifies five tweakable settings and says they "belong in a **settings/gear
menu**, persisted globally (not per-project)". Nothing in the plugin can reach any of them today.

Phase 4 built the seams for this deliberately and said so in place — `LookAndFeel.h:59`: *"Both
tweakables are user-facing in Phase 8's settings menu, so they are settable now rather than being
constants that have to be dug out later."* `setMode`, `setCornerRadius` and `setAccentIntensity` all
exist and none has a caller. This plan is the caller.

The ABOUT panel rides with it because the user asked for it at 08-01 UNIFY and because a menu is
where it belongs. `ABOUT.md` already ships the same content as documentation.

## Output

- A global preferences store, the plugin's first — everything until now was per-project APVTS state
- A gear button and a `juce::PopupMenu`, inventing no geometry
- Four settings live, each repainting what it changes
- An ABOUT overlay reusing Phase 5's approved overlay treatment
</objective>

<acceptance_criteria>

## AC-1: Settings persist globally, not per project

```gherkin
Given a setting changed in one plugin instance
When the host is closed and a DIFFERENT project is opened
Then the setting is still in force
And no project file carries it — saving and reloading a project changes no setting
```

## AC-2: A missing, unreadable or hostile preferences file costs nothing

```gherkin
Given no preferences file, or one that is truncated, or one whose values are out of range
When the plugin starts
Then every setting falls back to PLANNING.md's documented default
And the plugin starts normally rather than refusing to load
```

## AC-3: Each setting changes what it claims, immediately

```gherkin
Given the editor is open
When theme, corner radius or accent intensity is chosen from the gear menu
Then the chassis repaints with that value
And nothing else about the plugin's sound or state changes
```

## AC-4: Default step count seeds a FRESH instance and never overrides a restore

```gherkin
Given the default step count setting is 32
When a new plugin instance is created
Then it starts at 32 steps
But when a project saved at 16 steps is restored
Then it opens at 16 — the saved project wins over the preference
```

## AC-5: ABOUT names both authors and the project

```gherkin
Given the gear menu is open
When "About Forró Box…" is chosen
Then a panel shows both authors with their links and the repository URL
And dismissing it leaves the plugin exactly as it was
```

<task type="auto">
  <name>Task 1: The global settings store</name>
  <files>src/Settings.h, src/Settings.cpp, CMakeLists.txt, tests/StateRoundTripTest.cpp</files>
  <action>
    Build `forrobox::Settings` over `juce::PropertiesFile`. This is the plugin's FIRST global
    store — grep confirms no `PropertiesFile`, no `ApplicationProperties` and no
    `getUserApplicationDataDirectory` anywhere in `src/` — so it is a new subsystem and not a
    variation on the APVTS.

    THE FIVE SETTINGS AND THEIR DEFAULTS COME FROM `PLANNING.md:855-862`, read once into one table
    of structs the way `ids::channelInfos` is, so the id, the range and the default cannot drift
    apart: theme (Dark default), corner radius (2 px default, 0 the alternative), accent intensity
    (100% default, 35% floor), display font (IBM Plex Mono default — declared here, WIRED in 08-03)
    and default step count (16 default).

    EVERY READ CLAMPS. A preferences file is a plain XML file in the user's own config directory:
    it can be hand-edited, truncated by a full disk, or written by a future build with a wider
    range. `State`'s bounded scalars are the precedent — `ForroBoxState.h` keeps `presetIdx` private
    behind a clamping setter precisely so an out-of-range value cannot exist in memory at all. Do
    the same rather than validating at the boundary.

    NOT A SINGLETON, and not owned by the processor. One `PropertiesFile` per process, reached
    through a function-local static, because a host loads many instances of a plugin into one
    process and two instances writing the same file must not interleave. State the sharing in the
    header, and say what is NOT guaranteed: two instances open at once will not see each other's
    changes live, and last-writer-wins on disk. That is the documented behaviour, not a bug to be
    discovered later.

    Do NOT wire anything to the UI in this task. A store with no caller is 02-04's "a guarantee with
    no caller is not a guarantee" — so the tests ARE the caller until Task 3, and they must exercise
    the real file, in a temp directory, not a mock.
  </action>
  <verify>
    cmake --build build-linux --target ForroBoxTests -j8 && (unset DISPLAY; ./build-linux/ForroBoxTests)
    Checks: round-trip every setting; absent file; truncated file; out-of-range values clamped;
    a value written by one handle is read by a second opened on the same path.
    Then run `/code-review` on the diff.
  </verify>
  <done>AC-1 and AC-2 satisfied at the store level</done>
</task>

<boundaries>

## DO NOT CHANGE

- **Any length `verify-geometry.py` cross-checks.** The gear takes unspecified space; it does not
  move a specified box. If the header has no room, that is a finding, not a licence.
- **`setStateInformation`'s restore precedence.** 08-01's AC-2 — an emptied or 16-step project wins
  over every preference. This plan adds a seed, never an override.
- **The 46 parameter IDs and the count.** A preference is not a parameter; it has no automation lane
  and no place in saved project state. `midi_gate` at 07-03 is the precedent for what IS a
  parameter, and these five are the opposite case.
- **`ForroBoxLookAndFeel`'s existing setters.** Call them. Do not add a second path to the same
  field.
- **Everything 08-01 shipped.**

## SCOPE LIMITS

- **No display font.** It is the fifth setting and it goes to 08-03, because it needs two font
  families embedded and neither is straightforward: Space Mono ships only 400 and 700 and is not
  variable, so it cannot supply the 500 and 600 the type scale uses, and JetBrains Mono is
  variable-only — 04-01's problem exactly. `Settings` DECLARES the setting so the store is complete;
  nothing reads it yet.
- **No `CACHAÇA` easter egg, no Ciclotron™ treatment.** The rest of Phase 8.
- **No per-project settings.** `PLANNING.md:853` says global, and the APVTS already owns
  per-project.
- **No settings the spec does not list.** Five, from one table.

</boundaries>
