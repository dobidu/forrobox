<objective>
## Goal

Produce a Windows x64 VST3 with MSVC 2022 driven from WSL, prove the 01-02 parameter and state layer
is not GCC-specific by running the same 161-check suite under MSVC, install the plugin to the
per-user VST3 folder, and confirm Ableton Live 12 scans, loads and opens it. Along the way, settle
the plugin display name to ASCII and give the project a git repository so Phase 1 can transition.

## Purpose

Phase 1's goal is a plugin that builds on Linux *and* Windows and loads in a host — this is the half
that has never been tested. It also closes all three open items blocking the phase: the display-name
defect (before any host caches the name), the missing repository (before transition demands a commit),
and the unverified assumption that a real DAW accepts the plugin at all. Everything after this builds
on a foundation that has been loaded in the DAW the project targets.

## Output

- `Forro Box` as the ASCII display name; accented parameter and group names untouched
- `scripts/build-windows.sh` — repeatable MSVC build driven from WSL
- Windows x64 `ForroBox.vst3` bundle, installed to `%LOCALAPPDATA%\Programs\Common\VST3`
- `ForroBoxTests.exe` built and passing under MSVC
- A git repository with Phase 1 history
</objective>

  <files>scripts/build-windows.sh</files>
  <action>
    Write `scripts/build-windows.sh` — a bash script run from WSL that drives the Windows toolchain
    through interop. Make it idempotent and re-runnable, `set -euo pipefail`, and have it echo each
    command it runs so a failure is diagnosable from the log alone.

    Steps:
    - Resolve the UNC source path as `\\wsl.localhost\Ubuntu-24.04\home\bidu\forrobox`. Derive it
      from the distro name rather than hardcoding "Ubuntu" — the distro is `Ubuntu-24.04`, and the
      wrong name silently fails.
    - Build directory `C:\Users\carlo\forrobox-build` — on the Windows filesystem deliberately. The
      source stays on the UNC share (reads measured at 22 ms for 30 KB, no duplication needed) while
      MSVC's many small artifact writes stay local, which is the half of UNC that is actually slow.
    - Configure: `cmake.exe -S <unc> -B <winbuild> -G "Visual Studio 17 2022" -A x64
      -DJUCE_PATH=<unc-juce> -DFORROBOX_TESTS=ON`.
    - Build: `cmake.exe --build <winbuild> --config Release --parallel`.
    - **Fallback, and only if configure fails because CMake rejects a UNC source directory:** mirror
      the source to `C:\Users\carlo\forrobox-win` with `rsync -a --delete` excluding `build*/`,
      `.git/` and `.paul/`, then configure from there. Report clearly which path was used — do not
      silently switch, because a mirrored build can go stale against the real source.
    - Run `ForroBoxTests.exe` from the Windows build tree and print its output verbatim.

    Capture the full configure and build output to `scripts/build-windows.log` for the review, and
    grep it for warnings whose path contains `src/` or `tests/` — JUCE's own warnings under MSVC are
    not this project's to fix, and conflating them hides ours.

    Expect MSVC to find genuine issues GCC and Clang did not: it is stricter about some conversions
    and about `-Wshadow`-class problems in different places. Treat any warning from our own files as
    a defect to fix, not as noise to filter.
