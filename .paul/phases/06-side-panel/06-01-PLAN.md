<objective>
## Goal
Name the concept two components already are, and give the one derived value the UI follows by
recomputation the publication counter every other derived value here has.

## Purpose
Phase 6 adds a third place that shows a slice of the pattern and a third reader of the mute/solo
gate. Both duplications are already paid for, and the invoice is on record:

**The overlay and the grid are two copies.** `rebuildPads`, `padFor`, `toggleCell`,
`refreshFromState`, `refreshIfStateChanged`, `stepCount`, `lastPatternGeneration` and the dense
row-major pad vector exist twice, differing in a row table. This is not a speculative hoist — **both
of 05-04 Task 2's fixes were re-fixes of bugs the grid had already had**: "read the pattern once at
open and never again" was 05-01's, and "record the generation outside the lock" was 05-03's, which
that plan shipped wrong twice. Two fixes, applied to two copies, one plan apart. 05-04's close
hoisted `readStepWindow` and `snapshotPattern`; the rest is this plan.

**The channel gate is the one derived value with no signal.** This codebase follows derived
processor state through counters — `getPatternPublicationCount`, `getStepPublicationCount` — and the
resolved mute/solo gate has none, so the only way to follow it is `SequencerGrid::refreshRowStates`
recomputing it at 60 Hz. `/simplify` measured that as free (11.7 ns, zero allocations), so this is
altitude and not cost, and the plan must not pretend otherwise. What the missing signal forces is a
three-link chain: an unconditional resolve, a `rowDimmed` cache to edge-detect against, and a
rebuild-seeding special case in `rebuildPads`.

## Output
- `PatternPads` — one holder for "a component showing a slice of the pattern"
- A published, counted `VoiceEngine::Settings` the UI reads instead of resolving
- The grid and the overlay both built on them, with no behaviour change
- `/code-review` after Task 2, because the publication crosses the audio thread
</objective>

## AC-1: One holder for a component that shows a slice of the pattern

```gherkin
Given the sequencer grid and the kit overlay
Then both own a PatternPads rather than their own pad vector, stepCount and generation
And each describes its rows as a table: which lanes a row READS and which lane a click WRITES
And the grid's rows come from lanesForRow / writeLaneForRow, and the overlay's four from one lane each
And no behaviour changes: the same clicks write the same lanes and the same pads light
```

**The row table is the whole difference.** `displayedVelocity` already takes a lane cover and
returns the max across it, which degenerates correctly for a cover of one — so the overlay's four
single-lane rows and the grid's composite BATERIA row are the same function with different data.

**This is a hoist for TWO, and that is a real risk.** Phase 6's own views are the third instance and
they do not exist yet. The shape must therefore be the one the two present copies already agree on —
a pad vector, a step window, a generation and a row table — and nothing invented for a caller that
has not been written.

## AC-2: The resolved channel gate is published and counted

```gherkin
Given the processor resolving channel settings once per block
Then it publishes the resolved Settings with a publication count, as the step snapshot is published
And the publication is lock-free and allocation-free, and processBlock's contract is unchanged
And the UI reads the published value rather than calling resolveChannelSettings itself
And a reader that has seen the current count does no work
```

**Not a performance claim.** `/simplify` measured `resolveChannelSettings` at 11.7 ns and
`refreshRowStates` at 13 ns. The plan is not to make those faster and the SUMMARY must not say it
did. It is to make the gate followable the way every other derived value here is followed, which is
what removes the `rowDimmed` cache's reason to exist and the rebuild-seeding special case with it.

**The publication is the audio thread's, and `StepSnapshot` is the precedent to read first.** That
one fits a whole payload in one 64-bit word precisely to avoid a double-buffer; `Settings` is about
150 bytes and will not, so this needs the double-buffer handover 02-04 built or a documented reason
it does not.

## AC-3: Nothing changed, and that is proved rather than asserted

```gherkin
Given a cleanup plan with no intended user-visible change
Then the reference renders are byte-identical to the ones before it
And the full check suite passes with the same count of checks, on all three compilers
And a render of the grid, the overlay and a dimmed row matches the pre-change image exactly
```

**A refactor that changes a pixel has a bug in it.** The ten reference PNGs are already written by
the suite; comparing them against the committed set before and after is the cheapest honest proof
that this plan did what it says. Hash them.

```gherkin
Then every check passes, and the three verify scripts stay green

```
