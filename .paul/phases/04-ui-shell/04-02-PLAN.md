<objective>
## Goal

Build the `Knob` — the plugin's most-used control — as a custom `juce::Component` with the exact
geometry `PLANNING.md` and `controls.js` specify, both polarities, the full interaction set, and a
real APVTS attachment. Prove it by placing the twenty strip knobs (`VOL`, `PITCH`, `DECAY`, `PAN` ×
5 channels) into geometry reserved for them, driving real parameters.

## Purpose

`PLANNING.md:347` calls the knob "the single most-used control", and `:357` says the flat indicator
line "*is* the knob's identity". Every later plan instantiates it: 04-03's fader family sits beside
it, 04-04's two signature 54 px header knobs are its most important instance, and Phase 6's side
panel `MIX` knob is a third size. Getting the geometry and the feel right once is what makes those
plans layout work rather than component work.

It is also the first plan in Phase 4 that touches real parameters, which is why `/code-review`
becomes applicable here.

## Output

- `src/Knob.{h,cpp}` — the component: relative geometry, both polarities, the gesture set
- `src/ValueTooltip.{h,cpp}` — the shared value tooltip, spec'd at `PLANNING.md:374`
- `ChassisLayout::StripLayout` extended to the full reserved stack from `PLANNING.md:284-294`
- Twenty attached strip knobs, live against `ids::channelParam`
- Pixel and interaction coverage in `tests/UiTest.cpp`, every new instrument self-tested

## AC-1: The knob's geometry is the spec's, and it is RELATIVE

```gherkin
Given a Knob rendered headlessly at 28 px, 32 px and 54 px
When its arcs, hub and indicator line are measured in each render
Then every dimension is the spec's 100x100 viewBox value scaled by the knob's size — track and value
  arc radius 38, stroke 5, hub radius 30, indicator from centre to (50,16), hub stroke 1.5
And the sweep runs -135 deg to +135 deg with 0 deg pointing up, at every size
And a knob at 54 px measures exactly 54/32 times the arc radius of one at 32 px, within one pixel
```

**Why relative and not pixels.** `PLANNING.md:347` says the knob is "drawn as SVG in a 100×100
viewBox, rendered at 28/32/54px", and `controls.js:47-48` sets `--ksize` with a fixed
`viewBox="0 0 100 100"`. The numbers 38, 30, 5 and 16 are viewBox units, **not** pixels: at 32 px the
track radius is 12.16 px. Treating them as pixels would draw a correct-looking 100 px knob and three
wrong ones, and the strip knobs are the 32 px case — the one nothing in the header would reveal.

## AC-2: Both polarities draw the arc the spec describes

```gherkin
Given a unipolar knob and a bipolar knob over the same range
When each is rendered at its minimum, centre and maximum
Then the unipolar value arc always starts at -135 deg and sweeps to the value angle
And the bipolar value arc starts at 0 deg (centre) and sweeps toward the value angle in either
  direction, so at centre it has zero extent and at the minimum it sweeps left
And the indicator line points to the same angle in both, because polarity changes the ARC only
And PITCH and PAN are the bipolar instances, per controls.js and app.js:181,183
```

## AC-3: The gesture set matches `controls.js`, which outranks PLANNING's prose

```gherkin
Given an attached knob with a known range and interval
When each gesture is applied
Then vertical drag moves the value by (dy / 160) * range
And Shift+drag applies a 0.18 multiplier to that
And the wheel moves by step * max(1, range / 50) per notch, and by step * 0.2 with Shift held
And Up/Right add one step and Down/Left subtract one, only when focused
And Alt+click resets, double-click opens an inline text editor, and right-click is NOT consumed
And every gesture shows the value tooltip, and the drag cursor is ns-resize
```

**Where the two sources disagree, `controls.js` wins and the deviation is recorded.**
`PLANNING.md:368` says only "Scroll wheel: increment; `Shift` for fine steps"; `controls.js:160-161`
is specific and is what the prototype actually feels like. `PLANNING.md:369` says double-click uses
`prompt()` and explicitly adds "a plugin should show an inline text editor" — so the editor is
spec-directed, not a deviation. Right-click is the case where PLANNING contradicts itself and
`:876-878` settles it against `:370`.

## AC-4: A knob is a view of a parameter, not a second copy of its state

```gherkin
Given a knob attached to an APVTS parameter
When the parameter changes from any source — host automation, a profile reload, setStateInformation
Then the knob repaints to the new value without the attachment firing a write back
And the knob's range and interval come from the parameter's NormalisableRange, never from a
  constructor argument, so there is exactly one source for each
And reset returns the parameter to ITS default value, not to whatever the knob was built with
And a drag is wrapped in beginChangeGesture / endChangeGesture so the host records one gesture
And no knob writes to the parameter while merely being repainted
```

**Two findings from `/graphify`, both AMBIGUOUS edges in the graph, both real.**

- **Reset target.** `controls.js:35` freezes `this.def = opts.value ?? min` at construction, and
  `app.js:527` pushes profile values in with `fire=false` — which never updates `def`. In the
  prototype, resetting a knob after loading CARUARU returns it to the value it had at page load.
  That is a prototype artefact, not intent: a plugin's reset target is the parameter's own default,
  which is also what Phase 6's profile reload will move away from. Deliberate deviation.
- **Interval ownership.** `controls.js:124` quantises with `round(v/step)*step` using a `step` the
  knob owns. In JUCE the interval already lives on the parameter's `NormalisableRange`. Carrying a
  second copy is the shape that produced 03-03's `dry = 1 - 0.5*wet` and 04-01's tracking bug: the
  knob must ASK the parameter, so there is nothing to diverge.

## AC-5: The strip's full interior is reserved, and only the knob grid is filled

```gherkin
Given ChassisLayout::StripLayout
When a strip's interior is derived
Then it exposes a box for every item PLANNING.md:284-294 lists in order — hit visualiser, divider,
  knob grid, divider, pattern cycler, mute/solo row, ghost-prob row, and the bateria sub-dots on
  strip 5 only
And every box is non-empty, inside the strip, and non-overlapping with its neighbours
And the knob grid is 2 columns with gap 9 x 6 holding four 32 px knobs, centred
And 04-02 PAINTS only the knob grid and the two dividers; every other box is geometry with nothing
  drawn in it
```

**Why reserve boxes this plan does not fill.** 04-01 computed the strip's `controls` rect and then
discarded it through `ignoreUnused`, which made its own "reserve their boxes" deliverable unreachable
by the plans that needed it. Reserving the whole stack now means 04-03 and Phase 5 add components
without re-flowing the strip, and it means a change to any pad or margin fails an assertion rather
than silently moving the knobs.

## AC-6: The instruments prove themselves, and the arc measurement is not blind

```gherkin
Given every new measurement helper this plan adds
When each is run against a synthetic component with a known answer
Then each returns that known answer, including a case it must reject
And the arc-extent instrument is shown to DISTINGUISH a unipolar arc from a bipolar one at the same
  value, and a 38-radius arc from a 30-radius one
And the interaction assertions are driven through juce::MouseEvent / KeyPress rather than by calling
  the value setter, so a gesture wired to nothing fails
```

**This is where the plan is most likely to fool itself.** An arc is thin, anti-aliased and curved;
"some coloured pixels appeared in the right quadrant" is an assertion four wrong arcs also pass.
04-01 shipped two instruments that could not fail and `/simplify` found a third. Count arc ink per
angular sector about the centre and assert the sector PROFILE, and prove the instrument separates
the cases it claims to separate before trusting a single arc claim.
