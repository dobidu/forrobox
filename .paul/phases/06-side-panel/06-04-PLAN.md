<objective>
## Goal

Every accented string in `src/` is written as the characters it means, with the source and execution
charset pinned once in CMake. The `\xNN` escape is gone from the codebase, and with it the three
mechanisms that existed only to survive it: the verifier's `decode_c_escapes`, its `join_literals`,
and the twelve-character allowlist test.

## Purpose

This is the fourth local fix of one class of bug. `PluginProcessor.cpp:985`, `Chassis.cpp:57` and
`Chassis.cpp:421` each split a literal by hand to dodge the greedy escape, and none of the three
carried a test. 06-02 then shipped `"m\xc3\xa9dio"` — where `\xa9d` parses as a three-digit escape
and is out of range — and the three compilers disagreed about it: Clang refused it, GCC truncated it
to `\x9d` silently, and `verify-profiles.py` could not see it at all because it compares source text.

Each fix so far has made the class DETECTABLE. Pinning the charset makes it UNREPRESENTABLE, and it
removes code rather than adding it. Every plan that ships more accented strings first makes this
bigger — and the next one is 06-05.

It is also a live false-failure waiting to happen. The allowlist is hard-coded to twelve characters
(`á â ã ç é ê ó ô Á Â — ™`). The source already uses **23** distinct non-ASCII characters, so
`É Ó Ç · × ÷ … ‹ › ↓ ↗` are all outside it. They have not fired only because the check is scoped to
`profileInfos` and `timbreSpecs`; the first accented display name carrying an `É` fails a correct
build.

## Output

- `CMakeLists.txt` pinning the charset for every target
- Ten source files whose accented literals read as the words they are
- `scripts/verify-profiles.py` with the escape machinery deleted
- `tests/UiTest.cpp` with a repertoire check that cannot false-fail, and a negative control proving
  it can fail
</objective>

<task type="auto">
  <name>Task 1: Pin the charset in CMake and write the accented literals as themselves</name>
  <files>
    CMakeLists.txt, src/ParameterIDs.h, src/Chassis.h, src/Chassis.cpp, src/HeaderBar.cpp,
    src/KitOverlay.cpp, src/PluginProcessor.cpp, src/SidePanel.cpp, src/Typography.cpp,
    src/DragMidiButton.cpp, src/MixBus.h
  </files>
  <action>
    Pin the charset once, on the `ForroBox` target as PUBLIC so the test executable inherits it —
    the test target already takes `juce_recommended_*_flags` transitively for exactly this reason,
    and a second copy of the flags would be free to drift:

      MSVC:        /utf-8
      GCC/Clang:   -finput-charset=UTF-8 -fexec-charset=UTF-8

    MSVC is the flag that is load-bearing: without `/utf-8` it reads the source as the system ANSI
    code page and mangles every accent. The GCC/Clang pair is already the default on this machine —
    pin it anyway, so the build does not depend on a locale nobody set deliberately.

    NOT `u8"..."`. This project is C++20 (`CMAKE_CXX_STANDARD 20`), where `u8` literals are
    `const char8_t*` and will not bind to the `const char*` fields in `ChannelInfo`, `ProfileInfo`
    and `timbreSpecs`.

    Then rewrite all 36 escape sites across the ten files as real UTF-8 text. The 23 characters in
    play are:

      · Á Â Ç É Ó × á â ã ç é ê ó ô ÷ — … ‹ › ™ ↓ ↗

    Three things to get right, and one not to touch:

    - KEEP the `juce::CharPointer_UTF8 (...)` wrappers. They are correct and load-bearing:
      `juce::String (const char*)` reads its bytes as Latin-1 and hands back mojibake for every
      accent. That constructor is what had the kit overlay rendering "peÃ§a" for a whole plan, and
      it is recorded at `tests/UiTest.cpp:10496`. This plan changes the SPELLING OF THE BYTES
      inside the wrapper, never the wrapper.
    - REMOVE the hand-split literals. `"CACHA\xc3\x87" "A"` becomes `"CACHAÇA"`, `"m\xc3\xa9" "dio"`
      becomes `"médio"`. The greedy escape was the only reason for the break, so the break goes with
      it — along with the trailing `// Aço Aberto` style comments, which existed to say what the
      escape meant and are now what the literal says.
    - DELETE the comment at `src/Chassis.h:545` documenting the split-literal discipline. It
      instructs a reader to do the thing this plan makes unnecessary.
    - DO NOT touch the `id` fields. `"triangulo"`, `"ganza"`, `"campina"` and every other identifier
      in `ParameterIDs.h` are ASCII by design and are fixed — renaming one invalidates saved host
      state. Only the accented DISPLAY strings beside them change. The VST3 display name stays the
      ASCII `Forro Box` for the reason recorded in PROJECT.md.
  </action>
  <verify>
    grep -rn '\\x[0-9a-fA-F]' src/ --include=*.cpp --include=*.h   # no hits in literals
    cmake --build build-linux --target ForroBoxTests -j8 && (unset DISPLAY; ./build-linux/ForroBoxTests)
    cmake --build build-clang  --target ForroBoxTests -j8 && (unset DISPLAY; ./build-clang/ForroBoxTests)
    python3 scripts/verify-theme.py && python3 scripts/verify-profiles.py && python3 scripts/verify-geometry.py
    Read the REAL exit code of each, not a grep of the build log for "error".
  </verify>
  <done>AC-1 and AC-2 satisfied on GCC and Clang; MSVC confirmed at Task 3's close</done>
</task>

<task type="auto">
  <name>Task 3: Replace the allowlist with a repertoire rule, and prove it can fail</name>
  <files>tests/UiTest.cpp</files>
  <action>
    The allowlist at `tests/UiTest.cpp:10545` exists to catch a compiler-truncated escape. With no
    escapes left, that specific failure is unrepresentable — but the check still earns its place,
    because a MISSING `/utf-8` on MSVC produces exactly the same signature: valid-looking text made
    of characters Portuguese is not written with.

    So keep the check and fix its rule. Replace the twelve hand-typed characters with the full
    repertoire, stated as a rule rather than as an inventory of what this text happens to use today:

    - every accented letter Brazilian Portuguese is written with, both cases:
      á à â ã é ê í ó ô õ ú ü ç  and  Á À Â Ã É Ê Í Ó Ô Õ Ú Ü Ç
    - the typographic characters this UI draws, each named with its source:
      · × ÷ — … ‹ › ™ ↓ ↗

    Written that way it cannot false-fail on a correct new accent, which the current list would do
    on the first `É` or `Ó` — and it still rejects the Latin-1 mojibake an unpinned MSVC build
    produces, because `Ã` followed by a stray control byte does not survive the letter rule.

    Then the negative control, which the old check never had. Apply the same predicate to a string
    carrying U+00DD `Ý` — the character GCC's truncation of `\xa9d` actually produced, so this is
    the real historical failure, not an invented one — and assert it is REPORTED. Follow
    `TestHarness.h`'s law: the instrument is self-tested against a subject with a known answer, and
    the control asserts the mutation applied rather than assuming it.

    Keep the `check8` round-trip and the `accented >= 12` floor. Both still hold and both catch
    different things.
  </action>
  <verify>
    cmake --build build-linux --target ForroBoxTests -j8 && (unset DISPLAY; ./build-linux/ForroBoxTests)
    cmake --build build-clang  --target ForroBoxTests -j8 && (unset DISPLAY; ./build-clang/ForroBoxTests)
    MUTATE: add `É` to a profile displayName, confirm the suite still PASSES (the old list would
    have failed it). Then add `Ý`, confirm the suite FAILS and names U+00DD. Assert each edit
    landed before reading the result. Revert both.
    FORROBOX_MSVC_JOBS=2 ./scripts/build-windows.sh --install
  </verify>
  <done>AC-4 and AC-5 satisfied, and AC-2 completed on MSVC — the compiler the charset flag is for</done>
