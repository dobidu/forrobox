<objective>
## Goal

Give the processor its full parameter surface and its complete persisted state: 45 automatable APVTS
parameters organised into a globals group plus five per-instrument groups, and a `ValueTree` child
node carrying the pattern grid, active profile, dirty flag, preset index and per-channel pattern
slot. Prove `getStateInformation`/`setStateInformation` round-trips every one of them losslessly
with a console test that actually runs.

## Purpose

Everything downstream reads this. Phase 2's clock derives step timing from `bpm`/`swing`/`steps` and
its pattern tables from the grid node; Phase 3's voices read the per-channel params; Phase 4 attaches
UI controls to these exact IDs. Parameter IDs and group IDs become part of the state path a host
saves into a project, so getting them fixed now is what stops a later rename from silently breaking
every saved session. State round-trip is also one of the project's success metrics.

## Output

- `src/ParameterIDs.h` — every parameter and state key as a named constant, declared once
- `src/PluginProcessor.{h,cpp}` — `createParameterLayout()`, an APVTS member, real state read/write
- `src/ForroBoxState.{h,cpp}` — grid/profile/dirty/preset state and its `ValueTree` serialisation
- `tests/StateRoundTripTest.cpp` — console app asserting lossless round-trip
- `CMakeLists.txt` — new sources plus a `ForroBoxTests` console target
</objective>

    Note on `sync`: PLANNING.md's "VST3 parameter mapping" list omits it while its global state table

<task type="auto">
  <name>Task 2: Grid and profile state as a ValueTree node, with real save/load</name>
  <files>src/ForroBoxState.h, src/ForroBoxState.cpp, src/PluginProcessor.h, src/PluginProcessor.cpp</files>
  <action>
    Create `forrobox::State` in `src/ForroBoxState.{h,cpp}` owning the non-automatable state:
    - `static constexpr int kMaxSteps = 32;` and `kNumLanes = 8`
    - 8 lanes of `std::array<std::uint8_t, kMaxSteps>` keyed zabumba, triangulo, pandeiro, ganza,
      bb, cx, hh, tom — values 0..127
    - `activeProfile` (string), `dirty` (bool), `presetIdx` (int 0–7), and a `pattern` slot (1–8)
      per channel
    Lanes are always stored at the full 32 slots regardless of the `steps` parameter; `steps` selects
    the active window. Storing a variable-length lane would make a 32→16→32 sequence lossy at the
    persistence layer, which is a different thing from the deliberate truncation the UI performs when
    the user changes step count.

    Serialisation: `void writeTo (juce::ValueTree& parent) const` and
    `static State readFrom (const juce::ValueTree& parent)`, using the keys from ParameterIDs.h.
    Encode each lane as base64 of its 32 raw bytes (`juce::Base64::toBase64`), one property per lane.

    `readFrom` must be defensive — this data comes back from arbitrary host project files:
    - missing node or missing lane → that lane all zeros
    - base64 that fails to decode, or decodes to the wrong length → pad with zeros / truncate to 32
    - any value > 127 → clamp
    - `presetIdx` outside 0–7 and `pattern` outside 1–8 → clamp
    - unknown `activeProfile` string → keep it verbatim (a future profile must not be destroyed by an
      older build) but do not let it select anything
    Never throw and never assert on bad input: a corrupt project file must degrade, not take the
    host down.

    In the processor: hold a `State` member. Replace the 01-01 stubs —
    `getStateInformation`: copy `apvts.copyState()`, attach the state node via `writeTo`, then
    `juce::AudioProcessor::copyXmlToBinary`.
    `setStateInformation`: `getXmlFromBinary`, bail out cleanly if null or if the tag does not match
    the APVTS type, then `apvts.replaceState` and `State::readFrom`.
    Keep both strictly on the message thread; `processBlock` must remain untouched by this plan.
  </action>
  <verify>`grep -n 'new \|delete\|lock' src/PluginProcessor.cpp` shows no change inside processBlock; the round-trip test from Task 3 passes, including its malformed-input cases</verify>
