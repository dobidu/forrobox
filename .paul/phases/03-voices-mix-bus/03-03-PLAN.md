<objective>
## Goal

Finish the signal chain `PLANNING.md` specifies — `voices → character bus → limiter → master` — and
then do the thing the whole phase exists for: **listen to all four grooves against the prototype and
fix what does not match.**

Three pieces, all global:

1. **Character bus** — parallel dry/wet. The wet path is a lowpass into a `tanh` drive; each timbre
   sets its own cutoff and drive, and the `MIX` knob sets the blend. Both are smoothed.
2. **Limiter** — −6 dB, knee 0, 20:1, 2 ms attack, 120 ms release; off means transparent rather than
   removed, so toggling it cannot click. It must report its gain reduction, because Phase 8's GR
   meter is the only thing that will ever read it and reopening the limiter then is worse.
3. **Master** — `gain = (value/100)²`.

## Purpose

Phase 3's goal, verbatim from ROADMAP: "The four profiles audibly match the prototype. Verified by
A/B listening before any UI work begins." 03-01 made it audible and 03-02 made it breathe; neither
could be judged against the prototype, because until the character bus and the limiter exist the
plugin is neither shaped nor gain-staged like the thing it is being compared to.

This is also the last plan in Phase 3, so closing it triggers the phase transition.

- Gain reduction published for Phase 8
- `scripts/render-audition.sh` rendering the finished chain

## Specification — the authority, quoted

`PLANNING.md` → **Timbre character** (~line 619) and **Limiter & master** (~638) give the numbers.
`audio.js:26-130` is the graph they describe:

```js
// master chain: sum -> character -> limiter -> masterGain -> out
charInput.connect(charDry);                       // dry path
charInput.connect(charFilter);                    // wet path: lowpass ...
charFilter.connect(shaper); shaper.connect(charWet);   // ... into tanh

limiterNode.threshold.value = -6;  knee = 0;  ratio = 20;
limiterNode.attack.value = 0.002;  release.value = 0.12;
master.gain.value = 0.85;                          // then setMaster(state.master/100)

setMaster (v01) { master.gain.value = v01 * v01; }
setLimiter (on) { threshold = on ? -6 : 0;  ratio = on ? 20 : 1; }   // transparent, not removed

// setTimbre:
let cut = 18000, drive = 1;
if (id === "hifi") { cut = 16000; drive = 1.2; }
else if (id === "lofi") { cut = 5200; drive = 2.4; }
else if (id === "ciclo") { cut = 9000; drive = 9; }
curve[i] = Math.tanh (x * drive);                  // x over [-1, 1], 1024 points
charFilter.frequency.setTargetAtTime (cut, now, 0.02);
const wet = id === "hifi" ? m * 0.5 : m;
charWet.gain.setTargetAtTime (wet, now, 0.02);
charDry.gain.setTargetAtTime (1 - wet * 0.5, now, 0.02);
```

Five things the prose does not say, and that the sketch settles:

- **`HI-FI` halves its own wet gain** (`m * 0.5`), the other two do not. So at `MIX` 100 the wet path
  is 0.5 for HI-FI and 1.0 for the others — HI-FI is the subtle one by construction.
- **Dry is `1 − wet × 0.5`, not `1 − wet`.** The two paths deliberately sum to more than unity, which
  is part of why the limiter is on by default.
- `setTargetAtTime(target, now, 0.02)` is an **exponential one-pole with a 20 ms time constant**, not
  a linear ramp: `v(t) = target + (v0 − target)·e^(−t/τ)`.
- The lowpass is a `createBiquadFilter()` whose **Q is never set, so it is Web Audio's default of
  1.0** — not Butterworth 0.707. That is a small resonant lift at cutoff, and it is the spec.
- The limiter is **never bypassed structurally**; "off" sets threshold 0 dB and ratio 1:1 so the same
  node stays in the path. Removing it would click.

## AC-1: The character bus shapes the sound the way the spec says

```gherkin
Given each of the three timbres in turn at MIX 100
When a broadband signal is rendered through the bus
Then energy above that timbre's cutoff is attenuated relative to below it, and LO-FI at 5.2 kHz
  attenuates more than CICLOTRON at 9 kHz, which attenuates more than HI-FI at 16 kHz
And the wet path adds harmonic content that is not in the input, more at higher drive
And at MIX 0 the output is the dry input at unity, to within the smoother's settling error
```

## AC-2: HI-FI is halved and the dry path is not

```gherkin
Given MIX at 100
When the wet and dry gains are read for each timbre
Then HI-FI's wet gain is 0.5 and LO-FI's and CICLOTRON's are 1.0
And every timbre's dry gain is 1 − wet × 0.5, so HI-FI is 0.75 and the others 0.5
And nothing in the bus assumes dry + wet == 1
```

## AC-3: Cutoff, drive and mix changes are smoothed, not stepped

```gherkin
Given the bus running with a steady input
When the timbre or MIX changes between one block and the next
Then no output sample jumps by more than a stated bound, at any block size
And the new value is reached with a 20 ms exponential time constant, measured
And the smoothing is per sample, so the result does not depend on where the block boundary fell
```

  <action>
    Create `forrobox::MixBus` as a **sibling** member of the processor, prepared and reset alongside
    the engine, processed in place immediately after `engine.render (buffer)`.

    A sibling rather than part of `VoiceEngine`, and this overrides STATE's original Phase 3 design
    input ("a persistent VoiceEngine … owning voices, RNG, the jitter queue, smoothers, character bus
    and limiter"). The reasons, recorded here so the choice is deliberate:

      - the engine is about VOICES — a pool, per-voice state, per-lane keys. The bus is one global
        stage with no per-voice anything
      - `render` already sums into a buffer the processor cleared, so a sibling composes cleanly
      - 03-02 reduced `processBlock` to a single `engine.render` call site precisely so a second stage
        could be added without the +3.5 dB-on-Stop trap
      - splitting the settings means each stage reads only what it uses

    So split `resolveChannelSettings` into two resolvers: the engine's (per-channel plus `cachaca`)
    and the bus's (`timbre`, `charMix`, `limiterOn`, `master`). Do not grow
    `VoiceEngine::Settings` with values the engine never reads.

    Implement the graph as the sketch has it, in this order per sample:

      wet = tanh (lowpass (x) * drive)
      out = x * dryGain + wet * wetGain

    Put the three timbres in a declarative table beside the humanisation constants' pattern — a
    `TimbreSpec { cutoffHz, drive, halvesWet }` array indexed by the `timbre` choice index, so it
    diffs against `PLANNING.md`'s table line by line. `halvesWet` is HI-FI's `m * 0.5`; it is the one
    per-timbre irregularity and it must not be a special case buried in the process loop.

    Use `juce::dsp::StateVariableTPTFilter<float>` for the lowpass, one per channel, with
    **resonance 1.0** — 03-01 verified that JUCE's `resonance` IS Q, and Web Audio's default
    BiquadFilter Q is 1.0, not 0.707. Do not "fix" it to Butterworth; the resonant lift is the spec.

    Apply `tanh` directly rather than through a 1024-point table. This is a deliberate deviation:
    Web Audio's `WaveShaperNode` samples its curve over [-1, 1] and CLAMPS beyond, so at drive 1.2 an
    input of 2.0 comes out at tanh(1.2) = 0.834 where direct tanh gives 0.984. The grooves peak at
    1.454, so inputs do exceed 1.0 and the difference is real. Direct tanh is chosen because a
    waveshaper with a hard ceiling at an arbitrary input level is a table artefact, not intent, and
    "correct plugin practice wins wherever the two conflict" (PROJECT.md). Record it, and listen for
    it at AC-7 — if CICLOTRON sounds wrong, this is the first thing to check.

    Smooth cutoff, wet gain and dry gain with a **one-pole, 20 ms time constant**, per sample:
    `coeff = 1 - exp (-1 / (0.02 * sampleRate))`, `current += (target - current) * coeff`. That is
    exactly `setTargetAtTime`. `juce::SmoothedValue` is a LINEAR ramp over a duration and is not the
    same curve — do not substitute it. Name the constant; do not write 0.02 at three sites.

    Avoid: allocating in `process`; `juce::SmoothedValue` for these three; a table-based shaper;
    recomputing the filter coefficient per sample when only the target moved (set the cutoff on the
    filter once per block from the smoothed value — per-sample `setCutoffFrequency` calls `std::tan`
    every sample, which 03-01 measured as the single most expensive thing in the engine).
  </action>
  <verify>
    Per timbre at MIX 100, band energy above the cutoff falls relative to below it, and the three
    cutoffs order correctly. Harmonic content appears that is not in a pure-tone input, more at
    higher drive. At MIX 0 the output matches the input to within the settling error. Wet and dry
    gains read 0.5/0.75 for HI-FI and 1.0/0.5 for the others. A timbre change mid-render produces no
    sample jump above the stated bound at block sizes 32 and 2048, and the measured settling time is
    20 ms. All three compilers green.
  </verify>
  <done>AC-1, AC-2 and AC-3 satisfied.</done>
</task>

<task type="auto">
  <name>Task 2: Limiter, master, and the gain reduction Phase 8 needs</name>
  <files>src/MixBus.h, src/MixBus.cpp, src/PluginProcessor.h, src/PluginProcessor.cpp, tests/VoiceTest.cpp</files>
  <action>
    Use `juce::dsp::Compressor<float>` — it takes exactly the four parameters the spec names
    (threshold, ratio, attack, release) and its knee is fixed at 0, which is also the spec. Do not
    hand-roll a limiter, and do not use `juce::dsp::Limiter`, which fixes ratio and attack.

    On: threshold −6 dB, ratio 20, attack 2 ms, release 120 ms. Off: threshold 0 dB, ratio 1 — the
    same object, made transparent, exactly as the sketch does it. `PLANNING.md` says "bypassed rather
    than removed, to avoid a click", so the object must stay in the path and the toggle must be a
    parameter change, not a branch around it.

    Then master: `gain = (value/100)²`, applied after the limiter. Smooth it with the same one-pole as
    Task 1 — a master fader that steps on a block boundary is the most obviously wrong thing a mix
    bus can do, and nothing in the spec says otherwise.

    **Publish the gain reduction.** `juce::dsp::Compressor` has no accessor for it, so derive it: the
    block's peak in against the block's peak out through the limiter stage, expressed in dB, stored in
    a relaxed atomic. Phase 8 wires the meter (`ROADMAP` names it) and Phase 5 may show it earlier.

    This is deliberately an accessor with no current consumer, which the project's own rule warns
    about — so the justification has to be explicit: the alternative is a limiter that computes the
    information and throws it away, and Phase 8 reopening this file to get it. A test asserts the
    value is real (non-zero under limiting, zero when off), which is what makes it a measurement
    rather than a promise. Note in the code that the figure is a per-block peak ratio, NOT the
    compressor's instantaneous internal gain the way Web Audio's `reduction` is — a meter polled per
    frame cannot tell the difference, and the honest description belongs next to the value.

    Avoid: a `if (limiterOn)` branch that skips the compressor (it would click, and the spec says so);
    an unsmoothed master; computing gain reduction by dividing sample by sample (it divides by zero
    between hits); reporting a positive number for "no reduction" (the meter grows right-to-left from
    zero).
  </action>
  <verify>
    A signal at 1.454 comes out held near −6 dB with overshoot no worse than a 2 ms attack allows.
    Reported gain reduction is non-zero under limiting and exactly zero with the limiter off. With
    the limiter off the output equals its input exactly. Master at 100/82/50/0 gives 1.0/0.672/0.25/0
    of the input, and 0 is exact silence. Toggling the limiter mid-render produces no discontinuity
    above the AC-3 bound. Zero allocations across 2000 blocks. All three compilers green.
  </verify>
