<objective>
## Goal

Port the musical content — the heart of the product — from `data.js` into C++: the four regional
profiles with their eight pattern lanes each, their tempo/swing/cachaça/timbre settings and mute
state, the velocity notation that decodes them, and the tiling that fills a 16- or 32-step window.
Prove the tables are verbatim by cross-checking the C++ source against `data.js` mechanically, not
by eye.

## Purpose

`PLANNING.md` calls this "the heart of the product" and says it "should be ported verbatim". It is
also the one part of the project where a silent transcription error would be invisible: a wrong
digit in a pattern is not a crash or a failed test, it is a groove that is subtly wrong, and nobody
would know which digit. The clock (02-02) has nothing meaningful to advance over until these tables
exist, and Phase 3's A/B listening test is only valid if the patterns are right.

## Output

- `src/Profiles.h` / `.cpp` — the four profiles, the velocity decoder, and expansion into lanes
- `src/ParameterIDs.h` — profile identifiers added to the single source of truth
- `scripts/verify-profiles.py` — mechanical `data.js` ↔ C++ cross-check
- `tests/StateRoundTripTest.cpp` — decoder, tiling and profile-load cases
</objective>

## AC-1: The velocity notation decodes exactly as specified

```gherkin
Given the notation rule from PLANNING.md: '.' is a rest, '1'-'9' is level × 14, spaces are cosmetic
When a 16-character pattern string is decoded
Then '.' yields 0 and '9' yields 126
And every digit d yields min(127, d × 14)
And whitespace anywhere in the string is ignored without shifting any step
And the result always has exactly 16 entries, all within 0..127
And a string with the wrong number of significant characters is rejected rather than silently padded
```

## AC-4: Tiling fills the whole lane, independent of the window  [REVISED 2026-09-07]

Original wording required "expansion never writes beyond the window", i.e. slots 16-31 zeroed at a
16-step window. `/code-review` showed that contradicts the prototype and the 01-02 decision: `app.js`
`setSteps` re-tiles (`out[i] = arr[i % old]`), so loading a profile at 16 steps and later switching
to 32 gives a silent second bar in the port where the prototype repeats bar 1 — and what you hear
depends on whatever STEPS happened to be at load time. Since expansion always tiles from a 16-entry
base, filling all 32 costs nothing and makes profile load window-independent, which is what "the
window is a view, not a storage size" actually implies.

```gherkin
Given a decoded 16-entry pattern
When it is expanded into a lane
Then every one of the 32 slots is filled, with lane[i] equal to pattern[i mod 16]
And the result does not depend on the current step count
And switching the step window later changes which slots are read, never their contents
```

## AC-5: Loading a profile fills every lane

```gherkin
Given a forrobox::State and a chosen profile
When that profile is applied at a given step count
Then all 8 lanes are filled: zabumba, triangulo, pandeiro, ganza, bb, cx, hh, tom
And bateria's four kit pieces come from the profile's bb/cx/hh/tom patterns, not from one shared lane
And activeProfile is set to the profile's id
And no lane is left at its previous contents
And applying a second profile fully replaces the first, leaving nothing behind
```

      **verbatim** from `data.js`, including the cosmetic spaces every four characters. Keeping the
      spacing makes a visual diff against `data.js` meaningful and gives Task 3's cross-check an
      exact target.
    - `findProfile(juce::StringRef id) -> const Profile*`, returning nullptr for an unknown id so a
      project saved by a newer build degrades rather than resolving to the wrong groove.

      caruaru   138 / 54 / 32 / HI-FI

<task type="auto">
  <name>Task 2: Expansion into state lanes with 16/32 tiling</name>
  <files>src/Profiles.h, src/Profiles.cpp</files>
  <action>
    Add to `forrobox`:

    - `expandPattern(const std::array<std::uint8_t,16>& base, int steps) -> State::Lane` filling a
      full 32-slot lane by `lane[i] = base[i % 16]` for `i < steps`, and zero beyond `steps`. Lanes
      stay 32 slots regardless of the window — the 01-02 decision — so the window is a view, not a
      storage size. Clamp `steps` to the legal set (16 or 32) rather than trusting the caller.
    - `applyProfile(State&, const Profile&, int steps)` filling all 8 lanes from the profile's
      patterns and setting `activeProfile` to the profile id. Fill every lane unconditionally: a
      profile whose pattern happens to be all rests must still overwrite whatever was there, or a
      profile switch would leave the previous groove bleeding through.
    - Bateria's four kit pieces come from the profile's own `bb`/`cx`/`hh`/`tom` patterns. Do not
      collapse them into one lane; `PLANNING.md` treats the collapsed BATERIA sequencer row as a
      *display* of the maximum across the four, not as storage.

    Keep everything here a pure function of its inputs — no globals, no I/O, no allocation beyond the
    caller's `State`. Phase 2's later plans will call this from the message thread and hand the
    result to the audio thread through a double-buffer swap, so anything stateful here would become a
    race later.

    Do NOT set any parameter. `applyProfile` reports the profile's bpm/swing/cachaça/timbre through
    the `Profile` it was given; actually moving those parameters is Phase 6's full-reload behaviour
    and doing it here would make this plan touch the APVTS from a place that has no business doing so.
  </action>
