<objective>
## Goal
Replace the three separate audio→UI atomics with one group-atomic publication, and build the three
views that read it: a continuous playhead sweeping the sequencer, a trigger LED in each strip head,
and an activity meter in each strip's reserved `hitVisualiser` box.

## Purpose
Phase 5's goal is that the sequencer is playable and LEGIBLE. 05-01 made it playable — pads show the
pattern and edit it. Nothing yet shows the groove MOVING: the plugin plays and the UI is static.

This is also PROJECT.md's Phase 2 item coming due. `currentStep`, `lastStepVelocities` and
`emittedSteps` are three separate atomics, *"ordered but not group-atomic"* — so a reader can see
step N with step N-1's velocities. Nothing read them until now, which is why it has never mattered.
Three views arriving at once is the forcing function.

- `src/StepSnapshot.{h,cpp}` — the group-atomic publication, audio-thread side
- `src/Playhead.{h,cpp}` — the sweeping line
- `src/HitVisualiser.{h,cpp}` — one strip's LED and activity meter
- The strip head's trigger-LED box reserved and cross-checked
- Reference renders showing the playhead mid-sweep and meters mid-decay

## AC-1: One publication, group-atomic, and the audio thread still allocates and locks nothing

```gherkin
Given the audio thread emitting a step
Then the step index and its eight lane velocities are published as ONE snapshot
And no reader can observe one step's index beside another step's velocities
And `processBlock` allocates nothing and takes no lock
And a torn read is proved impossible by a test that would SEE one if the publication were split
```

**A 16-byte `std::atomic<T>` is not guaranteed lock-free and `processBlock` is contractually
lock-free.** `std::atomic<T>::is_always_lock_free` must be asserted for whatever is actually used —
an assertion on the wrong type is the shape this project keeps finding. The mechanism is a
double-buffer with an atomic index, mirroring PROJECT.md's stated constraint for the pattern going
the other way (*"double-buffer or `AbstractFifo` swap, never in-place mutation"*).

`positionInSteps` is published SEPARATELY as a plain `double`. It is naturally lock-free, and it does
not need to be consistent with the trigger snapshot: the playhead and the LEDs are different views
of different questions. Bundling them would buy nothing and cost the lock-free guarantee.

## AC-2: The playhead sweeps continuously, and its position is the clock's

```gherkin
Given the transport running
Then a 3 px line sweeps the sequencer's pad strips, top -3 px to bottom +3 px, in `--c-pandeiro`
And its horizontal position is derived from the clock's position in steps, not from a UI counter
And it spans every row, not only the first
And when the transport stops it is hidden, not frozen mid-sweep
And nothing about it runs on the audio thread
```

**The prototype gets its sweep free from CSS** — `movePlayhead` sets
`transition: left <stepDur>ms linear` and the browser interpolates. JUCE has no such thing, so the
sweep is driven from `positionInSteps` at frame rate. That is a DIVERGENCE worth naming: the
prototype glides to each step's centre over one step duration and waits there when swing delays the
next trigger, while a position-driven sweep is linear in musical time. The checkpoint judges it.

## AC-3: Each strip's LED and activity meter follow the triggers, and respect mute/solo

```gherkin
Given a channel triggering
Then its 8 px head LED goes from resting 0.22 opacity to `0.25 + vel x 0.75` with a
  `0 0 <2 + vel x 7>px` glow
And its activity meter fills to `scaleX(level)` at `0.35 + level x 0.65` opacity over 16 tick
  divisions
And the level is `max(level, velocity)` on trigger and decays by x0.82 per frame
And a MUTED or soloed-out channel does NOT light up — `PLANNING.md:489`
And the decay is told elapsed frames rather than reading a clock, as `GainReductionMeter` is
```

**`GainReductionMeter` is the precedent and it is load-bearing.** 04-05 built it told-the-elapsed-time
rather than reading a clock, because three checks had failed on MSVC's clock rather than on the code.
The same applies here: x0.82 per frame is a per-FRAME law, so the meter is told how many frames
passed.

## AC-4: The strip head's LED box is reserved and cross-checked

```gherkin
Given the strip head row
Then the trigger LED has a reserved 8 x 8 rectangle, vertically centred, 7 px left of the index
And that gap and that diameter are cross-checked against forrobox.css by verify-geometry.py
```

<task type="auto">
  <name>Task 1: One group-atomic publication, replacing three loose atomics</name>
  <files>src/StepSnapshot.h, src/StepSnapshot.cpp, src/PluginProcessor.h, src/PluginProcessor.cpp, tests/VoiceTest.cpp</files>
  <action>
    Build the audio→UI publication as ONE snapshot and retire the three separate atomics.

    The snapshot carries the step index and the eight lane velocities together. Publish it through a
    double-buffer with an atomic index — write the inactive slot, then store the index with release
    ordering; the reader loads the index with acquire and reads that slot. Mirror of the pattern
    handover going the other way, and PROJECT.md's stated constraint for exactly this.

    `static_assert` that the index atomic is `is_always_lock_free`. Assert it on the TYPE ACTUALLY
    USED — an assertion on a neighbouring type is the shape this project keeps finding.

    Publish `positionInSteps` separately as a plain `double` (assert lock-free too). It is the
    playhead's input: its integer part is the step and its fraction is the phase, which is what the
    clock already computes as `Span.startInSteps`. Do NOT fold it into the snapshot — it would push
    the struct past any lock-free width for no benefit, since the playhead and the LEDs answer
    different questions and need no mutual consistency.

    Retire `currentStep`, `lastStepVelocities` and `emittedSteps` as separate members. Keep
    `getEmittedStepCount()` working — `PluginProcessor.h:138` records that it exists to catch a step
    emitted twice in one block, which is a real hazard 02-02 hit and must not be lost.

    Avoid: a hand-rolled seqlock. 02-04 judged and rejected one for the pattern — it needed atomic
    bytes at 30x the copy cost and could latch its generation odd, wedging the audio thread on a
    stale table for a session. The same reasoning applies here.

    Avoid: publishing from anywhere but the audio thread, and avoid making the UI side able to write.
  </action>
  <verify>
    Build and run under GCC and Clang, `DISPLAY` unset.
    A test that would SEE a torn read: drive the processor so consecutive steps carry DIFFERENT
    velocity sets, read the snapshot from a second thread in a tight loop, and assert every
    observation is a step paired with ITS OWN velocities. Prove the test can fail by publishing the
    two halves separately in a throwaway build and confirming it reports a tear.
    Re-run the existing allocation-window test (500 blocks) and the zero-allocation counter.
  </verify>
  <done>AC-1 satisfied. `/code-review` run and its findings answered before Task 2 begins.</done>
