<objective>
## Goal
**A user can save, find, rename and delete their grooves without leaving the chassis.**

**The side panel** (user decisions: a fifth entry, labelled **MEUS GROOVES**):
- Below UNIVERSITÁRIO, the same `.profile` box model (`ProfileButton`, a USER variant: no
  `profileInfos` entry, its own name and description).
- **Description** (shown when active, like the regional three lines): the count — "1 groove salvo" /
  "N grooves salvos" — and how to add one: "Salve pelo menu ⚙." With an empty library the entry
  still shows, text dimmed, and its click does nothing.
- **Click** loads the first groove of the sorted bank (`loadUserGroove`), as a regional click loads
  that profile's default groove. The header cycler then walks the user bank (18-01).
- **Active** when the state is `user/<id>` and pristine — the regional rule (`app.js:555`): an
  edited state is no longer the groove it names. The CUSTOM tag behaves exactly as for a regional
  profile.
- **It fits.** Measured on the 1.0x render: ~40 px between the MIX row and the bundle; one more
  collapsed entry costs ~32 px, and the tall active box is still one of five. A layout test asserts
  the MIX row stays above the bundle with each of the five entries active and with none.
- The header's STYLE switch keeps four segments; none is lit under `user` (`indexOfProfile` → -1,
  as now).

**The gear menu** gains a GROOVES band above About (English, like the rest of the menu):
- `Save groove as…` — always.
- `Save over "<name>"`, `Rename "<name>"…`, `Delete "<name>"…` — enabled only while the state names
  a user groove this library has; `<name>` is that groove.
- `SettingsMenu::build` takes the active user groove's name (or none); `apply` returns new results
  (`saveAs`, `saveOver`, `rename`, `remove`) that write nothing to Settings — the Chassis dispatches
  them. Save-over acts at once (it is the user's own groove, chosen by name in the menu).

**The preset screen's inline prompt** (user decisions: inline name entry; inline delete confirm):
- **Name entry** (save as / rename): the header's groove-name screen becomes a text field, styled
  as `BpmField`'s inline editor is (screen ground and foreground). Pre-filled: empty for save-as,
  the current name for rename, all selected. **Enter** commits, **Esc** or a click elsewhere
  cancels. Input is limited to `kMaxUserGrooveNameLength`; Enter on an empty or invalid name keeps
  the field open.
- **Delete confirm:** the screen reads `APAGAR <name>? ↵`; Enter deletes, Esc or a click elsewhere
  cancels.
- **A failure** (an unwritable folder) shows `ERRO: NÃO SALVO` on the screen for ~2 s, then the
  normal name returns. The library's `Result` text goes to the debug log.
- While the prompt is open the cycler arrows and the poll's `setText` leave the screen alone.

**Every instance told** (18-01's deferred finding):
- `UserGrooveLibrary` gains a synchronous `juce::ListenerList` (13-01's decision for Settings):
  `grooveOverwritten(id)`, `grooveRemoved(id)`, and `libraryChanged()` after any write.
- Each processor registers on construction and leaves on destruction. An instance whose state is
  `user/<id>` marks itself dirty when ANOTHER instance overwrites or deletes `<id>` — its lanes are
  no longer that groove. The writer itself adopts or marks as 18-01 does.
- A nested write from inside a notification is refused (`jassertfalse`, a failing `Result`), the
  rule 14-01's /code-review gave Settings.
- Another PROCESS's writes are still seen on the next rescan (no file watching — 18-01's scope).

## Purpose
- **ROADMAP Phase 18:** "browsable beside the 16 built-in grooves … Rename, overwrite, delete".
  Phase 18 closes with this plan.
