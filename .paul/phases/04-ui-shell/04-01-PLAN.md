<objective>
## Goal

The plugin window shows the Forró Box chassis — correct background surfaces, borders, shadows and
region geometry for the header / matrix / sequencer / footer rows and the 280 px side panel — at any
host size from 0.7× to 2×, in both themes, with all seven specified font weights rendering at their
real weights.

No controls yet. Knobs are 04-02, pads and buttons 04-03, header/footer wiring 04-04.

## Purpose

Three of Phase 4's six ROADMAP concerns are infrastructure that every later plan and every later
phase reads: the design tokens, the fonts, and the fixed-design-px coordinate system. Getting them
wrong is not a visible bug in this plan — it is a wrong colour in Phase 6's side panel and a wrong
type weight in Phase 5's row labels, with nothing pointing back here.

It also builds the instrument the rest of the phase is measured with. Phase 3 established that audio
claims are proved by offline render plus measurement, with listening as a separate human checkpoint.
The same split applies to the UI, and the equivalent instrument was **verified during planning**: a
`Component` that is never added to a desktop needs no window peer, so it can be painted into a
`juce::Image` headlessly and read back pixel by pixel. Measured in the planning spike: probing
(5,5) returned exactly `ff141414` and (20,20) exactly `ffe8650a`, on this machine, with no display.

## Output

- `assets/fonts/` — seven TTFs plus both families' OFL licence files
- `scripts/build-fonts.py` — the one-time, re-runnable asset build (fetch, instance, name-patch)

- `src/PluginEditor.*` — the scale transform, replacing the placeholder paint
- `tests/UiTest.cpp` — a fourth suite: the headless render harness and its own self-tests

<acceptance_criteria>

## AC-1: The fonts are real, all seven weights, and provably distinct

```gherkin
Given the seven embedded typefaces (Space Grotesk 400/500/600/700, IBM Plex Mono 400/500/600)
When each is loaded from binary data and asked for its name and style
Then each reports family "Space Grotesk" or "IBM Plex Mono" and its own style name, with no two
  faces in a family reporting the same style
And rendering the same string at the same height in each weight of a family produces strictly
  increasing ink mass with at least a 5% step between adjacent weights
And both families' OFL licence files are present in assets/fonts/
```

**Why ink mass and not advance width.** Measured in the planning spike at 24 px: the four Space
Grotesk widths for "FORRO BOX" are 100.326 / 100.589 / 100.646 / 100.777 — a 0.45% total spread,
which no honest tolerance can separate from rounding. Ink mass over the same string is
417.3 / 523.2 / 572.3 / 617.9, a 9% smallest step. A width-based assertion would pass with four
copies of one weight, which is exactly the failure this criterion exists to catch.

## AC-2: Every token matches forrobox.css, and cannot drift from it

```gherkin
Given the C++ token tables for both themes
When scripts/verify-theme.py compares them against forrobox.css's :root and [data-theme="light"]
Then every colour token in both themes matches by value, every instrument accent matches, and
  neither side has a token the other lacks
And the check runs on every build, failing the build on divergence
And a mutation to any single token value in either file fails the check, naming the token
```

```gherkin
Given the editor at any size from 840x546 (0.7x) to 2400x1560 (2x)
```

<task type="auto">
  <name>Task 1: Build, embed and verify the seven font weights</name>
  <files>scripts/build-fonts.py, assets/fonts/*, src/Typography.h, src/Typography.cpp, CMakeLists.txt</files>
  <action>
    Write `scripts/build-fonts.py` — a one-time but re-runnable asset build, committed so the
    provenance of every byte in assets/fonts/ is reproducible rather than remembered.

    **The refinement the decision needs, verified during planning.** The approved option was
    "fetch upstream static TTFs + OFL.txt". Space Grotesk has NO static SemiBold anywhere upstream:
    floriankarsten/space-grotesk publishes Light/Regular/Medium/Bold statics plus
    `SpaceGrotesk[wght].ttf`, and google/fonts publishes the variable font ONLY. The design uses 600
    for five things (instrument names, sequencer row labels, profile names, timbre names, global
    knob labels), so 600 cannot be skipped.

    Loading the variable font directly is not the answer either: JUCE 8.0.12 bundles HarfBuzz with
    the variable tables but `juce::Typeface`'s public API exposes no variation-axis setter, so
    `createSystemTypefaceFor` loads the face's DEFAULT instance — and Space Grotesk's fvar default
    is **wght=300, Light**. Every weight in the UI would render at the thinnest one, silently.

    So: fetch the variable font once and instance it offline into four static TTFs. Verified working
    during planning with fonttools 4.63.0, already on this machine.

    - Fetch `https://raw.githubusercontent.com/google/fonts/main/ofl/spacegrotesk/SpaceGrotesk%5Bwght%5D.ttf`
      and that directory's `OFL.txt`
    - Fetch `IBMPlexMono-Regular.ttf`, `-Medium.ttf`, `-SemiBold.ttf` and `OFL.txt` from
      `https://raw.githubusercontent.com/google/fonts/main/ofl/ibmplexmono/` — these ARE published
      as statics at exactly the three weights the spec asks for, so they are used as fetched
    - Instance Space Grotesk with `fontTools.varLib.instancer` at wght 400/500/600/700

    **Patch each instance's name table.** `--update-name-table` does NOT work here — it raises
    `ValueError: Cannot find Axis Values {'wght': 600.0}` because the STAT table declares no named
    axis value at 600. And the un-patched output is worse than merely unhelpful: the instancer sets
    `usWeightClass` correctly but leaves name ID 1 as **"Space Grotesk Light"** and name ID 2 as
    "Regular" for every weight, so JUCE reports all four as the same family and style. Set name IDs
    1, 2, 4, 6, 16 and 17 explicitly per weight, in both the Windows (3,1,0x409) and Mac (1,0,0)
    encodings. Verified: the four then report Regular / Medium / SemiBold / Bold under family
    "Space Grotesk".

    Add a SECOND binary-data target `ForroBoxFonts` via the existing `forrobox_add_binary_data`,
    with its own NAMESPACE (`FontData`) and HEADER_NAME (`FontData.h`). Do not add the fonts to
    `ForroBoxSamples`: that target's header is included by the audio code, and a font change should
    not recompile the sampler.

    `src/Typography.h/.cpp` exposes the faces and the type scale:
    - Seven `juce::Typeface::Ptr`, created once and cached. Message thread only — say so at the
      declaration, since Phase 3's habit is to state the thread at the boundary
    - A `TextStyle { const char* element; float heightPx; Weight weight; float letterSpacing;
      bool uppercase; }` table, one row per row of PLANNING.md's type-scale table, keyed by an
      enum. The element NAME travels with each row so a diff against the spec is readable — the
      same reason `voiceSpecs`' anonymous positional rows were flagged in Phase 3
    - Look faces up by explicit Ptr, NEVER by `juce::Font("Space Grotesk", "SemiBold", h)`. The
      four faces are separately registered and the name-based path is not what is being relied on
    - JUCE has no letter-spacing on `Font`, and the design leans on it heavily (0.13em on the
      wordmark, 0.20em on section labels). Provide one helper that draws a tracked string by
      advancing per glyph, so 04-03 and 04-04 do not each invent one

    Avoid: committing the variable font itself (it would invite someone to load it and get Light);
    subsetting to shrink the ~620 KB (the Portuguese copy needs Ó Â Á Ç and Phase 8 needs ♪ U+266A —
    check coverage, record what is missing, but do not subset in this plan).
  </action>
  <verify>
    `python3 scripts/build-fonts.py --verify` re-derives every file and reports byte-identical.
    The UiTest font checks report seven faces with distinct styles per family and strictly
    increasing ink mass with a >=5% step. `ls assets/fonts/` shows both OFL files.
  </verify>
  <done>AC-1 satisfied: seven weights load, are distinct by name and by measured ink, licences ship.</done>
</task>

<task type="auto">
  <name>Task 2: Generate-and-cross-check the design tokens for both themes</name>
  <files>src/Theme.h, src/Theme.cpp, scripts/verify-theme.py, CMakeLists.txt</files>
  <action>
    `src/Theme.h/.cpp` holds both palettes. One array of structs per the `channelInfos` pattern —
    `{ const char* cssName; juce::uint32 dark; juce::uint32 light; }` — so a token cannot exist in
    one theme and be missing from the other, and the CSS name travels with the value.

    Cover: the 15 dark / 13 light surface and text tokens, the 5 instrument accents (identical
    across themes), the 4 bateria sub-colours, `--danger` (theme-independent), and the two
    tweakables `--r` (2 px default, 0 allowed) and `--accent-i` (1.0).

    Translate the alpha tokens honestly. `--fg-dim` is `rgba(232,232,232,0.5)` — an alpha colour
    over whatever is behind it, not a pre-blended opaque value. Store the alpha and let JUCE
    composite, or the light theme's text over `--panel` comes out wrong.

    Also carry the shadow and gradient recipes, which are as much of the look as the colours:
    the recessed inset pair, the raised-panel top highlight, the sequencer well, and the screen
    text glow — per theme, from PLANNING.md's "Spacing, radius, shadow".

    **`scripts/verify-theme.py`, wired into the build exactly like `verify-profiles`** (a stamp
    file, `DEPENDS` on the script and both inputs, `add_dependencies(ForroBox verify-theme)`, and
    NO `WORKING_DIRECTORY` — cmd.exe refuses the UNC current directory the Windows build uses).

    It parses `forrobox.css`'s `:root` and `[data-theme="light"]` blocks and compares every token
    against `src/Theme.cpp`, both directions, failing and naming the token on any divergence.
    This is the same argument as the groove tables and it is recorded as a project decision: a
    wrong hex digit is not a crash or a failed test, it is a colour that is subtly wrong with no way
    to tell which digit. Comparing against the design source is the only check here with real
    signal; a unit test holding the expected hexes by hand would duplicate the same typo risk.

    Note in the script what it does NOT cover: the type scale is spread across CSS rules rather than
    declared in one block, so it is transcribed from PLANNING.md's table by hand and is not
    cross-checked. Say so, so the gap is known rather than assumed closed.

    Avoid: `Colour::fromString` on the CSS text at runtime (parsing the stylesheet in the plugin
    makes the design file a runtime dependency); a `LookAndFeel` colour-ID map as the only home for
    the tokens (the IDs cover a fraction of them and Phase 6 needs the rest by name).
  </action>
  <verify>
    `python3 scripts/verify-theme.py` exits 0 and reports the token count for both themes. A
    one-digit mutation to any token in Theme.cpp, and separately in forrobox.css, fails it naming
    that token. A clean build runs it.
  </verify>
  <done>AC-2 satisfied: both themes match the stylesheet and the build enforces it.</done>

    over a `--line` background** — the gap IS the divider, so do not draw borders between strips;
    getting this wrong gives 2 px seams that read as heavier than the prototype.

    Each strip paints `--panel`, its accent bar (4 px, instrument colour, radius 1, with the soft
    glow at accent-intensity x 35%), and its own name and index from `ids::channelInfos` — the
    display names already live there and must not be re-typed. The zabumba strip carries `.anchor`:
    `--panel` mixed 88% with `--c-zabumba`. Keep it barely perceptible; the brief forbids
    decoration and this is the one tint that survives that rule.

    Inside the strips and the side panel, leave the control areas empty. Reserve their boxes so
    04-02/04-03/04-04 drop components into settled geometry rather than re-flowing the strip.

    `ForroBoxLookAndFeel` is created here but stays thin: the token accessors, the two font
    families, the default radius, and only the JUCE colour IDs that the components actually consume.

    other four geometry constants where they are; the tests and the constrainer both read them.

    Avoid: storing a second processor reference in the editor (the base class already keeps one, and

  </action>

<task type="auto">
  <name>Task 4: The headless UI measurement harness, self-tested</name>
  <files>tests/UiTest.cpp, tests/TestSuites.h, tests/TestHarness.h, CMakeLists.txt</files>
  <action>
    A fourth suite in the SAME executable. Phase 2 recorded why: a second executable recompiles the
    whole JUCE module set, and a suite that is built but never run reports nothing while looking
    like coverage.

    The harness — verified feasible during planning, so this is transcription of a working
    approach rather than exploration:
    - `renderComponent(Component&, int w, int h) -> juce::Image` — set bounds, construct an ARGB
      image, `paintEntireComponent(g, false)`. A component never added to a desktop needs no peer,
      so this needs no display. `ScopedJuceInitialiser_GUI` is already held by `TestMain`
    - `pixelAt(img, x, y) -> juce::Colour`, plus an `argb` comparison that prints both values as hex
      on failure — a colour mismatch printed as two decimal triples is unreadable
    - `inkMass(img, bounds)` — the sum of brightness, the weight discriminator AC-1 needs
    - `warmth(colour)` — for the anchor-tint assertion, so "measurably warmer" is a number

    **Each instrument gets its own proof, against a synthetic component with a known answer, and
    each proof includes a case the instrument must REJECT.** This is not optional ceremony: Phase 3
    found twelve wrong measurements before it found a wrong line of code, and the one instrument
    that already had a self-test was the pattern the other nine were missing. `bandEnergy`'s
    semitone grid never sampling 1000 Hz was found by exactly this, on its first run.

    Put the new helpers in `UiTest.cpp`, not `TestHarness.h`. STATE has carried "move the
    measurement layer out of `TestHarness.h`" since 03-02 because ~250 of its lines are DSP used by
    one suite and the other two suites recompile on every edit to it. Adding a second measurement
    layer to the same header would make that worse in the same plan that could avoid it.

    Avoid: asserting on a whole-image hash or a golden PNG (a one-pixel antialiasing difference
    between GCC and MSVC fails it, and the message tells you nothing); probing a coordinate on a
    region boundary (probe well inside, and say why at the call site).
  </action>

    Every harness self-test passes, including the rejection cases. The suite runs with no DISPLAY
    set — confirm explicitly with `env -u DISPLAY ./build-linux/ForroBoxTests`.
  </verify>
