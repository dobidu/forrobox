<objective>
## Goal

Give the audio thread a way to read the pattern grid that takes no lock, allocates nothing, and can
never observe a half-written table — while the message thread keeps editing it freely.

## Purpose

`PROJECT.md` states the constraint directly: "Profile loading touches many parameters at once —
message thread via APVTS, with the audio thread picking up new pattern tables via double-buffer or
`AbstractFifo` swap, never in-place mutation." `PLANNING.md` names the prototype's own
`loadProfile()` reassigning `state.grid` while the scheduler reads it as exactly the race to prevent.

Every phase after this one depends on it. Phase 3's voices must ask "what velocity is at this step?"
from `processBlock`. Phase 6's profile reload rewrites all eight lanes at once from a button press.
Phase 5's grid editing rewrites one cell per click. Today `processBlock` deliberately does not touch
`patternState` at all, and a comment says why — this plan is what removes that restriction safely.

It closes Phase 2: step advance (02-02), host sync (02-03) and now the data the steps will address.

<task type="auto">
  <name>Task 1: The publication mechanism and the reader's snapshot</name>
  <files>src/PatternSnapshot.h, src/PatternSnapshot.cpp, CMakeLists.txt</files>
  <action>
    Build the handover as its own small class so it can be stress-tested without a processor, the
    way `Clock` can be swept without a host.

    **The mechanism, decided at plan time.** A generation counter plus a reader-private snapshot:

    - The writer (message thread) increments a generation to an odd value, writes the staging copy of
      all eight lanes, then increments it to even. Odd means "a write is in progress".
    - The reader (audio thread) loads the generation. If it is even and differs from the one it
      already holds, it copies the staging lanes into its own private buffer and re-loads the
      generation. If the generation still matches, the copy is committed; if it changed, the copy is
      discarded and the reader keeps the snapshot it already had.

    The reader therefore never blocks, never spins and never retries in a loop — a failed attempt
    costs one block of staleness, and the next block tries again. And when nothing has been published
    the generation is unchanged, so it copies nothing.

    **Why not the two-slot index scheme STATE recorded.** With two slots and an atomic index, the
    writer's target is the slot the reader is not using — but after two publications the only
    remaining target IS the slot the reader is holding, and two publications inside one ~5 ms block
    are reachable (a profile reload that publishes then fixes up, a drag across pads,
    `setStateInformation`). Nothing in that design enforces the spacing it depends on. Record this as
    a deviation from the recorded decision, with the trace.

    The payload is `std::array<State::Lane, State::kNumLanes>` — 8 lanes x 32 slots = 256 bytes. Small
    enough that copying it is cheaper than any slot arithmetic, and the copy only happens when
    something actually changed.

    Give the snapshot an accessor for "velocity at lane L, storage index N" so callers cannot index
    it wrongly, and note that mutes, solos and the step window come from APVTS parameters rather than
    from here.

    Avoid: a retry loop on the audio thread (that is the one thing a seqlock must not do here);
    `std::mutex` or `juce::CriticalSection` anywhere on the read path; making the reader's private
    buffer shared, which would defeat the whole point. Check `juce::AbstractFifo` and
    `juce::SingleThreadedAbstractFifo` first and record why neither fits — they are queues, and this
    is latest-value publication, but the check should be on the record.
  </action>
  <verify>A stress test with a real std::thread writer runs many thousands of iterations with zero torn snapshots; the allocation counter reads 0 across the read path; a run with no publications performs no copies</verify>
  <done>AC-1, AC-2 and AC-3 satisfied</done>
</task>

<task type="auto">
  <name>Task 2: Publish from every writer; read once per block through an emitter</name>
  <files>src/PluginProcessor.h, src/PluginProcessor.cpp</files>
  <action>
    Own a `PatternSnapshot` publisher on the processor. Publish from every path that mutates pattern
    state — `setStateInformation`, and the `LockedState` handle's release, so a caller that edits
    through the handle cannot forget. If making the handle publish on destruction is awkward, give
    the processor an explicit `publishPatternState()` and call it from every writer, but then say in
    the comment why the automatic route was not taken, because "every writer must remember" is a
    trap this project has already hit once.

    In `processBlock`, take the snapshot **once**, then hand it to the clock through a
    stack-allocated per-block emitter that implements `forrobox::StepListener` — constructed in
    `processBlock` holding what a step needs: the snapshot pointer, and the counters to update. The
    processor stops being the listener itself.

    This is the landing site 02-03's review recommended, and the reason is specific: `stepTriggered`
    had accumulated two concerns that were not its own, and one of them was a mutable member set
    before `advance` and read inside the callback. **Do not reintroduce that shape.** A stack
    emitter carries per-block context in its own fields, where the lifetime is obvious.

    Keep the contract: no allocation, no lock, no `juce::String`, and `patternState` still not read
    from `processBlock` — the snapshot is what it reads.

    Avoid: taking the snapshot inside the emitter's callback (that is per-step, not per-block);
    holding the snapshot across blocks in a member, which would reintroduce shared mutable state;
    reading mutes or solos from the snapshot rather than from their parameters.
  </action>
  <verify>processBlock takes the snapshot exactly once per block (assert via a counter on the publisher); a state round-trip leaves the audio thread reading the restored grid; the plugin builds and loads in Ableton Live 12</verify>
  <done>AC-4 and AC-5 satisfied; AC-7's contract half satisfied</done>
</task>

<task type="auto">
  <name>Task 3: Prove the velocity mapping and the concurrency, and negative-control both</name>
  <files>tests/StateRoundTripTest.cpp</files>
  <action>
    Two groups of cases.

    **Velocity mapping (AC-6).** Build a grid whose value is distinguishable per lane and per step —
    something like `velocity = lane * 32 + index`, clamped into range — publish it, and drive the
    processor so the emitter records what it read for each step. Assert the value for lane L at step N
    is exactly the grid's, that 0 reads as no hit, and that a 16-step window still reads storage
    index N rather than a window-relative index. That last one matters: 02-01 settled that the 32
    slots are storage and `steps` is a view, and a reader that indexes by the window would silently
    play the wrong half of a 32-step pattern.

    **Concurrency (AC-1, AC-2).** A real `std::thread` writer publishing distinct tables in a tight
    loop while the main thread takes snapshots. Detect torn reads structurally rather than by
    eyeballing: make every published table self-identifying — e.g. every byte in the table derived
    from one seed — so a mixture of two publications is detectable from the snapshot alone. Run enough
    iterations to be meaningful and report how many publications the reader actually observed, so a
    run where the writer never got scheduled cannot pass as evidence.

    Follow the control practice this phase earned:
    - commit the verified state before running mutation controls;
    - controls restore from the commit and refuse to run on a dirty file;
    - build controls in a throwaway directory, never the one whose results are then trusted;
    - assert each mutation applied before trusting its result.

    Controls that must detect: removing the second generation check (torn reads appear); making the
    reader retry in a loop (AC-2's no-spin property); indexing the snapshot by window instead of
    storage; dropping the publish from `setStateInformation`; taking the snapshot per step rather
    than per block.

    Avoid an assertion that cannot fail — three shipped in 02-03. In particular "the concurrency test
    completed" is not evidence of anything; the evidence is the observed publication count and the
    torn-read count.
  </action>
  <verify>Every AC-6 mapping case passes; the concurrency case reports a non-trivial number of observed publications and zero torn reads; each listed control detects, with the mutation asserted applied first</verify>
  <done>AC-6 satisfied with evidence; AC-1 and AC-2 independently controlled; AC-8 satisfied</done>
</task>
