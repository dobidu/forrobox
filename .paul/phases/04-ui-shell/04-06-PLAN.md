<objective>
## Goal
Five extra stereo output buses in the VST3 bus layout, each carrying one channel's voices, and an
`OUTPUT` toggle that switches them on. `ids::outputMode` stops being inert.

## Purpose
The parameter has been declared, host-visible, automatable and persisted since Phase 1 while doing
nothing — PROJECT.md's "Emerged During Phase 3" list names it as the one thing Phase 4 had to settle,
and 04-04 settled it as *implement it for real*. 04-05 drew the control and left it read-only
precisely so this plan could make it honest. It is the last plan of Phase 4.

## Output
A plugin that presents six output buses to the host; five of them carry per-channel stems when
MULTI-OUT is selected, and the OUTPUT toggle is live.
</objective>

<acceptance_criteria>

## AC-1: The plugin presents six buses and still works as a stereo plugin

```gherkin
Given a host that only ever enables the main bus
When the plugin is loaded and a groove plays
Then it sounds exactly as it does today, sample for sample
And `isBusesLayoutSupported` accepts main-stereo with every aux bus DISABLED
And it accepts main-stereo with all five aux buses stereo
And it still refuses an input bus, because this is an instrument
```

**The stereo path is the regression surface, not the new one.** Every existing audio test renders
through a single stereo bus, and this plan changes `getTotalNumOutputChannels()` from 2 to 12. The
proof that stereo is untouched is a rendered comparison against the committed tree, not a green
suite.

## AC-2: Each stem carries one channel's voices, pre-everything

```gherkin
Given MULTI-OUT is selected and all six buses are enabled
When a groove plays
Then aux bus i carries ONLY channel i's voices, with VOL, PAN, mute and solo applied
And it carries NO character bus, NO limiter and NO master — those are mix decisions
And a channel muted to silence produces a silent stem
And soloing one channel leaves the other four stems silent
```

**Decided at planning, with the user:** stems are pre-character, pre-limiter, pre-master. The
consequence has to be stated rather than discovered — **the five stems summed do NOT equal the main
mix.** `tanh(a+b) != tanh(a)+tanh(b)`, so the character bus cannot be distributed over the stems, and
the limiter acts on the sum by definition. A test asserts the inequality rather than leaving someone
to find it.

## AC-3: The main bus always carries the full mix

```gherkin
Given MULTI-OUT is selected
When a groove plays
Then the main stereo bus carries voices -> character -> limiter -> master, exactly as in STEREO
And switching OUTPUT between STEREO and MULTI-OUT does not change the main bus by one sample
```

**Also decided at planning, with the user.** The alternative — main goes silent in MULTI-OUT — makes
a host that instantiated the plugin with aux buses disabled produce SILENCE with no indication why,
which is the worst failure a groovebox can have. The cost is that routing both main and stems
double-counts, which is audible and obvious rather than silent.

## AC-4: STEREO leaves the aux buses silent, and does not merely ignore them

```gherkin
Given STEREO is selected
When a block is rendered into a layout where all six buses are enabled
Then every aux bus is SILENT
And it is silent because it was CLEARED, not because nothing was written to it
```

**A bus nobody writes is not a bus that is empty.** The host owns that memory and may hand back
whatever was in it. This is the multi-bus form of the trap `processBlock`'s unconditional
`buffer.clear()` already guards against for the main bus.

## AC-5: Nothing indexes a raw channel number any more

```gherkin
Given six enabled buses, so getTotalNumOutputChannels() is 12
When VoiceEngine and MixBus read their output
Then each addresses its bus through getBusBuffer, never through buffer.getWritePointer(0)
And VoiceEngine's "is there a right channel" test asks the BUS's channel count, not the buffer's
```

**This is the defect the plan is most likely to ship.** `VoiceEngine::render` reads
`buffer.getNumChannels()` (`VoiceEngine.cpp:401`) and writes `getWritePointer(0)`/`(1)`; with five
aux buses that is still main's left and right — correct by accident, and `numChannels` becomes 12,
which is a number the mono fold-down logic was never written for. `MixBus.cpp:77` does the same.

## AC-6: The OUTPUT toggle drives the parameter, and the audio follows

```gherkin
Given the footer
When OUTPUT's MULTI-OUT segment is clicked
Then ids::output_mode moves, as ONE complete gesture, and the segment lights
And it is no longer read-only, no longer dimmed, and takes the pointing hand back
And the routing changes on the next block, without a click or a discontinuity
```

## AC-7: Nothing regressed, on all three compilers

```gherkin
Given the existing 2593 checks
When the suite is built and run under GCC, Clang and MSVC with DISPLAY unset
Then all of them still pass, the three cross-checks are green, the Windows VST3 still builds and
  installs, and no new warning appears
```

    Avoid: applying the character bus, limiter or master to a stem. Decided at planning — stems are
    pre-everything, and the arithmetic consequence is AC-2's.

    Avoid: a second pass over the voices to fill the stems. One pass writes both.
  </action>

## DO NOT CHANGE

- `PLANNING.md`, `uploads/UIUX.md` — specification, read-only
- `controls.js`, `forrobox.css`, `app.js`, `data.js` and the prototype — design reference, read-only
- `~/JUCE` — consumed read-only
- Parameter and group IDs in `src/ParameterIDs.h` — fixed. `ids::outputMode` already exists with the

- **The voices themselves.** Phase 3 is closed. This plan changes where a voice's output GOES, and
  not one sample of what it produces
- **`MixBus`'s chain.** It processes the main bus and nothing else. Stems do not enter it
- **The main bus's audio.** AC-3 is that it is sample-identical across modes; a change there is a
  regression, not a feature
- **`processBlock`'s allocation-free, lock-free contract** — Phase 1's, inherited by every phase

## SCOPE LIMITS

- **No per-channel output ROUTING choice.** `output_mode` is one global STEREO/MULTI switch, which is
  what the parameter declares and what the prototype's toggle shows. A per-channel "send this one to
  its own out" matrix is a different feature with a different UI and is not in any spec
- **No mono stem option.** `PLANNING.md:845` offers "5 stereo buses or 5 mono + master"; ROADMAP
  chose stereo, and the channels have PAN, which a mono bus would discard
- **No MIDI output changes** — Phase 7
- **No sequencer grid, playhead or hit visualisers** — Phase 5
- **No side panel or profile reload** — Phase 6
- **Do not add per-voice gain/pan smoothing.** PROJECT.md lists it as emerged-during-Phase-3 and
  unscoped; it would change the main bus's audio, which AC-3 forbids
- No new third-party dependencies. Nothing pushed to any remote
