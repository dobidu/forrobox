<objective>
## Goal
Fill the 196 px sequencer region with the five-row pad grid: row labels, 16 or 32 pads per row that
show the real pattern and edit it on click. And first, extract the attachment lifetime guard that is
currently hand-copied across five classes.

## Purpose
Phase 5's goal is that the sequencer is playable and legible. The grid is the half a user touches —
everything else in the phase (the playhead, the LEDs, the overlay) decorates a grid that has to exist
and has to edit the right thing first.

The refactor goes first because PROJECT.md says so: the guard is written out five times, each copy
re-explaining the use-after-free AddressSanitizer confirmed at 04-03, and the honest moment to fix
that is before a sixth. 04-05 opened the same way with the `HeaderBar` split `/simplify` had
mandated, and it worked.

## Output
`ScopedControlCallback`, and a `SequencerGrid` component that reads and writes the pattern the audio
thread actually plays.
</objective>

## AC-1: The lifetime guard exists once

```gherkin
Given the five attachment classes
Then each holds its control through ONE shared mechanism that nulls the control's callbacks when the
  attachment dies
And no attachment re-implements that teardown by hand
And the rendered chassis is pixel-identical to the committed tree, in both themes
And every existing check still passes, unchanged
```

**A refactor that changes a pixel or a check is not a refactor.** The proof is a comparison against a
build of the COMMITTED tree — `ui-renders/` is gitignored, which 04-05 learned by asserting otherwise
— and the comparison itself must be proved able to fail before it is believed. The instrument that
does that already exists in the scratchpad and is built on raw channel tuples, because
`ImageChops.difference(...).getbbox()` reads an all-zero alpha channel as an empty image.

## AC-2: Every box the sequencer needs is reserved, and the numbers are the stylesheet's

```gherkin
Given the 196 px sequencer region
Then the head row, each of the five rows, each row's label and each row's pad strip have a rectangle
And the stack tiles the region's interior exactly, with no leftover and no overlap
And every declared length is cross-checked against forrobox.css by verify-geometry.py
And a mutation to any one of them fails the build naming the constant
```

**The whole stack is reserved here even though this plan fills only part of it.** 04-01 computed the
strip's content rect and discarded it, which made its own "reserve their boxes" deliverable
unreachable by the plans that needed it; 04-02 paid to redo it. 05-02's playhead and LEDs and 05-03's
overlay drop into settled geometry or they re-flow the grid.

## AC-3: A pad shows the velocity that is actually stored

```gherkin
Given a pattern with velocities across the full range
Then each pad's lit state and opacity follow that lane's stored velocity
And a velocity at or below the ghost threshold draws as a ghost
And the BATERIA row shows the MAXIMUM of its four sub-lanes, because four lanes collapse into one row
And a 16-step window shows 16 pads and a 32-step window shows 32, from the SAME stored 32 slots
```

## AC-4: Clicking a pad edits the pattern the audio thread plays

```gherkin
Given the grid
When a pad is clicked
Then that lane's stored velocity toggles between 0 and 100
And the BATERIA row writes CAIXA, not all four sub-lanes — the collapsed row edits the backbeat
And the change reaches the audio thread through the existing lock-free handover
And it survives a save/reload round trip
And the plugin's `dirty` flag is set, because the pattern no longer matches its profile
```

**`togglePad` writing caixa is not an implementation detail to be tidied.** `app.js:389` records the
reason in its own comment — the collapsed row edits the backbeat and the deep edits live in the kit
view, which is 05-03's overlay. Writing all four lanes would make one click destroy a pattern.

## AC-5: The grid is driven through real mouse events, and nothing waits on a clock

```gherkin
Given every interaction check
Then each is driven through juce::MouseEvent on the component under test
And any refresh a test needs is CALLED, never waited for
And `runDispatchLoopUntil` with a timer-sized argument appears nowhere
```

    `/simplify` named it `ScopedControlCallback` at 04-06 and named what it owns: the

    What it must NOT absorb is the VALUE law. `/simplify` re-judged the five classes twice and both
    times declined to merge them: the read map, the write map and the callback signature all differ,

    five are `ProportionAttachment` (a template), `ToggleAttachment`, `ChoiceAttachment`,
    `BpmAttachment` and `KnobAttachment` — and `KnobAttachment` holds a `ProportionAttachment` rather
    than duplicating it, so it may need less than the others.

    **Prove it is a move.** Build the committed tree in a throwaway directory, run its suite to
    produce the before renders, and compare pixel for pixel in both themes at all three scales. And
    prove the COMPARISON first, by mutating one pixel by one unit and confirming it is reported.

    Avoid: changing any attachment's value mapping, gesture shape, or when it fires. Avoid touching
    the controls themselves. Avoid a base class — the teardown is a MEMBER, not an inheritance.
  </action>

  <action>
    Five rows of `StepPad`, which 04-03 built and which already carries velocity-as-opacity, the ghost

    `static_cast<theme::Accent>(channelIndex)` the strips use — the cast `Chassis.h`'s static_assert

    **Reading.** A pad shows its lane's stored velocity. The BATERIA row shows `max(bb, cx, hh, tom)`
    — `app.js:365-371` — because four lanes collapse into one row. Read through the state handle;

    up with after getting it wrong.

    **Writing.** A click toggles between 0 and 100 (`app.js:387-397`). The BATERIA row writes CAIXA

    invariant PROJECT.md records as "every writer must remember is the invariant that fails". Setting
    `dirty` belongs here too: an edited pattern no longer matches its profile.

    16-step window shows slots 0-15; the tiling rule `new[i] = old[i % oldLen]` is 02-01's and is not
    re-implemented here.

    Avoid: writing the grid from the audio thread or reading parameters on it — this is all message
    thread. Avoid a per-pad Timer. Avoid rebuilding every pad on every repaint; the pads are children
    and JUCE repaints what is dirty.
