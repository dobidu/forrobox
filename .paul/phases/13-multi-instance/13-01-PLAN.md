<objective>
## Goal
`Settings` stops constructing a `juce::PropertiesFile`. Every access did that, and each one was a
`juce::Timer` holding a `SharedResourcePointer<TimerThread>`. When no other timer was alive, the
access spawned and joined the timer thread, about 14 times per gear click, including in the
processor's constructor during a headless scan.

The store becomes plain file I/O on the SAME format:
- `<PROPERTIES><VALUE name="…" val="…"/></PROPERTIES>`, read with `juce::XmlDocument`;
- written atomically through `XmlElement::writeTo (File)`, which goes via a `TemporaryFile`.

So:
- every existing user's settings file still loads;
- a write still re-reads the file first and keeps every key it did not change. That is the
  cross-process property the header argues for.

`Settings::Snapshot`: one parse, all five values, the same typed readers. `SettingsMenu::build` and
`settings::applyTo` read one snapshot each, instead of 5 and 4 parses.

## Purpose
- **ROADMAP Phase 13:** "`PropertiesFile`-per-open spawns and joins `TimerThread` ~14 times per gear
  click — replace the store or own it".
- **The user's decision at Phase 13 planning:** XmlDocument file I/O, over a `SharedResourcePointer`
  store. It keeps the re-read-before-write property and holds no long-lived object that could
  outlive `shutdownJuce_GUI()`.
- This is the foundation 13-02's broadcast is written against: `set` gains a notification, and a
  listener re-reads one snapshot.

## Output
- `Settings` with no `PropertiesFile`, plus `Snapshot`.
- The menu and `applyTo` each read the store once.
- Tests that pin the format to JUCE's own `PropertiesFile`, in both directions.
</objective>

## Measured at planning (2026-10-02)
- Both paths use XML: `Options::storageFormat` defaults to `storeAsXML` (`juce_PropertiesFile.cpp:55`),
  and the test override sets it explicitly. JUCE's load tries binary first, but this store has never
  written binary.
- The tags are `PROPERTIES`, `VALUE`, `name` and `val`. A value that parses as XML is stored as a
  child element; this store only writes integers.
- The file location comes from `defaultOptions().getDefaultFile()`. That is kept as the PATH
  resolver only: `Options` is a plain struct, not a `Timer`.
- The `Settings::shared()` callers outside the store: the editor (`applyTo`), the chassis menu
  (`build`, `apply`, `applyTo`) and the processor constructor (`defaultStepChoiceIndex`).

  <name>Task 1: The store as plain file I/O, plus Snapshot</name>
  <files>src/Settings.h, src/Settings.cpp, src/SettingsMenu.cpp</files>
  <action>
    - Replace `open()` with private helpers:
      - `readValues() const`: parse `target()` with `juce::XmlDocument::parse (File)`. Require the
        root `hasTagName ("PROPERTIES")`. Collect `VALUE` children whose `name` is non-empty into a
        `juce::StringPairArray`, or into a small map of key → raw string. Anything missing or
        damaged gives an empty set, so every key falls back to its default.
      - `writeValues (…)`: rebuild the `PROPERTIES` element. Keep every key that was read,
        including unknown ones, and change only the one being set. `createDirectory()` the parent,
        then `XmlElement::writeTo (target(), {})`, which is atomic via `TemporaryFile`.
      - `target()`: the override, or `defaultOptions().getDefaultFile()`.
      - Name the tag and attribute constants once, with a comment that they are JUCE's
        `PropertyFileConstants`. JUCE keeps those private, so the tags are copied, and the
        format-compatibility test is what pins the copy.
    - `get` = one key out of `readValues()`, through the SAME strict-integer parse, 64-bit clamp and
      default-on-damage logic. Keep those comments. `set` = read, change one key, write.
    - `struct Snapshot`: built by `Settings::snapshot() const`, holding one parse's raw ints for all
      five settings. It carries the typed readers (`themeMode`, `monoFamily`, `cornerRadiusPx`,
      `accentIntensity`, `defaultStepChoiceIndex`, `defaultStepCount`). The store's own typed
      readers delegate to a one-key `get`, so their callers are unchanged.
    - `SettingsMenu::build` and `settings::applyTo` take `const Settings&` as today, and take ONE
      `snapshot()` internally. Keep `build`'s "each setting read once" comment, updated to
      "one read".
    - A test seam for AC-4: a `parseCount()` that counts reads. Make it static or per-instance,
      whichever is smaller, and document it as test-only. Or an equivalent seam that costs nothing
      in production.
    - Rewrite the HOLDS NO OPEN FILE comment to what is now true. It still holds nothing open. The
      reason is no longer only the Timer: there is no `Timer` and no thread at all, which closes the
      08-02 deferred entry.
    - Avoid:
      - an in-memory cache, which would lose the cross-process re-read and is 13-02's question if
        anyone's;
      - binary-format support, which this store has never written;
      - changing `defaultOptions()` or the path rule.
  </action>
