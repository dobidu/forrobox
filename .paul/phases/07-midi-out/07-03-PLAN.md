<objective>
## Goal

The groove drives other instruments. Every hit the plugin plays — swung, jittered, velocity-varied,
ghosts included — also leaves as a MIDI note on the plugin's output bus, sample-accurately, with no
allocation and no lock on the audio thread. The note-off gate is a new global choice parameter:
a fixed 40 ms, or 80% of a step.

## Purpose

`PROJECT.md` lists live MIDI out as a Core Feature and the plugin has declared
`NEEDS_MIDI_OUTPUT TRUE` since Phase 1, while `processBlock` opens with `midi.clear()` and writes
nothing back. This is the last inert declaration in the plugin.

It is also the phase's ONLY audio-thread change, which is why Phase 7 was split three ways at
planning. Its failures are a different species from 07-01's wrong bytes and 07-02's OS integration:
a note stranded across a block boundary, an allocation in `processBlock`, a hung note when the
transport stops.

**It emits the PERFORMANCE, not the grid** — decided with the user at Phase 7 planning and recorded
in ROADMAP. The file export is deliberately un-humanised; live MIDI reusing that would drift against
the plugin's own audio the moment swing or `CACHAÇA` is non-zero, so a doubled instrument would play
out of time with the groove it is doubling.

## Output

- `src/GmPercussion.h` — the GM map, hoisted so two callers share one table
- A fixed-capacity, allocation-free pending-MIDI queue on `VoiceEngine`, drained per block
- `ids::midiGate` — a 46th parameter, two modes
- Checks for the properties that only fail at a block boundary
</objective>

<acceptance_criteria>

## AC-1: Every audible hit leaves as a MIDI note, at the sample it sounds

```gherkin
Given the transport running with a profile loaded
When a block is processed
Then every voice the engine triggers in that block has a matching note-on in the MIDI buffer
And the note-on's sample offset equals the voice's own trigger offset
And the note number is the GM number for that lane
```

## AC-2: It is the PERFORMANCE — swing, jitter, velocity variation and ghosts all reach the output

```gherkin
Given CACHAÇA raised and swing non-zero
When the same step is played twice with different humanisation keys
Then the MIDI note offsets differ by the jitter, not by a fixed grid position
And ghost notes appear as MIDI notes, at their own offsets and velocities
And muting or soloing a channel changes the MIDI exactly as it changes the audio
```

## AC-3: A note scheduled past the end of a block is emitted in the block that contains it

```gherkin
Given the 32 ms lookahead is longer than the block
When a hit is scheduled beyond the current block's last sample
Then no MIDI is emitted for it in this block
And it is emitted in the later block whose sample range contains it, at the right offset within it
And nothing is lost, duplicated, or reordered across the boundary
```

## AC-4: The note-off gate is selectable, and neither mode can strand a note

```gherkin
Given the MIDI GATE parameter
When it is FIXED
Then every note-off follows its note-on by 40 ms
When it is STEP
Then every note-off follows its note-on by 80% of the current step
And in both modes, stopping the transport emits a note-off for everything still sounding
```

## AC-5: The audio thread allocates nothing and takes no lock

```gherkin
Given a block that triggers the densest profile with ghosts at maximum
When processBlock runs
Then the allocation counter does not move
And the pending queue never grows, never reallocates, and drops loudly rather than silently if full
```

    HOIST THE GM MAP. `laneNotes` lives in `MidiExport.cpp`'s anonymous namespace, reachable by
    nothing. This plan needs the same eight numbers, and a second table is exactly what
    `ids::channelInfos` forbids in its own comment — "one array of structs makes divergence
    impossible instead of detectable". Move it to `src/GmPercussion.h`, keeping the
    `static_assert` that pins its rows to `ids::lanes` in order, and have `MidiExport.cpp` include it.

    THE HOIST MUST BE PROVED INERT: `verify-midi.py` compares the exported bytes against the
    prototype across 24 states, so if the move changed a single number that gate fails. Run it before
    and after and say so.

    ADD `ids::midiGate`, a global CHOICE parameter, default FIXED. Its display strings come from a
    table in `ParameterIDs.h` built the way `stepWindows`, `timbreSpecs` and the output modes are —
    one array, one source, `midiGateChoices()` derived from it. Do NOT write the strings twice.

    THIS IS THE 46th PARAMETER, and the count is a deliberate tripwire:
    `tests/StateRoundTripTest.cpp` asserts 45 in four places and cross-checks a declared total. Those
    numbers move to 46 as a conscious act, not as a fix to make a build pass. Adding a parameter is
    safe for saved state — APVTS gives a missing parameter its default — whereas renaming one is not,
    which is why `ParameterIDs.h` says the existing IDs are fixed.

    NO UI. `PLANNING.md` specifies no MIDI-gate control and the design mandate forbids inventing one;
    hosts expose it in their generic panel, and Phase 8's settings menu can attach to it later. Say
    that where the parameter is declared, so the next reader does not think a control was forgotten.
  </action>

<task type="auto">
  <name>Task 2: The pending queue, and the seam that fills it</name>
  <files>src/VoiceEngine.h, src/VoiceEngine.cpp, src/PluginProcessor.cpp</files>
  <action>
    `VoiceEngine::playVelocity` is THE seam, and its own comment already says why: "the one place a
    normalised velocity becomes a voice, so ghost notes can reach it without round-tripping through
    the uint8 grid velocity". Every humanised hit and every ghost passes through it with
    `(lane, velocity, sampleOffset)` — which is precisely a MIDI note. Tapping anywhere else means
    re-deriving the humanisation or missing the ghosts.

    A FIXED-CAPACITY queue on the engine, sized at construction, never grown. `processBlock` is
    allocation-free and lock-free and that is a PROJECT.md constraint, not a preference.

    THE BLOCK BOUNDARY IS THE WHOLE PROBLEM. `scheduleStep` delays every trigger by
    `lookaheadSamples` — 32 ms, ~1536 samples at 48 kHz — and a host block is commonly 128 to 512.
    So a scheduled offset ROUTINELY lands past the end of the current block. Each queued event
    therefore carries an offset measured from the START of the block it was scheduled in, and the
    drain subtracts the block length from everything it does not emit, so what remains is relative to
    the next block. Getting this backwards produces MIDI that is correct at 1024 samples and wrong at
    128, which no single-buffer-size test would catch — so the checks sweep block sizes.

    DRAIN IN `processBlock`, into the `juce::MidiBuffer` it is already handed. Note that it currently
    opens with `midi.clear()`: incoming MIDI is discarded, which is what an instrument that generates
    its own notes does, and the clear must stay BEFORE the drain or this plan's own notes are wiped.

    IF THE QUEUE IS FULL, drop and COUNT, do not silently discard. Publish the count the way
    `atomicMax` publishes a running peak — `forrobox::atomicMax` is this project's one law for that —
    so a test can assert it stays zero under the densest profile and a future reader has a number
    rather than a suspicion.

    Velocity: the engine's is normalised float; MIDI wants 1..127. Clamp at 1 for the reason 07-01
    wrote down — a note-on with velocity 0 IS a note-off.
  </action>
  <verify>
    cmake --build build-linux --target ForroBoxTests -j8 && (unset DISPLAY; ./build-linux/ForroBoxTests)
    Assert the allocation counter does not move across a dense block, and that the counter can
    REGISTER a reading — a broken counter reports zero for everything, which looks like success.
    Then run `/code-review` on the diff.
  </verify>
  <done>AC-1, AC-3 and AC-5 satisfied</done>
</task>

<task type="auto">
  <name>Task 3: The two gates, the all-notes-off, and the checks that need a boundary</name>
  <files>src/VoiceEngine.h, src/VoiceEngine.cpp, src/PluginProcessor.cpp, tests/VoiceTest.cpp</files>
  <action>
    FIXED is 40 ms from the note-on, tempo-independent. STEP is 80% of the current step — the same
    fraction `exportMIDI` uses, so a live note and an exported note agree at a steady tempo. The step
    duration is not something `playVelocity` knows, so it arrives the way `cachaca` does: one field
    on the per-block `Settings`, normalised and guarded ONCE where the parameter enters. That struct's
    own comment records why — a value normalised at three use sites had a NaN guard at only one of
    them.

    NEITHER MODE MAY STRAND A NOTE. On `releaseResources`, on a transport stop, and on a sample-rate
    change, every note still sounding gets its note-off. A hung note in a downstream sampler is the
    failure mode here and it outlives the plugin's own block.

    CHECKS, in `tests/VoiceTest.cpp` where the engine's other audio-thread claims live:
    - The same step at CACHAÇA 0 and CACHAÇA 100 produces DIFFERENT note offsets — the humanisation
      reaches the MIDI. A check that only asserts "a note exists" passes against a writer that
      ignores jitter entirely.
    - Ghost notes appear. Drive GHOST to 100 with a SILENT step and assert notes appear that the
      pattern does not contain.
    - Muting a channel removes its MIDI; soloing another removes everyone else's — live MIDI follows
      `audible`, which is mute AND solo, and is deliberately DIFFERENT from the file export's
      mute-only rule. Say so in the message: two rules, two reasons, and 07-01's `ChannelGate`
      header already explains the export's.
    - The boundary: sweep block sizes 32, 64, 128, 512 and 1024 over the same musical span and assert
      the total note sequence is IDENTICAL — same notes, same absolute sample positions. This is the
      check that catches an offset rebased the wrong way, and it cannot be written for one size.
    - Every note-on has a note-off, in both modes, and none survives a stop.

    Every check proved able to fail: mutate the jitter out of the queued offset, mutate the ghost
    path, mutate the boundary subtraction, and mutate one gate mode into the other.
  </action>

<boundaries>

## DO NOT CHANGE

- `src/MidiExport.h` / `.cpp` beyond including the hoisted GM header. The file writer is cross-checked
  byte for byte on every build; this plan must leave those bytes identical, and `verify-midi.py` is
  the proof.
- `src/GrooveExport.*` and `src/DragMidiButton.*` — 07-02's drag path. Live MIDI shares no code with
  it and no file with it.
- The existing 45 parameter IDs in `src/ParameterIDs.h`. Renaming one invalidates saved host state.
  ADDING `midi_gate` is the change; nothing else moves.
- The humanisation itself — the keyed-hash scheme, the jitter, the ghost rule, the lookahead. This
  plan READS the performance at the seam where it already exists; it must not re-derive or alter it.

## SCOPE LIMITS

- No MIDI control of the plugin FROM the host — `wantsMidiInput` stays as it is, and `midi.clear()`
  keeps discarding incoming events. Playing the grid from a keyboard is not in any phase's scope.
- No UI for the gate parameter. The design mandate forbids inventing a control the prototype does
  not specify; Phase 8's settings menu is where one would go.
- No MIDI clock, no MTC, no program change. The bus carries notes.
- No change to the reported latency. The 32 ms is `CACHAÇA`'s and is already correct; MIDI is emitted
  at the same sample offsets as the audio, so the two share one timebase.

</boundaries>
