<objective>
## Goal
Make the sequencer grid respond to every writer of the pattern, not only to its own clicks; and fill
the `STEPS` 16/32 buttons 05-01 reserved, with the tiling law `PLANNING.md:606-607` fixes.

## Purpose
05-01 built a grid that edits the pattern. `/code-review` then found it has **no writer but itself**:
`refreshFromState` runs on attach and after `toggleCell`, and nothing else. Two other writers exist
and neither reaches it — a host recalling a project replaces the lanes wholesale
(`PluginProcessor.cpp:1007`) while the editor keeps showing the previous pattern, and `ids::steps` is
host-automatable and read live by `processBlock` while `rebuildPads` snapshots it once, so a STEPS
automation to 32 leaves steps 16-31 invisible and uneditable behind a clock already playing them.

Both are the same gap seen from two sides, and Phase 6 makes it acute: profile loading is a wholesale
state replacement whose entire point is that the UI shows the result.

The `STEPS` buttons are the other half. No plan had ever claimed them — 05-01 reserved their boxes,
the ROADMAP names `steps` only as a Phase 1 parameter, and they have sat visibly empty since.

## Output
- A state generation on the processor, bumped where every writer already publishes
- `SequencerGrid` refreshing and rebuilding from it
- The `STEPS` 16/32 buttons, wired to `ids::steps`
- Processor-owned tiling, so automation and a click produce the same groove
</objective>

<acceptance_criteria>

## AC-1: The grid shows what the pattern IS, whoever wrote it

```gherkin
Given the editor is open
When any writer changes the pattern — a host recall, a preset, a profile load, the grid's own click
Then the pads show the new pattern without the user touching anything
And the mechanism is the one every writer already passes through, not a call each writer must remember
```

**"Every writer must remember" is the invariant that fails**, and this project has already been
bitten by it: 01-02's two state methods both bypassed the publish, which is why `LockedState`
publishes from its destructor. The refresh must hang off that same seam, so Phase 6's profile load
needs no new call.

## AC-2: A step-count change rebuilds the grid, from any source

```gherkin
Given a 16-step window
When `ids::steps` changes to 32 — from the buttons OR from host automation
Then the grid shows 32 pads, all editable, over the same 32 stored slots
And switching back shows 16
And nothing waits on a timer for this to happen
```

## AC-3: Switching to 32 TILES the pattern, and does so with the editor closed

```gherkin
Given a pattern edited inside a 16-step window
When the step count becomes 32
Then slots 16-31 become a copy of slots 0-15, so the edited bar repeats — `PLANNING.md:606`
And that happens whether the change came from a click or from host automation
And it happens whether or not an editor is open
```

**The tiling is the PROCESSOR's, decided with the user at planning.** The prototype has one path
(`setSteps`, `app.js:581`); a plugin has two, and a UI-owned tiling would make the same automation
produce a different groove depending on whether a window happened to be open. The APVTS listener can
fire on the audio thread, so the write goes through an `AsyncUpdater` — the hop is required, not
stylistic.

**Switching to 16 tiles nothing, and that is not an omission.** The prototype truncates its array;
our storage is always 32 slots with `steps` as a view (02-01's decision, recorded in
`expandPattern`'s own doc). Slots 16-31 simply stop being read — and because a later switch to 32
tiles over them, nothing that survives is ever observable. Truncating would destroy work for no
reachable benefit.

## AC-4: The STEPS buttons are the prototype's, and show which window is active

```gherkin
Given the sequencer's head row
Then `16` and `32` sit in the boxes 05-01 reserved, in the `.btn` treatment with `.on` for the
  active one
And clicking one sets `ids::steps` as one complete gesture
And the lit one follows the PARAMETER, so host automation moves it too
And every declared length is cross-checked against forrobox.css
```

**A read-only control still needs the display half** — this project's own recorded decision, found
twice in one plan at 04-04. The buttons must light from the parameter, not from the click.

<task type="auto">
  <name>Task 1: One state generation, and a grid that follows it</name>
  <files>src/PluginProcessor.h, src/SequencerGrid.h, src/SequencerGrid.cpp, tests/UiTest.cpp</files>
  <action>
    Give the processor a monotonic `stateGeneration`, bumped in `~LockedState` beside the
    `publishIfChanged` that is already there. That is the one seam every writer passes through —
    `toggleCell`, `setStateInformation`, `getStateInformation`'s copy, and Phase 6's profile load —
    so no writer has to remember anything, which is the invariant 01-02 proved cannot be maintained
    by convention.

    Bump it unconditionally rather than only when the lanes changed. `publishIfChanged` compares
    lanes alone, and this generation must also cover `activeProfile`, `dirty` and the pattern slots,
    which the grid's neighbours will read in 05-04 and Phase 6.

    Have `SequencerGrid` poll it — the grid already owns a 60 Hz `PollTimer` for the playhead, so
    this is a second edge-detect on the same tick, not a second timer. On a change, call
    `refreshFromState()`.

    Also poll the STEP COUNT, read from `ids::steps` the way `rebuildPads` reads it once today. On a
    change, `rebuildPads()` then `resized()` then `refreshFromState()` — `/graphify` found the
    prototype's `setSteps` calls `renderPads()` for the same reason: the pad COUNT changes, so a
    velocity refresh alone would leave 16 pads showing a 32-step window.

    Avoid: a second timer. Avoid: a `juce::ChangeBroadcaster` — the grid already polls, and a
    broadcaster would give this one signal a different delivery mechanism from the playhead and the
    visualisers beside it.

    Avoid: making `toggleCell` skip its own refresh. It bumps the generation like every other writer,
    so the poll will refresh again a frame later; `StepPad::setVelocity` early-outs on no change, so
    the duplicate costs 160 integer compares and no repaint. Suppressing it would mean the grid
    knowing which writes are "its own", which is the coupling this seam exists to remove.
  </action>
  <verify>
    Drive the processor directly, never a timer: write the lanes through `lockPatternState()`, call
    the grid's poll, and assert the pads followed. Do the same through `setStateInformation` with a
    blob carrying a different pattern — the host-recall path, which is the one `/code-review` named.
    Set `ids::steps` and assert the pad count changed and the new pads are editable.
    `runDispatchLoopUntil` with a timer-sized argument appears nowhere.
    Negative control: a poll that ignores the generation must fail the recall test.
  </verify>
  <done>AC-1 and AC-2 satisfied.</done>
</task>
