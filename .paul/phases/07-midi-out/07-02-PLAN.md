<objective>
## Goal

The DRAG MIDI button stops lying. Dragging it hands the host a real `.mid` file of the current
groove; clicking it opens an async save dialog for the same bytes; and the 2.6 s idle pulse and
bobbing arrow deferred here from 04-05 finally run, because there is now something behind them.

## Purpose

`PLANNING.md:492-506` calls this "the footer's primary call to action", and it is the last stub in
the chassis. 04-05 deferred its animation with a reason recorded in `DragMidiButton.h` — *"an
animated call to action for a control that does nothing is the loudest possible lie"* — and 07-01
removed the condition that reason depended on.

This is the OS-integration half of Phase 7, split from the byte format at phase planning by the
02-03 / 04-04 / 05-02 test. Its failures are a different species from 07-01's: a file that vanishes
under a lazy reader, a modal loop inside a plugin, a `FileChooser` destroyed before its callback
fires. None of those are byte errors and none would be caught by the cross-check.

## Output

- `src/GrooveExport.h` / `.cpp` — the current groove's bytes AND its filename, gathered from the
  processor in one place
- Drag-out and an async save dialog on `DragMidiButton`
- The idle pulse and the bobbing arrow
- Suite checks for the two rules that are easy to get wrong and invisible when wrong
</objective>

## AC-1: The groove leaves the plugin as a file a DAW accepts

```gherkin
Given a profile loaded and the editor open
When DRAG MIDI is dragged onto a DAW's arrangement
Then a MIDI clip appears carrying the pattern, at the plugin's current BPM
And the file is named `forrobox_<profile>_<bpm>bpm.mid`
```

## AC-2: The export reads MUTE, and solo does not reach it

```gherkin
Given one channel muted and a DIFFERENT channel soloed
When the file is exported
Then the muted channel is absent
And every other channel is present — soloing does not silence the rest of the file
```

## AC-3: The dragged file outlives the drag, and does not accumulate without bound

```gherkin
Given several drags in one session
When each drop completes
Then the file each one handed the OS still exists at the moment the OS reads it

```

```gherkin
Given the editor open inside a host
When DRAG MIDI is clicked
Then a save dialog opens WITHOUT blocking the message thread
And the file it writes is byte-identical to what a drag would have handed over
And dismissing it writes nothing
```

<task type="auto">
  <name>Task 1: The current groove, as bytes and a filename</name>
  <files>src/GrooveExport.h, src/GrooveExport.cpp, CMakeLists.txt, tests/MidiExportTest.cpp</files>
  <action>
    One place that answers "what would we export right now", so the drag and the dialog cannot
    disagree:

        struct GrooveExport
        {
            std::vector<std::uint8_t> bytes;
            juce::String filename;
        };

        GrooveExport renderCurrentGroove (ForroBoxAudioProcessor&);

    Its own file, NOT `MidiExport.h`: that header is a pure function of its arguments — 03-02's law
    for the clock, and what lets `verify-midi.py` sweep it offline with no processor. Including
    `PluginProcessor.h` there would end that. This is the adapter between the two.

    It gathers:
    - the pattern and `activeProfile` through `lockPatternState()`,
    - `bpm` from `ids::bpm`,
    - the step window from `currentStepWindow()`, which already exists,
    - and the mute gate.

    THE MUTE GATE IS THE TRAP. `ChannelGate` is MUTE-ONLY and its header says so in as many words:
    `exportMIDI` reads `chans[id].mute` and never looks at solo. A caller holding
    `resolveChannelSettings()` will reach for `! settings.channels[c].audible`, which folds SOLO in
    and would silence every unsoloed channel in the file. Read the per-channel `ids::mute` parameter
    directly.

    THE FILENAME IS `forrobox_<profile>_<bpm>bpm.mid`, from `app.js:454`. Two things that look like
    omissions and are not:
    - The prototype writes `state.activeProfile || "custom"`, and that fallback is UNREACHABLE here.
      `State::activeProfile` defaults to `"campina"` and only ever holds one of the four ids. Do not
      port the `|| "custom"` branch as dead code.
    - The DIRTY flag does NOT change the filename. `markCustom()` (`app.js`) sets `dirty` and never
      clears `activeProfile`, so an edited campina still exports as `forrobox_campina_<bpm>bpm.mid`.
      Using `dirty` to write "custom" would be inventing behaviour the design source does not have.

    Assert the profile id is filename-safe rather than assuming it: the four ids are ASCII lowercase
    today, and a `static_assert` or a check costs nothing and documents why no sanitiser is needed.

    Add `src/GrooveExport.cpp` to the `ForroBox` source list.

    Checks in `tests/MidiExportTest.cpp`, both of which are invisible when wrong:
    - AC-2's: mute one channel, SOLO a different one, export, and assert every unsoloed channel is
      still present. Then mutate `renderCurrentGroove` to use `audible` and confirm it fails.
    - The filename at two BPMs and two profiles, plus one with `dirty` set, asserting the name does
      NOT change.
  </action>
  <verify>
    cmake --build build-linux --target ForroBoxTests -j8 && (unset DISPLAY; ./build-linux/ForroBoxTests)
    MUTATE the gate to `! audible`, assert the edit landed, confirm the solo check fails. Revert.
    MUTATE the filename to use `dirty`, assert it landed, confirm the name check fails. Revert.
  </verify>
  <done>AC-2 satisfied; AC-1's filename half satisfied</done>
</task>

<task type="auto">
  <name>Task 2: The drag, the dialog, and the temp file</name>
  <files>src/DragMidiButton.h, src/DragMidiButton.cpp, src/FooterBar.cpp, src/PluginEditor.cpp</files>
  <action>
    Give `DragMidiButton` a `std::function<GrooveExport()>` the footer supplies, so the button knows
    how to ask and nothing about the processor.

    THE DRAG, from `mouseDrag` and not `mouseDown`. `performExternalDragDropOfFiles` is STATIC — no
    `DragAndDropContainer` instance is needed, and the editor does not become one. Pass `this` as
    `sourceComponent` and `canMoveFiles = false`: the receiver must copy, because the file is ours.

    THE TEMP FILE, decided with the user at planning: write into a `forrobox` subfolder of
    `File::getSpecialLocation (tempDirectory)`, and NEVER delete it inside the drag. Sweep previously
    written exports on the NEXT export and once on construction.

    The rejected alternative is worth stating where the code is, because it is the obvious one:
    deleting in the completion callback looks tidiest, but that callback fires when the DRAG ends,
    which is not the same instant the receiving application has finished reading. A host that copies
    lazily would get a file that vanished underneath it, and the failure mode is a silently empty
    MIDI track — no error anywhere.

    THE CLICK opens `juce::FileChooser::launchAsync`, with the same filename pre-filled, writing the
    same bytes.

    TWO WAYS THIS GOES WRONG, both silent:
    - NEVER a modal `browseForFileToSave`. `JUCE_MODAL_LOOPS_PERMITTED=1` is set on the TEST target
      ONLY and deliberately — `CMakeLists.txt` says so beside it: "modal loops in a plugin are
      exactly what the default forbids". A modal call here compiles and deadlocks a host.
    - The `FileChooser` MUST outlive its callback. A stack one destroyed at the end of `mouseUp` is
      a use-after-free that usually appears to work. Hold it as a member.

    Guard the click so a drag does not also fire it — a drag is a press, a move and a release, and
    `mouseUp` cannot tell the difference without knowing whether a drag started.
  </action>
  <verify>
    cmake --build build-linux --target ForroBoxTests -j8 && (unset DISPLAY; ./build-linux/ForroBoxTests)
    Grep the diff for `browseForFileToSave` and any modal variant — there must be none.
    Confirm the sweep by writing two exports in a test and asserting the older one is gone.
    Then run `/code-review` on the diff.
  </verify>
  <done>AC-3 and AC-4 satisfied; AC-1 ready for the checkpoint</done>

<task type="auto">
  <name>Task 3: The idle pulse and the bobbing arrow</name>
  <files>src/DragMidiButton.h, src/DragMidiButton.cpp, tests/MidiExportTest.cpp</files>
  <action>
    `PLANNING.md:499-500`: a 2.6 s ease-in-out loop breathing the glow between `0 0 0 1px <zabumba
    18%>` and `+ 0 0 20px <zabumba 28%>`, with the `↓` arrow bobbing 2 px on the SAME cycle. On
    hover or drag-active the animation stops and the border goes solid — the states
    `DragMidiButton.h` already has constants for.

    THE COMPONENT OWNS ITS OWN TICK AND IS TOLD ITS ELAPSED TIME. This is a recorded Key Decision,
    not a preference: `advancePulse (double seconds)` never reads a clock, and a `PollTimer` member
    reads one and calls it. Three 04-04 checks failed on MSVC's clock rather than on the code, and
    `KitOverlay`'s animation living in its parent cost `Chassis` a member meaning "when another
    component's animation last ticked". `Surface.h`'s `PollTimer::secondsSinceLastTick` and its
    clamped sibling already exist — use them rather than writing the eight lines a third time.

    STOP THE TIMER WHEN IT IS NOT PULSING. `KitOverlay`'s entrance poll is started on open and
    stopped on close so a shut panel does no work; a permanently running 30 Hz timer for a button
    nobody is looking at is the cost that comment exists to avoid.

    Checks: drive `advancePulse` to 0, a quarter, a half and a full cycle and assert the glow radius
    and the arrow offset at each — a pure function of phase, with no clock and no waiting. Assert
    the phase does NOT advance while hovered. Then mutate the cycle length and confirm the checks
    fail.
  </action>

<boundaries>

## DO NOT CHANGE

- `src/MidiExport.h` / `.cpp`. 07-01's writer is cross-checked byte for byte against the prototype on
  every build; this plan CALLS it and must not reshape it. A filename or a temp path has no business
  in a function whose whole value is being a pure function of its arguments.
- `scripts/verify-midi.py`, `scripts/verify-midi.js`, `tests/EmitMidi.cpp`. The fifth gate stays as
  it is; nothing here changes the bytes.
- `processBlock` and everything it calls. This plan adds no audio-thread code — live MIDI is 07-03.
- `PLANNING.md`, `audio.js`, `app.js`, `forrobox.css`, `data.js`, `controls.js` — read-only. A
  mismatch is never fixed by editing the reference.
- Parameter and group IDs in `src/ParameterIDs.h`.

## SCOPE LIMITS

- No live MIDI out. 07-03, and it emits the HUMANISED performance — swing, `CACHAÇA` jitter and
  ghosts — which is a different data path and an audio-thread change.
- The export stays the STORED GRID, un-humanised. That is 07-01's decision and the prototype's.
- No new third-party dependency. `juce::FileChooser` and `DragAndDropContainer` are both in JUCE.
- Do not make the editor a `DragAndDropContainer`. `performExternalDragDropOfFiles` is static; an
  instance would be machinery with no caller.
- No settings for the export folder, no format options, no "export selection". Phase 8 at the
  earliest, and not asked for.

</boundaries>
