<objective>
## Goal
**The `.forrogroove` file (18-01) becomes a sharing format.**

**The format, documented** (`docs/groove-format.md`):
- The XML shape (root `ForroBoxGroove`, `version`, `id`, `name`, `bpm`, `swing`, `cachaca`, eight
  `<lane id steps>`), each field's range and meaning, an example, and the reading rules (strict:
  any wrong field refuses the whole file; feel clamped).
- **Versioning:** `version="1"`. A reader refuses a version it does not know rather than
  guessing; a future change that old readers could not play bumps the version. Unknown extra
  attributes stay a refusal in v1 (strict now, so loosening later is the safe direction).
- The duplicate rules below, so a sender knows what the receiver will see.

**Export** (user decision: one groove at a time):
- `processor.grooveForExport()` → the PLAYING groove as heard (`captureUserGroove`, so a 16-step
  window tiles as a save does), named by the screen's name (`activeGrooveName`, or "Groove" when
  it has none).
- **Its id:** the user groove's own id when the state is a pristine user groove — so a recipient
  importing it twice, or the sender re-importing it, gets "identical"; otherwise a fresh UUID (a
  regional or edited groove is a new groove).
- `exportGroove (File)` writes it atomically (18-01's `.partial` path). The suggested file name is
  the groove's name made filesystem-safe, plus `.forrogroove`.

**Import** (user decisions: many files at once; same id + same content → ignored, same id +
different content → a new copy, nothing of the user's overwritten):
- `UserGrooveLibrary::importFile (File) → ImportOutcome { added | identical | copied | refused,
  id, reason }`.
- **The file's own id is used**, not its file name (a shared file may be renamed "baiao.forrogroove");
  the library writes it under `<id>.forrogroove` as always.
- **Duplicate:** `identical` when id and content match a library groove; `copied` — a fresh id and
  the name with " (2)" (" (3)"… if taken, trimmed to fit 24 characters) — when the id matches but
  the content differs.
- `processor.importGrooves (Array<File>) → summary { added, identical, copied, refused + reasons }`;
  one rescan and one notification per import batch, not per file.

**Hostile and foreign files, refused safely** (ROADMAP: "as the settings store and
`setStateInformation` already are"):
- **Size cap before parsing:** a groove file is ~2 KB; anything over 64 KB is refused unread — at
  import AND at every library scan (18-01 parses whatever sits in the folder).
- Not a regular file (a directory, a missing path), empty, binary, not UTF-8 XML, another root,
  version 2, a DOCTYPE with entities: refused with a reason. JUCE's `XmlDocument` expands no
  external entities; a test proves a DOCTYPE "billion laughs" file is refused or harmless.
- Every 18-01 strict rule still applies (lanes, steps, values, name).

`processBlock` untouched: all message thread.

<acceptance_criteria>

## AC-1: Export and import round-trip
```gherkin
Given a pristine user groove, and separately an edited regional groove at 16 steps
When each is exported and imported into an EMPTY library
Then the imported grooves equal what was playing (lanes tiled as heard, feel, name), the user groove keeps its id, the regional one has a fresh id
And the exported file is valid per docs/groove-format.md (the doc's example parses with the real reader)
```

## AC-2: The duplicate rules
```gherkin
Given a library holding groove X
When X's own file is imported, and then a file with X's id but different lanes
Then the first is "identical" and changes nothing; the second is "copied": a new id, the name "X (2)", X untouched
And a third such file becomes "X (3)", and a 24-character name is trimmed so " (2)" fits
And a batch of files reports each outcome and rescans and notifies once
```

## AC-3: Hostile, damaged and foreign files are refused safely
```gherkin
Given files that are: over 64 KB; empty; random bytes; a PNG; a .forrogroove that is a directory; a missing path; UTF-16 text; another XML root; version 2; a DOCTYPE entity bomb; each 18-01 strict-rule violation
When each is imported, and when each sits in the library folder during a scan
Then each is refused with a reason, nothing is written, the library is unchanged, and valid neighbours still load
And no case takes longer than a second or allocates in proportion to a declared size
```

## AC-4: Nothing else moves
```gherkin
Given the suite
When it runs with this plan's tests
Then every existing check passes, processBlock is untouched, and 18's library behaviour is unchanged for valid files
```
