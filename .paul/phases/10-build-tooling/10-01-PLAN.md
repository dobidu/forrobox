<objective>
## Goal
`ForroBoxTests.exe` exits on its own, promptly, with its real exit code, after it prints its
summary. `scripts/build-windows.sh` goes back to judging the suite by that exit code rather than by a
line read from a process it had to kill.

## Purpose
Every MSVC run since 09-06 has cost ~15 minutes of dead wait, and for a day it made `--install`
unreachable. The workaround at `b55135e` — kill after 900 s and trust the printed line — breaks a
standing project law, *"read the real exit code, never a wrapper's"*, in the one place that law was
written for. It also turns every later plan's MSVC verification into a quarter-hour tax, so Phase 10
goes first in v0.2 and this plan goes first in Phase 10.

## Output
- A **measured** cause: which exit stage blocks, and on what. Not a hypothesis.
- A cure, chosen by the user at a checkpoint once the cause is known.
- `run_tests()` judging by exit status again, with the timeout kept as a short safety net that
  counts as a FAILURE rather than a pass.
- `09-06`'s, `b55135e`'s and the Deferred Issues' accounts of the hang corrected to what was measured.
</objective>

## What is already known — measured at planning, 2026-09-25
- **The hang began at 09-06 (`982a758`).** Every SUMMARY through 09-05 records MSVC with a real exit
  0 read without a pipeline (09-05: 4824 / 4824). 09-07's SUMMARY is the first to say "read from the
  build log, because the process hangs after printing (09-06's finding)". So the window is ONE
  commit, `353eabd..982a758`.
- **That commit adds no thread, timer, singleton, `SharedResourcePointer`, `callAsync` or file
  chooser** anywhere in `src/` or `tests/` — grepped at planning. Reading the diff will not find it;
  measuring will.
- **The summary prints BEFORE the hang can start.** `fbtest::reportSummary()` runs inside `main`,
  and then `main`'s locals are destroyed in reverse order: `isolatedSettings`
  (`Settings::ScopedTestFile`), `removeSettingsFile`, `keepTimersAlive` (`stopTimer`), then
  `juceInit` (`shutdownJuce_GUI`). After those: CRT static destructors, then DLL detach. Three
  stages, and a marker between each localises the hang.
- **The process is BLOCKED, not spinning**: 0% CPU, state S, 233 KB working set, for 17 minutes
  (Deferred Issues, measured at the v0.1 tag).
- **The 08-02 pipe hang is a DIFFERENT bug** and stays fixed: output goes to a file, not a pipe,
  and it still hangs. Two bugs wore one symptom once already (see the Deferred Issues entry); this
  plan must not let that happen a second time.
- **The Linux binaries exit cleanly** (GCC and Clang, exit 0 at 2026-09-25).
- **No Windows debugger is installed** — no `cdb.exe`, no Debugging Tools, no procdump. The binary
  already imports `dbghelp.dll` (via JUCE), so an in-process probe can walk stacks.

<task type="auto">
  <name>Task 1: Exit-stage markers and a live-thread probe — measure where it blocks</name>
  <files>tests/TestMain.cpp, tests/ExitProbe.h (new, test target only)</files>
  <action>
    Add a TEST-ONLY probe that runs only when it is asked for (`--exit-probe` on the command line or
    `FORROBOX_EXIT_PROBE=1`), so the normal run's output and timing do not change:

    1. **Stage markers** written unbuffered to stderr and flushed, one line each:
       after `reportSummary`; after each of `main`'s four locals is destroyed (wrap them in a nested
       scope, or give each a small marker guard declared beside it so the reverse-order destruction
       prints between them — do NOT reorder the locals; `TestMain.cpp` says their order is
       load-bearing); in an `std::atexit` handler (registered first, so it runs last among
       handlers); and in the destructor of a function-local static constructed at the top of
       `main` (static destruction stage). On Windows, also a `DLL_PROCESS_DETACH`-stage marker is NOT
       reachable from an exe — say so in the probe's comment rather than faking one.
    2. **A watchdog thread** (Windows only, `#if JUCE_WINDOWS`), started just before `main`
       returns: if the process is still alive N seconds later (default 20), it enumerates every
       thread with `CreateToolhelp32Snapshot`, and for each other thread: `SuspendThread`,
       `GetThreadContext`, `StackWalk64` + `SymFromAddr` / `SymGetLineFromAddr64` via dbghelp,
       print the frames, then `TerminateProcess` with a DISTINCT code (e.g. 3) so the run cannot
       be mistaken for a pass. State plainly in the comment: during `ExitProcess` Windows has already
       terminated every other thread, INCLUDING this watchdog — so if the markers show the block is
       past `main`'s locals, the watchdog will print nothing, and that silence is itself the
       measurement.
    3. Build MSVC Release **with PDBs** for the test target (`/Zi` + `/DEBUG` on ForroBoxTests only;
       the plugin targets unchanged) so frames symbolise. If that needs a CMake change, confine it
       to the test target.

    Run it: `scripts/build-windows.sh` (it will still hit the old 900 s path — that is fine for this
    task), then run the exe directly from WSL with `--exit-probe`, output to a file, under a
    `timeout` well above N. Read the file, not a wrapper's status.

    Avoid: `std::cout` for markers (buffered, and the question is exactly what did not get flushed);
    any change to the order or type of `main`'s locals; leaving the probe on by default.
  </action>
  <verify>
    The probe run's output file shows the stage sequence and stops at a named stage. If that stage is
    within `main`'s locals, the watchdog's stack dump names the blocking frame of every live thread.
    The normal (no-flag) run's output is byte-identical to before apart from nothing — diff it.
  </verify>
  <done>AC-1 satisfied: the blocking stage is named from output, and (if reachable) the waiting function</done>
</task>
