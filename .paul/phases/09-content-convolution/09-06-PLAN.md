<objective>
## Goal

`‹ PÉ-DE-SERRA 01 ›` stops being a label. The header's cycler walks the **active profile's bank**,
each selection loads that groove's patterns *and* its feel, the state records **which** groove, and
save/reload brings it back.

This is what makes 09-04's twelve drafted grooves reachable. Until it lands they exist only as
audition files.

## Purpose

`PLANNING.md:843` specifies it as "a real preset system: save/load full plugin state". Both hero
screenshots show a cycler that does nothing. And two consecutive `/code-review` passes have raised
the same precondition — `applyGroove` records `profile.id()` and clears `dirty` while `State` has no
groove field, so applying `campina/xote-lento` leaves a state claiming "CAMPINA GRANDE, pristine".
**This plan is where that gets answered**, because it is the plan that makes it reachable.

## Output

- `State::activeGroove` — the id, persisted, authoritative
- Selecting a groove loads its eight patterns and its bpm/swing/cachaça
- The header cycler walks the active profile's bank and shows each groove's name
- A groove id from a newer build is preserved verbatim rather than lost
</objective>

<decisions>
## The state records the groove's ID, and that is why `dirty` stays false

Two consecutive reviews flagged that a non-default groove leaves a state lying about itself. There
are two ways out, and they are not equivalent:

- **Mark `dirty`** — which 09-05 did for slots. It makes the state honest but throws the identity
  away: reload restores `grooveBank[0]` and the cycler cannot show what was selected.
- **Store the identity** — which is what a *preset system* means. `PLANNING.md:843` says "save/load
  full plugin state", and a groove is part of that state now.

This plan stores it. Selecting a factory groove is then **not an edit** and `dirty` correctly stays
false — the state says CAMPINA GRANDE / XOTE LENTO and that is exactly what it is. 09-05's slots
took the other branch because a slot's *contents* are user-edited and have no factory identity to
record; the difference is real and both should say so where they are written.

An **ID, not an index**, following `activeProfile`'s precedent: `State::readFrom` preserves an
unrecognised profile string verbatim so "a project saved by a newer build must not lose its
profile" (07-02). A bank index would silently point at a different groove the moment a bank is
reordered or one is inserted — and 09-04's close records that revising a groove is one JSON edit.

## `presetIdx` is NOT repurposed, and this is where that is written down

`State::presetIdx` exists, is clamped to 0-7, is persisted and is round-trip tested — and it has
**no production reader**. It would fit a bank index exactly, which is precisely why the next reader
will assume it is one.

It stays as it is, and its doc comment gains a line saying it is prototype-parity and **not** the
groove selector. Repurposing it would substitute a fragile index for a robust id; removing it is a
state-format change whose only benefit is tidiness, and its four round-trip tests exist to prove the
persistence machinery works rather than to prove anything about presets.

If that judgement is wrong, it is wrong visibly.

## The cycler's contents change with the profile — the sanctioned deviation, now visible

The user chose per-profile banks at 09-02 planning over `PLANNING.md:843`'s flat eight. This is the
plan where that becomes behaviour a user sees: switching profile changes what the cycler offers.
Recorded in the ROADMAP already; restated at the control itself, because this is the first point
where the design source and the product visibly differ.
</decisions>

## AC-1: a groove loads completely
```gherkin
Given CAMPINA GRANDE selected and its bank of four
When the cycler moves to XOTE LENTO
Then all eight lanes hold XOTE LENTO's patterns
 And bpm, swing and cachaça become XOTE LENTO's, as parameter writes the host can see
 And the timbre and the bateria mute are unchanged, because those belong to the profile
```

## AC-2: the state says which groove, and dirty stays false
```gherkin
Given a groove selected from the active profile's bank
When the state is inspected
Then activeGroove holds that groove's id
 And dirty is false, because selecting a factory groove is not an edit
 And editing a pad afterwards sets dirty, as it always has
```

## AC-3: it survives save and reload
```gherkin
Given XOTE LENTO selected
When the state round-trips through getStateInformation/setStateInformation
Then activeGroove comes back
 And the cycler shows XOTE LENTO
 And the patterns and feel are XOTE LENTO's
```

## AC-4: an unknown groove id is not lost
```gherkin
Given a project saved by a newer build whose bank has a groove this build lacks
When it is loaded
Then activeGroove keeps the unrecognised id verbatim
 And the plugin plays the profile's default groove rather than throwing or going silent
```

## AC-5: the cycler follows the profile
```gherkin
Given CARUARU selected, showing its four grooves
When CAMPINA GRANDE is selected from the side panel
Then the cycler shows CAMPINA GRANDE's bank, starting at its default groove
 And moving past either end of a bank clamps rather than wrapping into another profile's
```
