<objective>
## Goal

Each regional profile carries a **bank of grooves** instead of one. The schema, the C++ storage, the
generator and the gates all grow to hold it — and **not one note changes**, because the four grooves
that exist become each profile's first entry and nothing else is added yet.

`ids::profileInfos` stops being hand-transcribed at the same time. It is the one consumer 09-01's
extraction skipped, it is the file this plan must edit anyway, and `src/Profiles.cpp:19-23` already
carries a comment saying 09-02 walks into it.

## Purpose

This is the mechanism plan, and it is deliberately empty of content. 09-03 drafts twelve grooves and
puts them in front of Esmeraldo; if the schema, the codegen and the gates land first and land green
with **zero musical change**, then every groove 09-03 adds is one JSON edit that six gates check —
which is exactly what 09-01 bought and what this plan extends from one groove per profile to N.

Splitting it this way also means the drafting plan's checkpoint sits at the end of a short plan
rather than behind four tasks of scaffolding.

## Output

- `assets/profiles.json` — each profile gains `grooves: [...]`, its first entry holding today's patterns
- `Groove` in `src/Profiles.h`; `Profile` carries the bank and keeps its `patterns()` accessor
- `ids::profileInfos` GENERATED, deleting the last hand transcription in the groove path
- `data.js` and the standalone page keep a top-level `patterns` so the read-only prototype still runs
</objective>

<decisions>
## The bank is PER PROFILE, and that departs from the spec

`PLANNING.md:843` specifies the top cycler as *"Real preset system: save/load full plugin state"*
with **eight flat labels** — `PÉ-DE-SERRA 01`, `BAIÃO SECO`, `XOTE LENTO`, `ARRASTA-PÉ`,
`XAXADO 88`, `FORRÓ ELÉTRICO`, `QUADRILHA`, `PISADINHA` — and `app.js:561`'s `cyclePreset` is
global: it walks that flat list and never looks at `activeProfile`.

Those eight are **rhythms**. The four profiles are **regions**. They are orthogonal axes, and the
ROADMAP's recorded assumption that "the factory presets ARE the per-profile grooves" does not
survive reading the code. It was written down as an assumption precisely so it could be corrected
here.

**The user chose per-profile banks at 09-02 planning, over the spec-faithful flat eight.** So
CAMPINA GRANDE offers its own list, CARUARU its own, and the cycler's contents CHANGE when the
profile changes — behaviour `PLANNING.md` does not describe. That makes it a **sanctioned
deviation**, the same standing as 08-01's ABOUT panel: PROJECT.md's mandate is that a control the
design source does not specify is not invented, and the user's explicit decision is the exemption
that mandate requires. This section is where it is written down.

The eight spec labels are not discarded — they are rhythm names, and 09-03 draws each profile's
groove names from them where the rhythm genuinely belongs to that region.

## `data.js` KEEPS a top-level `patterns`, and this is load-bearing

`app.js:135` is `const base = S(p.patterns[key])`, inside `buildGroove`. `app.js` is READ-ONLY.
Moving the patterns under `grooves[0]` in the generated `PROFILES` block would break both
prototypes on boot.

So the generated `PROFILES` keeps `patterns` — rendered from `grooves[0]` — and gains `grooves`
beside it. The prototype ignores the new key and behaves exactly as it does today. AC-4 is that
claim, and it is tested by running the prototype's own `buildGroove`, not by reading the diff.

## The C++ does NOT keep both

`Profile::patterns` becomes an accessor returning `grooves[0].patterns`. Storing the same eight
strings twice is the duplication this phase exists to end, and an accessor means **`applyProfile`
needs no change at all** — it already reads `profile.patterns`, and `profile.patterns()` reads the
same characters.
</decisions>

    contain the claim it declares, or the two have drifted.

    Avoid: deleting `check_descriptions` outright. Its whole value is that a description and its
    data can disagree, and generating the prose does not make them agree — it only moves where the
    disagreement can be introduced.

    Enrol `src/ParameterIDs.h` as an input to whichever gates now read it, and add it to the
    `--verify` target's DEPENDS. 09-01's SUMMARY records the enrolment failure four times; this is
    the fifth opportunity to repeat it.
  </action>

    `grooves: [{ "id": "...", "name": "PÉ-DE-SERRA 01", "patterns": { ...the eight lanes... } }]`.
    Give each existing groove the name the cycler should show for it. `validate` gains: at least one

<boundaries>

## DO NOT CHANGE
- `PLANNING.md`, `uploads/UIUX.md`, `forrobox.css`, `controls.js`, `app.js` — READ-ONLY design
  source. A mismatch is never fixed by editing the reference. `app.js:135` in particular constrains
  the generated JS shape; it is worked AROUND, not edited.
- `data.js`'s `INSTRUMENTS`, `CHANNEL_DEFAULTS`, `TIMBRES`, `PRESETS` and `buildGroove` — still
  hand-written and authoritative. Only `PROFILES` and `PROFILE_ORDER` are generated.
- Parameter and group IDs in `src/ParameterIDs.h`. The `profileInfos` ARRAY becomes generated; the
  parameter id strings around it do not move. Renaming one invalidates saved host state.
- `processBlock` stays allocation-free and lock-free. The groove bank is a `constexpr` table.
- `applyProfile` — the accessor exists so this function does not change. If it needs to, the shape
  is wrong.

## SCOPE LIMITS
- **NO NEW GROOVES.** Every profile ends this plan with exactly the one it has. 09-03 drafts the
  content; this plan proves the bank holds it. AC-1 is the tripwire.
- No UI. Nothing reaches a second groove until 09-05 builds the cycler — that is expected, and it is
  why this plan ships no content for a user to be unable to select.
- No change to `Profile`'s mute model. 09-01 refused a non-`bateria` mute and priced widening it;
  that price has not changed and no groove here needs it.
- No new third-party dependency.

</boundaries>
