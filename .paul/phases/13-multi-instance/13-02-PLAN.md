<objective>
## Goal
- **`Settings::Listener`** (`settingsChanged()`), held in a `juce::ListenerList` on the shared
  store. `set` calls it synchronously, on the calling (message) thread, AFTER a write that
  succeeded. No notification follows a failed write, because nothing changed.
- **`Chassis::applySettings()`** is the ONE entry point. It does three things:
  - `settings::applyTo (lnf, Settings::shared())`;
  - **a re-layout of the whole tree:** `resized()` on the chassis and every descendant, top down;
  - `repaintAll()`.
- **Who calls `applySettings()`:**
  - each `Chassis`, as a `Settings::Listener`, registered in the constructor and removed in the
    destructor;
  - the editor's constructor, which keeps SEEDING the store into its LookAndFeel, now through
    `applySettings()` in place of the hand-written pair.
- `handleSettingsMenuResult`'s `changed` branch stops applying by itself. The notification reaches
  this instance like every other one.
- **`Segmented` rebuilds its `spans` in `resized()`.** Today it builds them only in its
  constructor. `SidePanel` already re-measures in `resized()`, and `ValueScreen::preferredWidth`
  measures live, so a re-layout pass covers all three.

## Purpose
- **ROADMAP Phase 13:**
  - "theme, radius, accent, steps and the font (visibly torn today) stop going stale in the other
    instance";
  - "Re-layout after a font switch — `Segmented`'s cached spans, `SidePanel`,
    `ValueScreen::preferredWidth`".
- **The user's decision at Phase 13 planning:** a synchronous `ListenerList`, over
  `ChangeBroadcaster`. That puts no `AsyncUpdater` in a process static, and tests run
  deterministically without pumping the message loop.
- It closes 12-02's /simplify deferral: one entry point instead of the `applyTo` + `repaintAll`
  pair. The broadcast is its third caller, not a fourth copy of the pair.

## Output
- The listener on the store.
- A `Chassis` that follows the store.
- `Segmented` re-measuring on layout.
- Two-instance tests.
</objective>

## Measured at planning (2026-10-02)
- **The construction boundary holds.** `Chassis` must not SEED from the store when constructed:
  that once made `ChassisRig { light }` dark (Chassis.cpp:769). Following a CHANGE is a different
  act. The change is the user's latest word for every instance, so a rig in light mode that sees a
  theme change takes it, as the product's second instance would.
- **The font's metric delta is small:** 0.600 em against 0.612 em (08-03). A span may round to the
  same integer at small sizes, so the re-layout check must be proven by mutation (AC-3), not
  assumed.
- `set` callers: `SettingsMenu::apply` (the message thread, via the menu) and the tests. The
  processor's constructor only reads.

        when its next editor opens.

      - Derive from `Settings::Listener`. Add `Settings::shared().addListener (this)` at the END of
        the constructor, and `removeListener` FIRST in the destructor.

        seeding.
      - `void applySettings()`, public: `settings::applyTo (lnf, Settings::shared())`, then the
        re-layout, then `repaintAll()`.
      - The re-layout is a small recursive helper: `resized()` on a component, then on each child.
        It is the general mechanism (anything that caches a text metric recomputes it in
        `resized()`), not a list of the three known components.
      - `settingsChanged() override { applySettings(); }`.
      - `handleSettingsMenuResult`, `changed` branch: return true and nothing else. Comment it: the

      first paint" comment.
    - **Avoid:**
      - async delivery;
      - notifying from `get`;
      - a re-layout list naming the three components;
      - touching the store's file I/O (13-01).
