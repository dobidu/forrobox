<objective>
## Goal

The four regional grooves live in `assets/profiles.json`. The C++ table and the prototype's own
copies are GENERATED from it, and every consumer is proved to agree with it on every build. Not one
digit of the music changes.

## Purpose

`STATE.md` has carried this as a deferred item since **Phase 2**: *"Extract `PROFILES` from
`data.js` into a `profiles.json` consumed by both the prototype and the cross-check — the root fix
for parsing `data.js` with regexes, raised by `/simplify`."* It was blocked on a boundary decision,
and the user took that decision before this phase was planned.

It goes first because **every plan after it makes the problem worse.** `verify-profiles.py` is 390
lines that regex-parse JavaScript, including a hand-written brace matcher written because a
non-greedy regex matched the wrong object — and 09-02 multiplies the content it parses. Extracting
after adding grooves means extracting more.

And it is the plan that can prove it changed nothing. Four profiles exist today, cross-checked
digit by digit; the extraction either reproduces them exactly or it is wrong.

## Output

- `assets/profiles.json` — one file, the source of the music
- A generator with a `--verify` mode, following `scripts/build-fonts.py`'s established shape
- A cross-check that reads JSON instead of parsing JavaScript
- A new check the audit asked for: each profile's own DESCRIPTION, against its data
</objective>

<task type="auto">
  <name>Task 1: `profiles.json`, and a generator that proves it changed nothing</name>
  <files>assets/profiles.json, scripts/build-profiles.py</files>
  <action>
    Extract the four profiles out of `data.js` into `assets/profiles.json` — every field, not just
    the patterns: id, name, short, code, desc, bpm, swing, cachaca, timbre, muted, and the eight
    lane patterns. `PROFILE_ORDER` too, because the order IS data: `Profiles.cpp`'s static_assert
    ties row i to `ids::profileInfos[i]`.

    EXTRACT IT MECHANICALLY, not by hand. A hand-transcribed JSON is the exact failure this whole
    plan exists to end, and it would be transcribing 32 pattern strings. Write the extractor,
    run it, and let the diff be the proof.

    `scripts/build-profiles.py` then generates from that JSON, following `build-fonts.py`'s
    established shape — the same `--verify` contract 04-01 built and 08-03 reused:

      (no flag)   write the generated artefacts
      --verify    re-derive them and fail if what is on disk differs

    THE GENERATED C++ MUST BE BYTE-IDENTICAL to `src/Profiles.cpp`'s table as committed. That is
    this task's whole proof, and it is checkable with `git diff`: generate, and the diff is empty
    except for the parts the plan deliberately changes. A generator that produces equivalent-but-
    differently-formatted C++ has not proved anything about the music — it has produced a diff
    nobody can read.

    Keep the table's banner comment. `Profiles.cpp:8` already says "GENERATED FROM data.js — do not
    hand-edit a digit here", which has been an instruction to humans rather than a fact since
    Phase 2. Make it a fact, and update it to name the JSON.
  </action>
  <verify>
    python3 scripts/build-profiles.py --verify   # exit 0 against the committed tree
    git diff --stat src/Profiles.cpp             # the table's digits unchanged
    cmake --build build-linux --target ForroBoxTests -j8 && (unset DISPLAY; ./build-linux/ForroBoxTests)
    Checks: every profile's every lane decodes to the same velocities as before — asserted against
    values written in the test, not against the table being tested.
  </verify>
  <done>AC-1</done>
</task>

<task type="auto">
  <name>Task 2: the cross-check reads JSON, and the prototype is generated too</name>
  <files>scripts/verify-profiles.py, data.js, Forró Box (standalone).html, CMakeLists.txt</files>
  <action>
    **`verify-profiles.py` stops parsing JavaScript.** It reads `profiles.json` with `json.load`
    and compares the C++ against it. `match_braces` (:66) and the `PROFILES` regexes go — that
    machinery exists only because the source was JavaScript, and its own docstring records a
    non-greedy regex that matched `CHANNEL_DEFAULTS` instead.

    WHAT STAYS is everything that reads the C++: `join_literals`, the `timbreSpecs` comparison,
    `ids::profileInfos`, the lane order. The C++ is still the thing being checked; only the
    reference moved.

    **`data.js` becomes GENERATED for its `PROFILES` block, and that is a change of status worth
    stating.** For nine phases `data.js` has been the design source of truth and read-only. The
    user's decision moves the grooves out of it, which necessarily edits it — so this plan writes
    that down rather than doing it quietly. Everything else in `data.js` is untouched:
    `INSTRUMENTS`, `CHANNEL_DEFAULTS`, `TIMBRES`, `PRESETS` and `buildGroove` stay hand-written and
    stay authoritative.

    **The standalone page follows for free.** `docs/README-prototype.md:17` records
    `build_standalone.py` as what regenerates it from the sources, so the chain is
    `profiles.json` → `data.js` → `build_standalone.py` → the standalone page. Run it; do not
    hand-patch the inlined copy.

    **ENROL ALL THREE.** The build must compare the generated C++, `data.js`'s block and the
    standalone page against the JSON. Two of those are easy to forget precisely because they are
    generated — and a generated file that has drifted is worse than a hand-written one, because
    nobody thinks to look.
  </action>
  <verify>
    python3 scripts/verify-profiles.py           # reads JSON; reports what it compared
    python3 build_standalone.py && git diff --stat "Forró Box (standalone).html"
    grep -c "match_braces\|const PROFILES" scripts/verify-profiles.py   # 0
    cmake --build build-linux --target ForroBoxTests -j8
    Then run `/code-review` on the diff.
  </verify>
  <done>AC-2 and AC-3</done>
</task>

<task type="auto">
  <name>Task 3: the audit a machine can do</name>
  <files>scripts/verify-profiles.py, tests/VoiceTest.cpp</files>
  <action>
    The user asked for a deep review of the grooves. Most of that is a listening judgement and it
    belongs at the checkpoint. This task is the part that is mechanical, and it is not small —
    **each profile's description makes claims about its own data**, and nothing has ever compared
    them:

      campina    "Timbre HI-FI, bateria em silêncio."   → timbre hifi, muted.bateria true
      caruaru    "Peso extra na zabumba, swing alto."   → swing 54, the highest of the four
      petrolina  "Timbre LO-FI, cachaça baixa."         → timbre lofi, cachaca 16
      sp         "Quantizado, cachaça quase zero."      → swing 16 lowest, cachaca 6 lowest

    Two kinds of claim, and both are checkable. The NAMED ones — a timbre by name, `bateria em
    silêncio` — are exact. The ORDINAL ones — `swing alto`, `cachaça baixa`, `quase zero` — are
    claims about this profile's RANK among the four, which is why they can be checked at all
    without inventing thresholds.

    DO NOT invent a claim the text does not make. A description that says nothing about cachaça is
    not asserting anything about it, and a checker that guesses would fail on correct data. Parse
    what is written; ignore what is not.

    In the suite, prove the structural properties of every pattern: exactly 16 significant
    characters, velocities within 1-9, and that no lane of any profile is silent unless the
    profile's data says that channel is muted. The last one is the check that would catch a lane
    accidentally emptied by the extraction — the failure this plan most needs to not have.
  </action>
  <verify>
    python3 scripts/verify-profiles.py   # reports the description claims compared
    cmake --build build-linux --target ForroBoxTests -j8 && (unset DISPLAY; ./build-linux/ForroBoxTests)
    Mutations: change `petrolina`'s timbre to hifi while its description says LO-FI; unmute
    campina's bateria; empty one lane. Each must fail, naming the profile and the field.
  </verify>
  <done>AC-4</done>

<boundaries>

## DO NOT CHANGE

- **The music.** Not one velocity digit, in this plan. 09-02 adds and revises; 09-01 moves. Any
  diff in a pattern string here is a bug in the extraction, and AC-1 exists to catch it.
- **Everything in `data.js` except the `PROFILES` block.** `INSTRUMENTS`, `CHANNEL_DEFAULTS`,
  `TIMBRES`, `PRESETS` and `buildGroove` stay hand-written and authoritative. The other four
  cross-checks read `data.js` and `app.js` for their own values and must keep passing untouched.
- **`Profile`'s shape.** `Profiles.h`'s struct, `decodePattern`, `expandPattern` and the
  static_asserts tying row `i` to `ids::profileInfos[i]` are Phase 2's and are not this plan's to
  redesign.
- **The 46 parameter IDs**, and the pattern storage the audio thread reads.

## SCOPE LIMITS

- **No new grooves.** That is 09-02, and it is the reason this plan goes first.
- **Neither cycler.** `PAT 01`–`08` is 09-03 and the preset system is 09-04. The `PRESETS` list in
  `data.js` is not touched here.
- **No runtime JSON.** The plugin does not parse `profiles.json` at load — it is a BUILD-time
  source that generates a `constexpr` table. The audio thread keeps reading exactly what it reads
  today, and this plan adds no parsing, no allocation and no failure mode to a running plugin.
- **No `LOAD IR…`.** 09-05.

</boundaries>
