<objective>
## Goal

A pure function from the stored pattern, BPM and step window to the bytes of a Standard MIDI File —
type 0, PPQ 96, one track — whose output is compared BYTE FOR BYTE against the prototype's own
`exportMIDI`, run as JavaScript, across every profile and step window.

## Purpose

`PLANNING.md:804-825` specifies the format completely and names `exportMIDI()` in `audio.js` as the
reference implementation. That makes this the same shape as the groove tables: a design source
exists, and Phase 2's decision was *"generated from `data.js`, never transcribed, and cross-checked
on every build"* — because a wrong digit is not a crash, it is a file a DAW opens with the groove
subtly wrong and no way to know which byte.

A MIDI file is worse than a groove table for this. Its bytes are a delta-encoded stream: one wrong
VLQ shifts every event after it, and the result still parses. A test that asserts "34 events" or
"the first note is 36" would pass against a file whose timing is silently wrong from bar two.

The reference is RUNNABLE, which is what makes this a cross-check rather than a second
transcription. `audio.js:311` assigns `window.FB_AUDIO = { Engine, exportMIDI }`, and Node 24 is on
this machine with `Blob` as a global — so the prototype's own function can produce the expected
bytes and the C++ is compared against them, not against my reading of them.

## Output

- `src/MidiExport.h` / `.cpp` — `State` + bpm + steps → `std::vector<std::uint8_t>`
- `scripts/verify-midi.js` — runs the prototype's `exportMIDI` under Node
- `scripts/verify-midi.py` — a FIFTH cross-check, comparing the two across a matrix of states
- Suite checks for the properties bytes cannot express

<task type="auto">
  <name>Task 1: The Standard MIDI File writer</name>
  <files>src/MidiExport.h, src/MidiExport.cpp, CMakeLists.txt</files>
  <action>
    A free function in `namespace forrobox`, taking the pieces rather than the processor:

        std::vector<std::uint8_t> renderStandardMidiFile (const State&, int bpm, int steps,
                                                          const ChannelGate& muted);

    Taking the state BY VALUE OR CONST REF and not the processor is 03-02's law for the clock: a
    pure function of its arguments can be swept exhaustively offline with no processor, no host and
    no audio device. It is also what lets Task 2 feed it a matrix of states.

    The format, from `PLANNING.md:806-820`:
    - Header `MThd`, length 6, format 0, one track, division 96.
    - One `MTrk`. Sixteenth = 24 ticks.
    - Note-on `0x99`, note-off `0x89` — channel 10, which is `0x9` and `0x8` with the low nibble 9.
    - Gate = `floor(24 × 0.8)` = 19 ticks. Write the multiplication, not the 19: the prototype
      writes `Math.floor(stepTicks * 0.8)` and a literal would stop tracking PPQ.
    - Tempo meta `FF 51 03` from `round(60000000 / bpm)`; time signature `FF 58 04 04 02 18 08`.
    - Events collected, sorted by tick, then delta-encoded as VLQ.
    - Velocity clamped to `[1, 127]` — the prototype's `max(1, min(127, round(vel)))`. A zero
      velocity note-on IS a note-off in MIDI, so the clamp is load-bearing, not cosmetic.
    - GM map: zabumba 36, triângulo 81, pandeiro 54, ganzá 82, BB 36, CX 38, HH 42, TOM 45.

    THE MAP IS ONE ARRAY OF STRUCTS beside the lane it belongs to, not a parallel table — the rule
    `ids::channelInfos` states in its own comment and 06-05 applied to `kitPieces`. Zabumba and BB
    share note 36 deliberately; that is the spec, not a mistake to normalise away.

    A STABLE SORT, and it matters: two lanes can land on one tick (zabumba and BB share a note
    number, and any two lanes can share a step), so an unstable sort would reorder equal-tick events
    between runs and the byte comparison in Task 2 would flake. `std::stable_sort`.

    Add `src/MidiExport.cpp` to the `ForroBox` source list.
  </action>
  <verify>
    cmake --build build-linux --target ForroBoxTests -j8 && (unset DISPLAY; ./build-linux/ForroBoxTests)
    Read the first 22 bytes of a produced file by hand ONCE and confirm the header is
    `4D 54 68 64 00 00 00 06 00 00 00 01 00 60` — then never eyeball bytes again; Task 2 is the
    check that can fail.
    Then run `/code-review` on the diff.
  </verify>
  <done>AC-3 partially satisfied: the format is written; Task 3 proves it is READ BACK correctly</done>

<task type="auto">
  <name>Task 2: The cross-check — the prototype's own exportMIDI, run as the reference</name>
  <files>scripts/verify-midi.js, scripts/verify-midi.py, CMakeLists.txt</files>
  <action>
    `scripts/verify-midi.js` stubs `window`, loads `audio.js`, and calls
    `window.FB_AUDIO.exportMIDI (state)` — the DESIGN SOURCE ITSELF, not a port of it. It reads a
    state as JSON on stdin and writes the bytes as hex on stdout. `audio.js:29` touches
    `window.AudioContext` only inside the engine's init, so loading it does not need a browser.

    `scripts/verify-midi.py` drives the comparison over a MATRIX, because one agreeing file proves
    one file:
    - each of the four profiles,
    - at 16 and 32 steps,
    - at two BPMs, one of which does not divide 60000000 evenly (the tempo meta rounds),
    - and one run per channel with that channel muted, plus one with BATERIA muted.

    It asks the C++ for the same bytes through a tiny `--emit-midi` mode on the test executable, or
    a dedicated tool — whichever needs less machinery; state the choice in the script's docstring.

    ON A MISMATCH, PRINT THE FIRST DIVERGING OFFSET and the surrounding bytes from both sides. A
    delta-encoded stream shifts everything after one wrong VLQ, so "files differ" sends the reader
    to diff two hex dumps by hand; the offset is the whole diagnosis.

    Wire it as a build dependency like the other four, with `verify-midi.js`, `audio.js` and
    `src/MidiExport.cpp` in its DEPENDS — `audio.js` because it is the reference, and 06-06 shipped
    a gate whose DEPENDS did not list what it read.

    IF NODE IS ABSENT, FAIL LOUDLY at configure time or skip with a stated reason — do not pass
    silently. `FORROBOX_REQUIRE_PROFILE_CHECK` is the precedent: a check that quietly stops running
    is the failure this project keeps finding.
  </action>

<task type="auto">
  <name>Task 3: The properties bytes cannot express</name>
  <files>tests/UiTest.cpp, tests/TestSuites.h</files>
  <action>
    The byte comparison proves the C++ agrees with the prototype. It cannot prove the prototype's
    format is what PLANNING says, and it cannot fail if BOTH are wrong the same way. These checks
    read the produced file BACK and assert the spec directly:

    - `juce::MidiFile::readFrom` parses it, reports ONE track, and a time format of 96.
    - Every note-on is channel 10, and every note-off follows its note-on by 19 ticks.
    - The GM note numbers are compared against a table carrying `PLANNING.md`'s own line numbers,
      so a wrong number is traceable to the row that specifies it.
    - AC-4's two negative controls: raise CACHAÇA and swing, write the file, and assert the ticks
      are still exactly `step × 24`; and assert no note exists at a step whose stored velocity is 0.

    THE SECOND NEGATIVE CONTROL IS THE POINT. "Ghosts are not exported" is true today for a reason
    that has nothing to do with this writer — `PLANNING.md:584` says ghosts are never written into
    the pattern at all, so the writer excludes them by never seeing them. A check that passes
    because the feature is absent is the shape this project keeps finding, so SAY SO in the check's
    message rather than letting a future reader think the writer filters them.

    Every check must be proved able to fail. Mutate the gate, the channel nibble and one GM number,
    assert each edit landed, and confirm the matching check fails and no other.
