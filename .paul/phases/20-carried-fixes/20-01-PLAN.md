<objective>
## Goal
Close the three issues deferred from v0.3:
1. **One chooser helper and one warning, used by every file dialog.** `launchChooser` and the
   warning box are lifted out of `Chassis.cpp` into a shared unit. `LOAD IR…` and the MIDI export
   use them.
2. **The MIDI export asks before replacing a file.** When the forced `.mid` extension points at a
   file that already exists, the user is asked first. 19-02 fixed the same bug for grooves.
3. **The seqlock contention check is deterministic.** It no longer depends on how the CI
   scheduler happens to interleave two threads.

## Purpose
Each bug class gets one fix instead of three. Export groove… saved nothing because a chooser was
read after its own reset (19-02). The MIDI and IR dialogs are hand-written copies of the same shape,
so the rule should live in one place before Phase 23 changes `LOAD IR…`. Silently replacing a
user's file is data loss. A macOS CI run that goes red at random teaches people to rerun instead of
read.

## Output
- `src/AsyncFileChooser.h/.cpp`: `forrobox::launchChooser` and `forrobox::showWarningBox`
- Chassis, SidePanel and DragMidiButton all use them
- DragMidiButton gains two hooks, a replace confirmation and a warning. Chassis wires the
  confirmation to the preset screen's `SUBSTITUIR O ARQUIVO?`
- Test seams `DragMidiButton::exportTo` and `SidePanel::loadImpulseResponseOrWarn`, with new tests
- A deterministic contention test, and the saturated-writer test keeping only properties that
  hold for every interleaving
</objective>

  <action>
    - PatternSnapshot.h: add `friend struct PatternPublisherTestAccess;` to PatternPublisher, with
      a comment saying it is test-only. No behaviour change, no runtime cost. processBlock is
      untouched.
    - New case "pattern handover: a held lock is refused, not waited for". A helper thread takes
      `publisher.lock` through the test access struct, publishes a new staging table under it
      (or the test stages one), signals that it holds the lock, then holds for about 2 s and
      releases. The main thread then times one `reader.refresh`. Check: it returns false,
      elapsed < 500 ms, contentionCount == 1, and seedOf (reader) is still the old seed. After
      the helper joins, refresh returns true with the new seed.
    - Why a helper thread and not the main thread: a reader mutated to `enter` would deadlock on
      a same-thread SpinLock. With the holder on another thread it unblocks after about 2 s and
      FAILS the elapsed and false checks. The test reports the failure instead of hanging.
    - testSaturatedWriterStarvesSafely: remove the `contentionCount() > 0` assertion and its
      comment's claim; point to the new case. Keep writer-saturated, accounting, torn == 0 and
      convergence. Also drop `failed > 0`, since it is scheduler-dependent on the same runner,
      unless it is shown to hold for every interleaving. Say why in the comment.
    - Mutation proof: change refresh's ScopedTryLockType to ScopedLockType (blocking). The new
      case fails and the suite finishes. Revert.
  </action>
