<objective>
## Goal

Make `SYNC` real. When it is on, the clock follows the host's tempo and transport and step 0 lands on
the host's bar. When it is off, nothing about the internal behaviour changes.

The mechanism is a reformulation, not a second mode: `Clock::advance` stops taking "advance by N
samples" and starts taking "this block spans musical position *A* to *B*". The processor computes that
range — from the playhead when synced, from `bpm` when not — and host loops, jumps and tempo ramps
stop being special cases.

## Purpose

`PLANNING.md` requires that `SYNC` "follow host tempo AND host transport" and "lock step 0 to the host
bar", and is explicit about why a local counter cannot do it: alignment must be derived from absolute
host PPQ each block, or a 16- or 32-step pattern drifts out of phase with the project. A groove that
drifts against the DAW is not a groove a producer can use, and `Timing accuracy of triggers` is a
named success metric in PROJECT.md — "step 0 locked to host bar when synced" is its wording.

02-02's clock owns its own position (`gridPhase`, `nextStep`), which is exactly what cannot accept a
host jump. Bolting sync alongside that would mean a re-anchor entry point or a `syncMode` flag — a
second mode sharing only the swing and rounding code. The reformulation keeps one path and is cheaper
now than after Phase 3's voices depend on the emission semantics.

<task type="auto">
  <name>Task 1: Reformulate advance() around a musical position range</name>
  <files>src/Clock.h, src/Clock.cpp, src/PluginProcessor.cpp, tests/ClockTest.cpp</files>
  <action>
    Replace `advance (numSamples, params, listener)` with a form that takes the musical span of the
    block — start and end position in steps (sixteenths) — plus the block length in samples, so the
    clock can convert a position to a sample offset without owning a position itself.

    Delete `gridPhase`, `nextStep` and the pending-step record. With a range as input, "which step is
    next" is a question about the range, not remembered state: the first sixteenth boundary at or
    after the start, iterated to the end. A swung step's placement is computed from its own boundary,
    so nothing needs deferring across blocks and there is no debt to carry — this is what 02-02's
    `/simplify` pass predicted would dissolve the clamp problem entirely.

    Keep exactly, and unchanged in behaviour:
    - swing on odd steps only, `(swing/100) x 0.6 x stepDuration`, never advancing the grid;
    - `floor(x + 0.5)` rounding rather than `juce::roundToInt`, whose ties-to-even is not
      translation-invariant — the reason is still live because offsets are still block-relative;
    - the window wrap over `activeSteps`, not over `State::kMaxSteps`;
    - the non-finite input guards;
    - `noexcept`, no allocation, no locking.

    The processor computes the range for the internal path: `end = start + numSamples / stepSamples`,
    carrying `start` forward between blocks. That moves the tempo source fully to the processor,
    which is where `Params`-by-value already put it — the clock should no longer compute
    `stepSamples` from `bpm` at all.

    Migrate all of 02-02's clock cases to the new call shape. Do NOT delete a case to make it
    compile: the count must be accounted for, and each property must still be asserted. The
    block-size invariance sweep, the tempo-change invariance case, the offset-in-block property, the
    drift run and the allocation counter with its self-test are the ones that matter most.

    Avoid: keeping a `syncMode` flag or a second entry point "just in case" — the whole point is one
    path. Avoid making the range a sample count in disguise (e.g. passing bpm and deriving the range
    inside the clock), which would put the tempo source back where it was.
  </action>
  <verify>Full suite green under GCC and Clang, with the clock case count accounted for against 02-02's 120; the block-size invariance and tempo-change invariance cases pass unchanged in intent; allocation delta across the emission path is 0</verify>
  <done>AC-1 and AC-2 satisfied; AC-8's allocation half satisfied</done>
</task>

<task type="auto">
  <name>Task 2: Drive the range from AudioPlayHead when SYNC is on</name>
  <files>src/PluginProcessor.h, src/PluginProcessor.cpp</files>
  <action>
    In `processBlock`, call `getPlayHead()` and `getPosition()` at most once, then decide the range:

    - `sync` off → internal tempo, exactly as Task 1 leaves it.
    - `sync` on, playhead usable → `start = ppqPosition * kStepsPerBeat`, `end = start + numSamples /
      stepSamplesFromHostTempo`. Step 0 falls on the host's bar because the position is absolute:
      derive the windowed index from the absolute step position, using
      `getPpqPositionOfLastBarStart()` as the bar anchor when the host supplies it.
    - `sync` on, playhead unusable → fall back to internal tempo. Every `PositionInfo` field is
      `Optional`; hosts populate them inconsistently, so treat absent PPQ or absent tempo as
      "cannot sync this block" rather than as zero.
    - `sync` on and the host is not playing → emit nothing, and report the stopped step.

    Host jumps and loops need no special case: because the range comes from the host's absolute
    position each block, a jump simply produces a range starting somewhere else. Add one guard, and
    say why: a range whose start is far behind the previous block's end must not be "caught up" by
    emitting the intervening steps — clamp the span to the block's own musical length so a backwards
    jump cannot produce a burst.

    Reject a non-finite or negative PPQ position the way `Clock::prepare` rejects a non-finite sample
    rate: NaN fails every comparison, so a `<= 0` test does not catch it.

    Consider whether `resetPending` should stay a separate atomic or become part of one published
    transport snapshot — 02-02 flagged it, and this plan adds a second control input. Keep it simple
    if a snapshot is not yet earning its place, and record the call either way; 02-04's handover is
    the natural moment for it.

    Avoid: reading the playhead more than once per block; `juce::String` anywhere on this path;
    touching `patternState` — the handover is 02-04.
  </action>
  <verify>Plugin builds under GCC, Clang and MSVC; processBlock calls getPosition() at most once; a state round-trip still does not restore `playing`; Windows VST3 loads in Ableton Live 12</verify>
  <done>AC-3, AC-4, AC-5, AC-6 and AC-7 satisfied at the processor level; AC-8 satisfied</done>
</task>

    Give it an advance helper that moves PPQ forward by a block at a given tempo, so a test reads as

    Cases, in `StateRoundTripTest.cpp` alongside the existing transport group:

    - **Transport (AC-5):** host not playing emits nothing even with the plugin's own transport on;

    Every timing invariant here needs a control proving the case can fail — the bar-lock case
    especially, since a clock that ignores the host entirely would still pass a weak version of it.

    Avoid: asserting bar lock only at position 0, which passes for a clock that never syncs at all.
