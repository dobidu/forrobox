<objective>
## Goal
**A user groove is a built-in groove's shape, kept in a file.** It holds:
- a stable `id` (a UUID, never changed by rename), a `name` (UTF-8, trimmed, 1–24 chars);
- `bpm`, `swing`, `cachaça`;
- the eight lanes at the full 32 slots, velocity 0–127. A built-in pattern is 16 chars of
  `'.'`/`'1'`–`'9'`; a user grid is not, so the file stores the State's own resolution.

It carries NO timbre, mutes, mixer, voices, IR or pattern slots (user decision: "grid + feel, like
a built-in"). Loading one behaves exactly as `loadGroove` does: feel parameters, then the lanes,
slots reset to PAT 01, pristine.

**Storage (user decision: a folder of groove files):**
- `<settings dir>/grooves/` — the directory `Settings::realFileLocation()` resolves
  (`~/.config/Forro Box/`, `~/Library/Application Support/Forro Box/`, `%APPDATA%\Forro Box\`), so
  the Linux `~/Forro Box/` trap Settings documents is not repeated.
- One file per groove: `<id>.forrogroove`, XML, root `<ForroBoxGroove version="1" id name bpm
  swing cachaca>` with one `<lane id="<ids::lanes id>" steps="v v v … (32 ints)"/>` per lane. The
  filename is the id, so a rename rewrites one file and never collides.
- **Strict read** (the `decodePattern` rule: refuse rather than guess): wrong root/version, a missing
  or duplicate lane, an unknown lane id, a step count ≠ 32, a value outside 0–127, a non-UUID id, an
  id ≠ the filename stem, an empty name → the file is skipped and reported, never half-loaded.
  `bpm`/`swing`/`cachaça` are clamped to their parameter ranges, as a restore clamps.
- **Atomic writes:** `XmlElement::writeTo` via `TemporaryFile`, as Settings writes. An overwrite
  never leaves a truncated file.
- Unlimited count (user decision). The bank is sorted by name, case-insensitively, ties by id, so
  the order is stable across instances and processes.

**The library object** (`forrobox::UserGrooveLibrary`, message thread only):
- `rescan()` lists the folder and parses every file; `grooves()` returns the sorted bank;
  `find(id)`.
- `save(name, snapshot) → id`, `overwrite(id, snapshot)`, `rename(id, name)`, `remove(id)`; each
  returns a `juce::Result` naming the failure (unwritable folder, unknown id, invalid name) and
  rescans after a successful write.
- One per process, shared by instances (`juce::SharedResourcePointer`). Another PROCESS's write is
  seen on the next `rescan()`, which the processor calls before resolving the bank (a directory
  listing of small files; the cycler is not a hot path).

**The reserved USER profile:**
- `ids::userProfile = "user"`; not in `profileInfos` (so the header's STYLE and `indexOfProfile`
  keep 4 entries), and a test fails if a `profileInfos` id or a `profiles.json` id ever equals it.
- A state playing a user groove is `activeProfile = "user"`, `activeGroove = <uuid>`, `dirty =
  false`. This resolves `activeGroove`'s meanings by SCOPE rather than adding a fifth in-band value:
  under a regional profile its four meanings are unchanged; under `user` it is a library id.
- **`activeGrooveName()`:** under `user`, the library's name for the id; an id not in this
  machine's library (a project from elsewhere, or a deleted groove) → empty, like `kNoGroove`. A
  UUID on the screen tells the reader nothing, unlike a newer build's `coco-02`.
- **`cycleGroove(delta)`:** under `user`, moves through the sorted library bank, clamped; an unknown
  id is "before the first", as `kNoGroove` is.
- The lanes are in the project as always, so a project naming a user groove this machine lacks
  still PLAYS what was saved — the rule `activeProfile`/`activeGroove`/the IR path already follow.

**Processor API** (message thread; `JUCE_ASSERT_MESSAGE_THREAD`):
- `saveUserGroove(name) → Result`: snapshots the current lanes + feel; on success the state becomes
  `user/<new id>`, pristine — it now IS that groove.
- `overwriteUserGroove() → Result`: only when the state is `user/<id>` with `id` in the library;
  writes the current lanes + feel into it; state becomes pristine.
- `loadUserGroove(id)`, `renameUserGroove(id, name)`, `deleteUserGroove(id)`. Deleting the ACTIVE
  groove marks the state dirty: its lanes are no longer a library groove.
- `userGrooves()` (the rescanned bank, for 18-02's UI).

`processBlock` is untouched: every new path runs on the message thread and publishes through the
existing pattern-state handle.

## Purpose
- **ROADMAP Phase 18:** "Save the current groove under a name, globally … Rename, overwrite,
  delete". 18-02 puts it on screen.
- **Phase 19** imports and exports this same file format.

## AC-1: The file round-trips, and only a valid file loads
```gherkin
Given a snapshot with all 32 slots of all 8 lanes set to distinct values 0–127, a non-ASCII name and non-default feel
When it is saved and the folder rescanned
Then the loaded groove equals the snapshot exactly, the file is <id>.forrogroove, and the id is a UUID
And each malformed variant (bad root, version 2, missing lane, duplicate lane, unknown lane, 31 steps, value 128, id ≠ filename, empty name) is skipped and reported while the valid files beside it still load
```

## AC-2: Save, rename, overwrite, delete
```gherkin
Given an empty library in a redirected test folder
When three grooves are saved ("b", "A", "c"), one renamed, one overwritten and one deleted
Then the bank order is by name case-insensitively, a rename keeps the id and the file name, an overwrite replaces content without changing id or name, a delete removes the file, and an invalid name or unknown id returns a failing Result with nothing written
And a second library instance on the same folder sees every change after rescan()
```

## AC-3: The USER profile plays, names and cycles
```gherkin
Given a library with two grooves
When the processor saves the current groove as "Meu Xote", then loads the other, then cycles both ways
Then the state is activeProfile "user" with the right id and dirty false, the lanes and bpm/swing/cachaça match the file, slots are PAT 01, timbre and mutes are unchanged, activeGrooveName returns the name, and the cycler clamps at both ends of the sorted bank
And under a regional profile, activeGrooveName and cycleGroove behave exactly as before (the existing tests pass unchanged)
```

## AC-4: A user groove survives the host, and its absence costs nothing
```gherkin
Given a state playing a user groove
When getStateInformation/setStateInformation round-trip it
Then activeProfile/activeGroove/lanes come back verbatim
And when that id is not in the library (deleted, or another machine), the lanes still play, the name is empty, and either cycler arrow loads the bank's first groove
And deleting the active groove marks the state dirty
```

## AC-5: Nothing reaches the audio thread
```gherkin
Given the allocation and lock checks the suite already runs on processBlock
When the suite runs with this plan's tests
Then they pass unchanged, and no new code is reachable from processBlock
```
