<objective>
## Goal
**The change.** `ValueScreen::paint` computes the value's baseline as
`type::baselineIn (style, area)`, and the suffix's as `type::baselineIn (suffixStyle, area)`. Each
row's baseline comes from its own font metrics, as `drawTracked` does everywhere else.
`ValueScreen::kBaselineFromCentre` (0.35) is deleted, and so are the comments that point at it.

**What it moves.** The 08-04 record measured `globalKnobName`: the real baseline is centre +
2.576 px, and 0.35 gives centre + 3.325, so text moves ~0.75 px UP on a 9.5 px row.
- Today the error is common-mode across a value and its suffix, which is why it was left. It is
  still a third spelling of the rule.
- Apply measures the shift for every style a `ValueScreen` uses: the BPM readout, the preset
  screen, and the global knob readouts.

**The visual checkpoint.** `ValueScreen` was approved at three checkpoints. This is a pixel change to
it, so the plan STOPS for the user:
- **Before:** the current reference renders, saved before the change.
- **After:** the same renders regenerated.
- **Compared:** a side-by-side crop of every readout, magnified, before against after, in both
  themes.

## Purpose
- **ROADMAP Phase 14:** "`ValueScreen`'s `kBaselineFromCentre` → `type::baselineIn` — a pixel
  change to a component approved at three checkpoints, so it carries its own visual checkpoint".
- **The 08-04 deferral:** "a third spelling of the same idea that is 0.75 px out for a 9.5 px row …
  belongs in a plan that can re-approve it." This is that plan.
- **v0.2's "no audible change" constraint:** unaffected. This is visual only.
