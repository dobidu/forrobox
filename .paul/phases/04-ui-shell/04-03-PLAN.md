<objective>
## Goal

Build the **step pad** — the phase's second headline component — with every static visual state the
spec gives it, and the **button family and fader** that finish the channel strip. When this closes,
every box `ChassisLayout::StripLayout` reserves is filled, and `MUTE`, `SOLO` and `GHOST PROB` drive
real parameters.

## Purpose

ROADMAP's Phase 4 goal is "the two components that carry most of the look built and reusable". The
Knob was one; the step pad is the other, and Phase 5's entire grid is 80 instances of it.

The strip is the other half. 04-01 reserved its twelve boxes and 04-02 filled one; leaving the rest
empty through another plan means 04-04 inherits a strip that still does not read as the prototype.

## Output

- `src/StepPad.{h,cpp}` — off / on-with-velocity / ghost / beat / hover / pressed
- `src/Button.{h,cpp}` — one component, three variants: base, mute/solo, arrow
- `src/Fader.{h,cpp}` — track, fill, thumb; click-to-jump and drag
- The strip's remaining five boxes filled, with `mute`, `solo` and `ghost` attached
- `scripts/verify-geometry.py` extended to every new design constant, in the same commit
</objective>

## AC-1: The pad's six static states are distinguishable, and each is the spec's

```gherkin
Given a StepPad rendered headlessly in both themes
When it is set to each state — off, on at full velocity, on at low velocity, ghost, beat, hover
Then each renders differently from every other, measured rather than asserted by eye
And an OFF pad carries the recessed treatment: a 180-degree linear gradient plus the inset shadows
And an ON pad carries the backlit radial gradient in its instrument colour
And opacity encodes velocity as 0.32 + (vel/127) x 0.68, so a low-velocity pad is measurably dimmer
  than a full-velocity one in the SAME colour
And a ghost pad renders as OFF plus a 3 px centred dot in the instrument colour
```

**Why "distinguishable" is the load-bearing word.** Six states drawn by one `paint` is six chances
to draw the same thing twice. 04-02's arc instrument had to be proved to separate unipolar from
bipolar before any polarity claim rested on it; the same applies here, and the pairwise comparison
is the assertion, not a per-state threshold.

## AC-2: The backlit gradient is an ELLIPSE with an offset origin

```gherkin
Given an ON pad, which is wider than it is tall
When its lit area is measured
Then the brightest point sits at 22% of the pad's height from the top, not at its centre
And the gradient is wider than it is tall — its horizontal falloff is slower than its vertical one
And the pad's rounded rectangle is NOT distorted by whatever produces that ellipse
```

**Settled at planning, because JUCE cannot express it directly.** The spec is
`radial-gradient(120% 100% at 50% 22%, ...)` (css:630) — an ellipse with `rx = 1.2 x width`,
`ry = 1.0 x height`, centred at `(50%, 22%)`. `juce::ColourGradient`'s radial mode is **circular**:
`point1` is the centre and `point2` sets one radius. Verified in
`~/JUCE/modules/juce_graphics/colour/juce_ColourGradient.h:67`.

The resolution: `juce::FillType` carries its own `transform`
(`juce_FillType.h:154`), applied to the GRADIENT and not to the shape. So build a circular gradient
of radius `ry` about `(0.5w, 0.22h)` and give the fill
`AffineTransform::scale (rx / ry, 1.0f, centreX, centreY)`. For a 40x26 pad that is a radius-26
circle stretched 1.846x in x — an ellipse, with the pad's corners untouched.

**Do not** reach for `Graphics::addTransform`: that transforms the context, so it would stretch the
rounded rectangle too.

## AC-3: The button family is one component with three variants


## AC-4: MUTE, SOLO and GHOST PROB drive real parameters

```gherkin
Given the strip's buttons and fader attached to the APVTS
When MUTE is clicked
Then the mute parameter toggles, the host sees one complete gesture, and the button's lit state
  follows the PARAMETER rather than a bool the button kept for itself
And SOLO behaves the same on its own parameter
And dragging or clicking the GHOST PROB fader moves the ghost parameter, absolutely positioned from
  the track rect as controls.js:232-247 does it — NOT with the knob's (dy/160) drag law
And a parameter changed from outside repaints all three without writing back
```

**The fader's law is deliberately NOT the knob's.** `controls.js:232-247` computes the value from
the pointer's position within the track rectangle — click-to-jump, and a drag is the same
computation repeated. There is no `/160`, no shift-fine and no wheel. Three controls in this
project, three different laws; unifying them would be wrong.

## AC-6: Every new design constant is cross-checked, against the file that carries it

```gherkin
Given the constants this plan adds — pad height, radius, gap, the gradient stops, the button
  paddings and borders, the fader track and thumb
When scripts/verify-geometry.py runs
Then each is compared against the source file that declares it, and a mutation to any one of them
  fails the build naming the constant
And each is added in the SAME commit as the constant itself
```

**This is 04-02's most expensive lesson, applied forward.** `verify-geometry.py` was written to
close "a C++ test cannot police a constant it also consumes", then shipped policing only
`forrobox.css` while the knob's five identity numbers sat unread in `controls.js`. Check which file
carries each constant: the stylesheet has the pad's gradients, shadows and the button box model;
`controls.js` has the fader's track/thumb geometry.
