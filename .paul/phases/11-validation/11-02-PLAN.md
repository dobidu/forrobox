<objective>
## Goal
`DragMidiButton` hands its file to the OS through a hook whose default is exactly today's call,
`juce::DragAndDropContainer::performExternalDragDropOfFiles (files, false, this, callback)`.
UiTest's drag-export check installs a fake. The suite therefore never starts a real OS drag, and
`shutdownJuce_GUI` returns.

## Purpose
- **The hang blocks the Windows build.** `build-windows.sh` has been red three runs out of three
  since this morning, so the pluginval step 11-01 wired in is unreachable.
- **It's the milestone's oldest open question.** Phase 10's hang had been "environmental, not
  reproduced" since 09-06.
- **The mechanism, measured at 11-01 APPLY and confirmed at planning:**
  - `~ScopedJuceInitialiser_GUI` → `DragAndDropHelpers::ThreadPoolHolder::~ThreadPoolHolder` →
    `ThreadPool::removeAllJobs (true, -1)`. JUCE's comment there: "Wait forever if there's a job
    running."
  - The job is the OLE `DoDragDrop` started when `UiTest.cpp:7649` drives the button past its
    8 px threshold.
  - **Disabling that one `mouseDrag` made `shutdownJuce_GUI` return on 3 of 3 MSVC runs**, where it
    had hung on 4 of 4. The only failure was the check that needed the drag.

## Output
- The hook on `DragMidiButton`, whose default is unchanged, so production behaviour is identical
- The test hands off to a fake. It gains coverage the real OS drag never gave it: the exact path
  handed over, the completion callback, and the refusal path
- `build-windows.sh` reaches its pluginval step, which closes 11-01's AC-3 gap
</objective>
