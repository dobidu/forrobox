<objective>
## Goal
Every cross-check gate declares what it reads **in one place, inside the script**. CMake takes its
DEPENDS from that declaration instead of a hand-kept list, and at run time the gate **fails** if it
opened any file in the repository that it did not declare. The class of bug called "the gate reads
a file the build doesn't know about" stops being possible to reintroduce silently.

## Purpose
This is the most-repeated defect in the project's record: six instances fixed one at a time across
06-05, 06-06, 08-01, 09-01 and 09-02, each found late, each by a review rather than by the build. A
gate that doesn't re-run when its input changes is the exact failure the gates exist to prevent: a
wrong digit that produces no crash, no failed build and no failing test.

## Output
- `scripts/gate_inputs.py`: `declare(files=…, globs=…)`, a `--list-inputs` mode, and a run-time
  audit that compares what was read against what was declared
- All six gate scripts declaring their inputs through it
- `forrobox_add_verify_target` deriving DEPENDS from `--list-inputs`; every hand-kept list, and
  `verify-geometry`'s regex scrape and its length floor, deleted
- The three live gaps closed as a consequence, not by hand
</objective>

## Measured at planning, 2026-09-25
Each gate was run under a Python audit hook that recorded every repository file opened for
reading; build dirs and `__pycache__` were excluded. The result was compared with its CMake DEPENDS.

| Gate | Reads | Declared? |
|---|---|---|
| `verify-theme` | `app.js`, `forrobox.css`, `src/Theme.h`, `src/Theme.cpp`, **`src/EffectOverlay.cpp`** | EffectOverlay.cpp **missing** |
| `verify-profiles` | `profiles.json`, `data.js`, `Profiles.cpp`, `Profiles.h`, `MixBus.h`, `ParameterIDs.h` | complete |
| `build-profiles --verify` | the same, plus the standalone HTML | complete |
| `verify-geometry` | `app.js`, `controls.js`, `forrobox.css`, 19 headers incl. `Typography.h` | complete (scraped) |
| `verify-charset` | 111 `src/` files, 13 `tests/` files, **9 `assets/fonts/*.ttf`** | fonts **missing** |
| `verify-midi` | `profiles.json`, `ParameterIDs.h`, **`MixBus.h`, `Profiles.h`** (through its `verify-profiles` import) | MixBus.h, Profiles.h **missing** |

Two limits of that probe, which carry into the design:
- **Imports via `importlib` don't raise an `open` audit event.** `build-profiles` and `verify-midi`
  load `verify-profiles.py` that way. The module file itself was not seen; the files it reads
  were. Enforcement must also walk `sys.modules` for module files under the repo.
- **A child process's reads are invisible.** `verify-midi` runs Node on `verify-midi.js`, which reads
  `audio.js` and `data.js`. Those stay declared by hand in the script, next to a comment saying why.
  They are the only inputs that can't be enforced.

## Decision taken with the user at planning
**Declared + enforced**, over the regex scrape the Deferred Issues entry named. A scrape of
`verify-midi.py` can't see what its imported module reads, and nothing would detect a miss.

## AC-1: One declaration per gate
```gherkin
Given any of the six gates
When its script is run with --list-inputs
Then it prints every repository file it reads (and every glob it scans) and nothing else
And that output is the ONLY place its inputs are written down: CMakeLists.txt names no input file for any gate
```

## AC-2: CMake depends on exactly the declaration
```gherkin
Given a configured build
When any declared input of any gate is touched (including the three that were missing:
     src/EffectOverlay.cpp, src/MixBus.h / src/Profiles.h for verify-midi, and an assets/fonts/*.ttf)
Then the next build re-runs that gate — shown by the build tool, not inferred
And adding a file under a declared glob re-runs the gate without a manual reconfigure
And editing a script's declaration re-configures on the next build
```

## AC-3: An undeclared read fails the gate
```gherkin
Given a gate that opens a repository file missing from its declaration
     (a throwaway mutation, never committed)
When the gate runs
Then it exits non-zero and names the undeclared file
And a gate whose declaration is complete passes exactly as before
And a module loaded through importlib counts as a read
```

<task type="auto">
  <name>Task 1: gate_inputs.py — declare, list, enforce</name>
  <files>scripts/gate_inputs.py (new)</files>
  <action>
    A small stdlib-only module, imported by every gate:
    - `declare(root, files=[...], globs=[(dir, pattern), ...], unobservable=[...])` records the
      declaration. `unobservable` holds inputs read by a child process (Node), declared but
      exempt from enforcement, with the reason carried at the call site.
    - Handle `--list-inputs` at declaration time: print one line per input, `file <abs path>` or
      `glob <abs dir> <pattern>`, then exit 0 without running the checks. The gate's own argument
      parser must not see or reject the flag; strip it before the script parses argv.
    - Otherwise install `sys.addaudithook` capturing `open` events in read mode, and register an
      `atexit` check. At exit, collect repository files read, plus `__file__` of every module in
      `sys.modules` under the repo (importlib reads raise no `open` event, measured at planning).
      Exclude build directories (any top-level dir containing a `CMakeCache.txt`), `__pycache__`,
      the gate script itself and `gate_inputs.py`. Any file not covered by a declared file or glob
      → print `UNDECLARED INPUT: <path>` and force a non-zero exit **even if the gate passed**.
      A gate that already failed keeps its own failure code.
    - Force the exit from `atexit` with `os._exit` only after flushing stdout/stderr. `sys.exit` is
      ignored inside atexit. Say so in a comment.
    - Write-mode opens are NOT reads: `build-profiles` without `--verify` writes its outputs.
    Avoid: third-party imports; any change to what a gate checks; scanning outside the repo
    (stdlib, fontTools); treating a write as a read.
  </action>
  <verify>
    A throwaway test script in the scratchpad that declares one file and reads two: it exits
    non-zero and names the second. With both declared it exits 0. `--list-inputs` prints both lines
    and runs nothing (a print in its body doesn't appear).
  </verify>
  <done>AC-3's mechanism exists and is proven on a case it must reject</done>
</task>
