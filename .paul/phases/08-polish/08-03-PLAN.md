<objective>
## Goal

The gear menu's fifth item works. IBM Plex Mono, JetBrains Mono and Space Mono are all selectable,
the choice survives a restart like the other four, and every mono glyph in the chassis redraws in
the chosen family. `Face::monoSemiBold` — embedded since 04-01 and asked for by nothing — is deleted.

## Purpose

`PLANNING.md:860` lists three display fonts and `PLANNING.md:885` calls two of them optional.
08-02 declared the setting, built its store entry and left its menu band free; nothing reads it.
That is the one deliberate gap in the settings menu, and closing it finishes Phase 8's third scope
item.

## Output

- Two more mono families in `assets/fonts/`, built reproducibly by the existing script
- A mono face that resolves through the CURRENT family rather than a fixed table
- One fewer embedded weight than before this plan started

  <files>scripts/build-fonts.py, assets/fonts/, CMakeLists.txt</files>
  <action>
    Extend `scripts/build-fonts.py` to fetch and build:

    - **JetBrains Mono at 400 and 500.** Published as a VARIABLE font only
      (`JetBrainsMono[wght].ttf` — confirmed at 08-02 planning against google/fonts), which is 04-01's
      Space Grotesk situation exactly. Instance it offline with the machinery already in this script
      and patch the name records, because `instantiateVariableFont` leaves name ID 1 naming the
      source's default instance for every weight — that is trap 2 in this file's own docstring and it
      is silent.
    - **Space Mono at 400 only.** It ships real statics (Regular, Bold and their italics) and is NOT
      variable, so 400 is used as fetched. Its 500 is handled in Task 2, not here — do not synthesise
      a weight, and do not instance a font that has no axes.
    - **DELETE IBM Plex Mono SemiBold.** `Face::monoSemiBold` is registered in `Typography.cpp`'s
      resource table and no row of `typeSpecs` asks for it. Confirmed with the user at planning.

    GENERALISE `instance_space_grotesk` RATHER THAN COPYING IT. It is already "instance a variable
    font at a weight and fix its name table"; a second copy for JetBrains Mono is the duplication
    every cross-check in this repo exists to prevent, and the two would diverge at the first fix.

    REPORT GLYPH COVERAGE FOR EACH NEW FAMILY against the 36-character repertoire
    `verify-charset.py` pins, not against a guess. 04-01 already recorded that neither shipped font
    carries U+266A; a family that cannot draw `Ó`, `Â`, `Á` or `Ç` would render the Portuguese UI as
    boxes the moment it was selected, and nothing else in this plan would notice. If one is missing a
    glyph this UI draws, STOP and report it — that is a spec decision, not an implementation detail.

    `--verify` must pass: every committed file re-derived byte-identically. 04-01 found the four
    instanced files were not reproducible until `recalcTimestamp = False`; that lesson is in the
    script and must survive this edit.
  </action>

    python3 scripts/build-fonts.py --check     (offline, against the manifest digests)

  </verify>

<task type="auto">
  <name>Task 2: The mono face resolves through the current family</name>
  <files>src/Typography.h, src/Typography.cpp, src/Settings.h</files>
  <action>
    Today `typefaceFor (Face)` indexes one flat table and caches one `Typeface::Ptr` per face. Make
    the MONO faces resolve through the family the user chose; the four sans faces are untouched,
    because `--sans` is not a setting.

    ONE TABLE, TWO DIMENSIONS, and the same law `ids::channelInfos` and `settings::infos` follow:
    family × weight in one array of structs so a family cannot be added without its weights. Space
    Mono's 500 entry points at its 400 FILE — that is where AC-3 lives, and the comment there carries
    the reason: CSS Fonts 4 §5.2 resolves a 500 request against {400, 700} by walking DOWN to 400, so
    this is the prototype's own answer and not a substitution this plan invented.

    THE CACHE IS THE TRAP. It is a `static std::array` keyed by face alone; keyed that way, switching
    family returns the previous family's typeface forever. Key it by family AND face, or clear it on
    change — and whichever is chosen, prove it by switching twice and back, because a cache that is
    merely cleared on the FIRST change looks correct until the second.

    DELETE `Face::monoSemiBold` and its resource row. `kNumFaces` is derived from the enum, so the
    arrays follow; check that nothing indexes the table by a literal.

    DO NOT read `Settings` from inside `Typography`. The type system is a leaf that the whole UI
    depends on, and making it reach a global store would put a file open behind every glyph — 08-02
    measured `Settings::get` at 12.4 µs. The family is PUSHED in, the way the LookAndFeel's mode is.
  </action>
  <verify>
    cmake --build build-linux --target ForroBoxTests -j8 && (unset DISPLAY; ./build-linux/ForroBoxTests)
    Checks: each family renders text; the three families are mutually DISTINGUISHABLE by ink mass,
    which is 04-01's instrument and the reason advance width was rejected; switching twice and back
    returns the original render exactly; Space Mono's monoMedium is its monoRegular typeface.
    Then run `/code-review` on the diff.
  </verify>
  <done>AC-2, AC-3, and the code half of AC-5</done>

## DO NOT CHANGE

- **The four SANS faces.** `--sans` is not a setting; Space Grotesk stays as 04-01 built it.
- **The type scale.** Which weight each row asks for is `PLANNING.md`'s table, cross-checked by
  `verify-geometry.py`. This plan changes which FAMILY supplies a weight, never which weight a row
  asks for.
- **`scripts/build-fonts.py`'s reproducibility machinery** — `recalcTimestamp = False` and the
  explicit name-record writes. 04-01 found both the hard way and both are load-bearing.
- **Everything 08-02 shipped.** The store, the gear, the menu's other four bands, the ABOUT panel.
- The 46 parameter IDs. A display font is a preference, not a parameter.

## SCOPE LIMITS

- **No font subsetting.** 04-01 recorded ~788 KB embedded and no subsetting; this plan changes the
  count by two families and one deletion and does not open that question.
- **No `♪ NO PONTO` glyph work.** U+266A is the `CACHAÇA` easter egg's problem, and that is a
  different plan in this phase.
- **No new settings.** Five, from one table, as `PLANNING.md:855-862` lists them.
- **No Ciclotron™ treatment, no easter egg.** The rest of Phase 8.
