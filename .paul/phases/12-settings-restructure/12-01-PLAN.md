<objective>
## Goal
Two structural moves, with no behaviour change:
- **`SettingsMenu`** owns the menu: the `SettingsMenuId` bands, `kAccentSteps` and their
  `static_assert`s, `build (const Settings&)`, and `apply (int id, Settings&) -> Result`
  (`dismissed`, `changed`, `about`, `unknown`). It also exposes named ids (`themeItem (i)`,
  `radiusItem (i)`, `accentItem (i)`, `stepsItem (i)`, `fontItem (i)`, `aboutItem`), so the tests
  stop typing `300 + 3`.
- **`settings::applyTo (LookAndFeel&, const Settings&)`** sets the theme, corner radius, accent and
  mono family: everything `applyStoredSettings` does except the repaint. The chassis keeps
  `repaintAll()`. The editor calls `applyTo` itself, because it owns the LookAndFeel. The menu path
  is: `apply → changed → applyTo + repaintAll`.

## Purpose
- ROADMAP Phase 12: "the settings menu lives in its own unit, and the tests stop transcribing its
  id table".
- **Measured:** 23 call sites in `UiTest.cpp` pass literal ids (`100`, `101`, `200`, `300 + 3`,
  `400`, `500`, `900` …). A renumbered band would silently retarget them.
- Phase 13's broadcast lands in exactly these seams (`applyTo` is what a second instance will
  call).

## Output
`src/SettingsMenu.{h,cpp}`; a `Chassis` that delegates; the editor using `applyTo`; tests on
named ids.
</objective>

## Measured at planning (2026-10-01)
- Ids are banded by index (`kSpan = 100`), with `static_assert`s on every band boundary and on
  the accent floor and ceiling. These move with the enum, not into the tests.
- `applySettingsMenuResult` returns bool, and each branch bounds-checks its own band (/code-review,
  08-02). The `Result` enum keeps that: an id outside every band is `unknown`, never a wrong write.
- Callers of `applyStoredSettings`: the editor's constructor and one test (`UiTest.cpp:15646`).
- The literal ids `0` (dismissal) and `55` (unknown) in the tests are DELIBERATE and stay literal:
  they test ids the menu never offers.
