<objective>
## Goal
One script fetches pluginval v1.0.4 and pins it by SHA-256. It runs the validator at strictness 10,
GUI tests included, on the Linux Debug VST3, the Linux Release VST3 and, from `build-windows.sh`,
the shipped Windows Release VST3. The verdict is its own and never pluginval's alone: a run FAILS on
a non-zero exit, on any failed test, on any `JUCE Assertion failure`, or on any `*** Leaked objects`
line.

## Purpose
ROADMAP's Phase 11 goal: "a real plugin validator passes on the VST3, repeatably". It's also why
Phase 11 comes before the settings restructure: pluginval should guard every later change.
**Measured at planning:** pluginval exits 0 and prints `SUCCESS` on a Debug build that logs 500
bypass-latency assertions and a Typeface leak at unload. A gate that trusts pluginval's own verdict
would be the check that cannot fail, the pattern this project has had to reject in every phase.

## Output
- `scripts/validate-plugin.sh`
- `build-windows.sh` runs it on the shipped Windows binary
- **The gate lands RED on Linux Debug, by design.** It fails on exactly the two findings that
  11-02 (bypass latency) and 11-03 (the Typeface leak) exist to fix. That red is the gate's proof
  that it can fail on something real.
</objective>

<task type="auto">
  <name>Task 1: scripts/validate-plugin.sh — fetch, pin, run, judge</name>
  <files>scripts/validate-plugin.sh</files>
  <action>
    - Bash with `set -euo pipefail`, like build-windows.sh. Constants: the version, both URLs and
      both pinned hashes. `fetch_pluginval <linux|windows>` downloads into
      `build/tools/pluginval-1.0.4/`, runs `sha256sum -c`, and refuses on a mismatch, deleting the
      bad zip. It then unpacks the zip and caches the result by hash.
    - `judge <log> <exit>` does the AC-2 rules in one place. It strips `\r` first, because the
      Windows log has CRLF endings. It prints a verdict block: target, strictness, seed, GUI
      on/off, PASS/FAIL, and for a failure each assertion `file:line` with its count and each leak
      line.
    - `validate <label> <vst3-path> <runner...>` runs `pluginval --strictness-level 10
      --timeout-ms 300000 --validate <path>` with `--skip-gui-tests` only when it was asked for.
      The output goes to a file, never a pipe (08-02's finding in build-windows.sh), and the real
      exit code is read with `|| rc=$?`.
    - Default mode: configure `build-debug` if it is missing (Ninja, Debug, `JUCE_PATH` read from
      build-linux's cache), build `ForroBox_VST3` in build-debug and build-linux, validate both,
      and exit non-zero if either failed. Then `--windows <C:\ path>` mode: copy `pluginval.exe` to
      `/mnt/c/Users/$WINUSER/forrobox-tools/` (the user is derived the way build-windows.sh already
      derives its paths), run it through interop, judge.
    - `--help` like build-windows.sh. Avoid: grepping for `SUCCESS` as the pass signal (measured to
      lie), and piping pluginval into `tee` (08-02).
  </action>
  <verify>
    `scripts/validate-plugin.sh`: Linux Release PASS; Linux Debug FAIL listing `juce_AudioProcessor.cpp:599 ×N` and the three leaked classes; overall exit 1.
    Run again: no download (cache hit). `git status` clean.
    Mutations: corrupt one byte of the cached zip → refused; a non-existent VST3 path → FAIL via exit code; unset DISPLAY → fails asking for --skip-gui.
  </verify>
  <done>AC-1, AC-2 and the Linux half of AC-3 and AC-4</done>
</task>
