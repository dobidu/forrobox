<objective>
## Goal

The per-strip `LOAD` button stops being the last stub. It opens a file browser, loads a user sample
for that channel, shows its name on the strip, and accepts a file dragged onto the strip. The path
persists; a sample that has moved falls back to the built-in voice.

## Purpose

`PLANNING.md:840` specifies it and no phase ever owned it — it was a ROADMAP gap found at 09-05
planning. It is the last ⬜ row in the README's feature table besides MIDI input, and five `LOAD`
buttons that visibly press and do nothing are what a reviewer sees first.

## Output

- `UserSamples` — one loaded sample per channel, published to the audio thread safely
- `LOAD` wired: file browser **and** drag-and-drop onto the strip
- The strip's name shows the loaded file; the built-in name returns when it is cleared
- Paths persist per channel, validated and degrading like 09-07's IR

<decisions>
## The bateria strip's `LOAD` targets CAIXA, following the rule already in the code

Bateria is one channel with four lanes. One sample across all four would make `BB`, `CX`, `HH` and
`TOM` identical, which is not a kit.

`PatternPads.h:88-90` already settles the shape: *"The composite BATERIA row … edits caixa (cx) —
the backbeat; deep edits live in the kit view."* The strip's `LOAD` follows the strip's own editing
rule. Per-piece sample loading would belong to the kit overlay, which `PLANNING.md:840` does not
describe, so it is out of scope rather than invented.

## A user sample REPLACES the channel's voice

`voiceSpecs[lane].usesSample` already splits `scheduleSample` from `scheduleSynth`
(`VoiceEngine.cpp:303`). A loaded sample makes that lane sampled for as long as it is loaded — it
replaces the synthesised voice, or for zabumba the three-layer `ZabumbaSampler`. Velocity scales it;
the zabumba's measured velocity layers are specific to those files and do not generalise.

Clearing returns the built-in voice, which is what makes the feature reversible without a reload.

## Every hazard 09-07 hit applies here, and the answers are already decided

That plan's `/code-review` found three HIGH, two of them live audio-thread defects. This one loads
files into buffers the audio thread reads, which is the same shape with five of them:

- **Never free a buffer the audio thread may be reading.** 09-07's answer was never destroy, gate
  with an atomic. Here the buffers are per channel and can accumulate over a session, so use the
  project's own handover instead: a double buffer with an atomic index, the shape `PatternSnapshot`
  has used since 02-04. The plan requires the lifetime argument written down where the swap happens.
- **Publish complete objects only.** The index flips AFTER the buffer is filled, release-ordered.
- **Validate the path is absolute** before it becomes a `juce::File` — a Windows path opened on
  Linux asserts in `parseAbsolutePath` on every load.
- **Refuse a file no reader can open.** `existsAsFile()` is not "is audio"; an mp3 renamed `.wav`
  must fail loudly, not silently produce nothing.
- **Tell the user when a load fails**, the way `DragMidiButton` does and 09-07's chooser now does.

## Drag-and-drop is specified, so it is built

`PLANNING.md:840`: *"Should accept drag-and-drop onto the strip."* The strip becomes a
`juce::FileDragAndDropTarget`. It must accept only what it can load — highlighting a strip for a
file that will then be refused is the dishonest kind of affordance.
</decisions>

When it is chosen, or dragged onto a strip

  <action>
    **`UserSamples`** — one decoded buffer per channel, resampled to the host rate at load time so
    `process` never resamples. Loading is message-thread only and builds a reader to prove the file
    is audio before accepting it.

    **The handover.** A double buffer per channel with an atomic index, the shape `PatternSnapshot`
    has used since 02-04: fill the inactive slot, then flip the index with release ordering. Write
    the lifetime argument down where the swap happens — specifically, why the slot being overwritten
    is safe to reuse. If it is not provably safe, say so and use 09-07's never-free instead.

    **The engine hook.** `VoiceEngine.cpp:303` already branches on
    `voiceSpecs[lane].usesSample`. A loaded user sample makes that lane sampled regardless of its
    spec; an unloaded one falls through to the existing behaviour. Keep `scheduleSample`'s existing
    zabumba path intact — the user sample is a different source, not a replacement for the three
    measured layers.

    **Persistence.** One path per channel in `State`, written and read like `impulseResponsePath`,
    kept verbatim, validated as absolute before becoming a `juce::File`, and restored after
    `setStateInformation` releases the state lock.

    Avoid: resampling or allocating in `process`. Avoid freeing a buffer the audio thread may hold.
  </action>

    Round-trip: five paths saved and restored; one deleted file falls back to its built-in voice
    with the path kept. A text file renamed `.wav` is refused. Then mutate, asserting each on disk

<boundaries>

## DO NOT CHANGE
- `PLANNING.md`, `forrobox.css`, `controls.js`, `app.js` — READ-ONLY.
- `ZabumbaSampler`'s three measured velocity layers and its embedded files. A user sample is a
  different source; it does not replace that machinery, it bypasses it while loaded.
- `processBlock`'s allocation-free, lock-free contract.
- The kit overlay. Per-piece bateria samples are not specified; the strip's `LOAD` follows the
  strip's own caixa rule.
- Parameter and group IDs. This plan adds no parameter — a sample is state, not automation.

## SCOPE LIMITS
- No sample browser, no bundled packs, no `BUNDLE: MINIMAL` selector. `PLANNING.md:848` makes that
  conditional on more packs shipping, which is not this plan.
- No velocity layers for user samples. The zabumba's are measured from its own four files and do
  not generalise to an arbitrary WAV.
- No per-lane loading inside the bateria kit.

</boundaries>
