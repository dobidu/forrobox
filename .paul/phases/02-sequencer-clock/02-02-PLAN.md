<objective>
## Goal

Build the clock: a sixteenth-note step counter advanced from the audio block's sample position, with
swing applied to odd steps, running on internal tempo from the `bpm` parameter. It emits step events
carrying a step index and a sample offset within the block. Nothing consumes them yet — Phase 3's
voices will.

The clock is a plain class, not processor code, so it can be driven exhaustively offline with no
audio device and no host.

## Purpose

`PLANNING.md` says of the prototype's 25 ms `setInterval` lookahead scheduler: "**In the plugin,
replace this entirely** — advance a step counter from the audio block's sample position so triggers
are sample-accurate." Timing accuracy is a named success metric, and a groove is the product: a
clock that drifts, or that emits a different step sequence depending on the host's buffer size, is
not something a listening test can later diagnose. It would just sound slightly wrong.

02-01 built the tables. This advances over them. 02-03 replaces the tempo source with the host's
playhead, and that substitution is only safe if the internal path is already correct and its
correctness is mechanically pinned.

<acceptance_criteria>

## AC-1: Internal tempo produces the specified step duration

```gherkin
Given a clock prepared at 48000 Hz with bpm 120 and swing 0
When it is advanced over 48000 samples (one second)
Then exactly 8 step events are emitted (60/120/4 = 0.125 s per sixteenth)
And the Nth event's absolute sample position equals round(N x 0.125 x 48000) within 1 sample
And no cumulative drift appears over 10000 steps
```

## AC-2: The step sequence is independent of block size

```gherkin
Given two identically prepared and reset clocks at the same bpm, swing and step count
When one is advanced with a single block of 8192 samples
And the other is advanced with 8192 blocks of 1 sample, then with irregular blocks (1, 7, 3, 512, 63, ...)
Then all three produce the identical sequence of (step index, absolute sample position) pairs
```

## AC-3: Swing delays odd steps without accumulating or reordering

```gherkin
Given a clock at bpm 120, 48000 Hz, with swing set to S
When it is advanced over several bars
Then even-numbered steps land on the unswung grid position for every S in 0..100
And each odd step lands later than its grid position by round((S/100) x 0.6 x stepSamples)
And emitted absolute positions are strictly increasing for every S in 0..100
And at S = 0 every step lands exactly on the grid
```

## AC-4: A step whose swung time crosses a block boundary is emitted once, in the later block

```gherkin
Given a clock at high swing whose next odd step's swung position falls beyond the current block's end
When the current block is advanced
Then that step is not emitted in this block
And it is emitted in a later block at its correct absolute position
And it is never emitted twice, and no step index is skipped
```

## AC-5: The step index wraps over the active window, not the storage

```gherkin
Given the `steps` parameter selecting 16
When the clock runs past step 15
Then the next emitted step index is 0
And every emitted index is within [0, 16)
And with `steps` selecting 32 every emitted index is within [0, 32)
And changing the window mid-run neither drops nor duplicates a step event
```

## AC-6: Transport start and stop behave as specified

```gherkin
Given a stopped clock
When transport starts
Then the first emitted event is step 0 at sample offset 0
When transport stops
Then no further events are emitted, and the reported current step returns to the stopped sentinel
And restarting emits step 0 again rather than resuming mid-pattern
And `playing` does not survive a state save/reload — reopening a project does not auto-play
```

## AC-7: bpm and swing changes mid-stream are handled without dropping or duplicating a step

```gherkin
Given a running clock
When bpm changes between blocks (including large jumps, 40 to 300 and back)
Or swing changes between blocks
Then step indices continue in unbroken ascending order modulo the window
And no event is emitted at a position earlier than the previous event
```

## AC-8: The clock allocates nothing and locks nothing when advanced

```gherkin
Given a test translation unit counting global operator new / delete calls
When the clock is prepared (allocation permitted) and then advanced over many blocks
Then the allocation count recorded across all advance calls is exactly zero
And `processBlock` takes no lock and touches `patternState` not at all
```

## AC-9: Everything still builds and passes under all three compilers

```gherkin
Given the new sources and the second test executable
When the project is built with GCC, Clang and MSVC
Then all three build with zero warnings from our own sources
And both test executables pass, with the pre-existing 287 checks unchanged in count and outcome
And the data.js cross-check still reports 32/32 patterns matching
```

<task type="auto">
  <name>Task 2: Implement forrobox::Clock and cover it exhaustively</name>
  <files>src/Clock.h, src/Clock.cpp, tests/ClockTest.cpp</files>
  <action>
    Build `forrobox::Clock` as a plain class with no JUCE processor dependency, so tests drive it
    directly with no audio device, no host and no plugin instance.

    Surface, roughly:
    - `void prepare (double sampleRate)` — the only place allocation is permitted
    - `void reset()` — back to "about to emit step 0"
    - `advance (int numSamples, const Params& p, EventSink&)` — `noexcept`

    `Params` carries what the clock reads per block: `bpm` (int, 40..300), `swing` (float, 0..100)
    and `activeSteps` (16 or 32). Pass it in rather than having the clock reach for the APVTS, so
    the tests can drive tempo and swing sweeps without constructing a processor.

    `StepEvent` carries the step index and the sample offset within the current block. Deliver
    events through a fixed-capacity buffer the caller owns, or a non-allocating callback — your
    choice, but the delivery path must have a hard bound and must NOT silently drop an event when
    that bound is hit. Bound it by construction: process internally in chunks no larger than the
    prepared block size so the per-call event count is provably capped, rather than trusting the
    host to honour `maximumExpectedSamplesPerBlock` (some do not).

    Timing requirements:
    - Step duration in samples is `sampleRate * 60 / bpm / 4`. Keep it fractional — accumulating
      a rounded integer per step is exactly the drift AC-1 tests for.
    - Swing offsets ODD step indices only, by `(swing/100) * 0.6 * stepSamples`, and does NOT
      advance the grid. Follow `app.js:637`'s structure, not its scheduler.
    - Derive each event's position from the grid position plus the swing offset, so a mid-run
      swing or bpm change cannot corrupt the phase. A step whose swung position lands past the
      block end is pending, not lost (AC-4).
    - Wrap the emitted index over `activeSteps`, never over `State::kMaxSteps` — 02-01 settled
      that the 32 slots are storage and `steps` is a view.

    Avoid: a per-sample loop over the block (correct but needlessly O(n) on the audio thread when
    the crossing points are computable); accumulating integer step durations (drift);
    `juce::String`, logging, allocation or locking anywhere in `advance`.

    In `tests/ClockTest.cpp`, cover AC-1 through AC-8. Two cases carry most of the weight:
    - the block-size invariance sweep (AC-2), which is the strongest available test of this class
      of code: one block of N vs N blocks of 1 vs irregular partitions must agree exactly;
    - the allocation counter (AC-8): override global `operator new`/`delete` in this TU to bump a
      counter, and assert the delta across the advance calls is exactly zero.

    Per 02-01's practice: for each timing invariant, also prove the test can FAIL — break the
    clock deliberately in a scratch copy and confirm the specific case reports it. Assert the
    mutation applied before trusting the result, and restore from a backup copy rather than
    `git checkout`, which discards uncommitted work in the same file.
  </action>
  <verify>`./build-linux/ForroBoxClockTests` passes; block-size invariance holds for single/unit/irregular partitions; the allocation delta across advance is 0; each timing invariant demonstrated to fail on a deliberately broken scratch copy</verify>
  <done>AC-1 through AC-5, AC-7 and AC-8 satisfied</done>
</task>

<task type="auto">
  <name>Task 3: Own the clock in the processor and add internal transport</name>
  <files>src/PluginProcessor.h, src/PluginProcessor.cpp</files>
  <action>
    Give the processor a `forrobox::Clock`, prepared in `prepareToPlay` (the sanctioned allocation
    point), and advance it from `processBlock` with `bpm`, `swing` and `steps` read from the APVTS
    as raw atomic parameter values — not through `getParameter`-style calls that build strings.

    Add transport: a `std::atomic<bool> playing`, with `setPlaying(bool)` / `isPlaying()` for the
    Phase 4 header button, and `static_assert (std::atomic<bool>::is_always_lock_free)` alongside
    the existing pair. Starting resets the clock; stopping resets it and sets the reported current
    step to the stopped sentinel (`-1`, matching `PLANNING.md`'s `currentStep` default). When not
    playing, `processBlock` does not advance the clock at all.

    `playing` is deliberately NOT an APVTS parameter and NOT persisted:
    - not a parameter, because `PLANNING.md`'s VST3 parameter-mapping list omits it, and a play
      toggle on an automation lane would fight the host transport;
    - not persisted, because a plugin that resumes playing when a project opens is hostile. This
      differs from `dirty` and `activeProfile`, which are persisted state — record the distinction
      as a decision in the SUMMARY.

    Expose `std::atomic<int> currentStep` for Phase 5's playhead to read at frame rate. Write it
    from the audio thread with `memory_order_relaxed`; it is a display value, and a stale frame is
    invisible while a lock would not be.

    `SYNC` is read but NOT honoured in this plan: with `sync` on, the clock still runs on internal
    tempo. Say so in a comment naming 02-03, so the gap reads as scheduled rather than forgotten.

    Keep the audio-thread contract intact: `processBlock` gains the clock advance and the atomic
    store and nothing else — no allocation, no lock, no `patternState` access, no `juce::String`.
    The step events are consumed by nothing this phase; do not add voices, MIDI output or
    `CACHAÇA` jitter (Phase 3).

    Avoid: reaching into `patternState` from `processBlock` to look up what the step should
    trigger. That is the data race 02-03's double-buffer handover exists to solve, and doing it
    here through `LockedState` would take a lock on the audio thread.
  </action>
  <verify>Plugin builds under GCC, Clang and MSVC; `processBlock` contains only ScopedNoDenormals, the not-playing early return, the clock advance, the currentStep store and the existing clears; a state round-trip does not restore `playing` as true; the Windows VST3 still loads in Ableton Live 12</verify>
