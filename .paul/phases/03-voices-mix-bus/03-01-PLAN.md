<objective>
## Goal

Give the velocities a voice. Build a persistent `VoiceEngine` owned by the processor, prepared with
sample rate and block size, that turns `StepEvent` + lane velocity into rendered audio: seven
synthesised voices per `PLANNING.md`'s Voice Specifications, plus zabumba played from four embedded
one-shots, summed through per-channel gain and stereo pan with mute/solo applied.

At the end of this plan the plugin makes sound for the first time in the project.

## Purpose

Phase 3's goal is that the four profiles audibly match the prototype, verified by A/B listening
before any UI work begins. Nothing can be listened to until something renders. This plan builds the
architecture that 03-02 (`CACHAÇA`) and 03-03 (character bus, limiter, master) extend, so getting
its **lifetime** right matters more than getting the voices pretty: 02-04's altitude review recorded
that `BlockEmitter` is the right adapter and the wrong owner, and named the three features that
break a block-scoped object. All three arrive in 03-02.

## Output

- `VoiceEngine` — persistent, `prepare`/`reset`/`schedule`/`render`, no allocation after `prepare`
- Seven synth voices (triângulo, pandeiro, ganzá, bateria BB/CX/HH/TOM) as a voice pool
- `ZabumbaSampler` — four embedded one-shots, velocity-layered, resampled once at `prepare`
- Per-channel output stage: gain from `VOL`, stereo pan from `PAN`, mute/solo gating
- `BlockEmitter` reduced to `engine.schedule (lane, velocity, sampleOffset)`
- A measuring test suite that runs with no audio device, and a script that renders WAVs to audition
</objective>

<acceptance_criteria>

## AC-1: The engine is audible and sample-accurate

```gherkin
Given a prepared processor with a pattern that has one zabumba hit at step 0 and one triângulo hit at step 4
When 2 bars are rendered offline at 120 BPM, 48 kHz, in blocks of 512
Then each lane's onset in the rendered buffer falls within 1 sample of the step position the clock reports
And the rendered buffer is not silent, contains no NaN or infinity, and no sample exceeds 1.0
```

## AC-2: Each voice is the voice it claims to be

```gherkin
Given a single hit at full velocity on one lane with all other lanes empty
When the rendered buffer is measured
Then its duration, peak level and dominant frequency band match PLANNING.md's Voice Specifications
  for that lane, within the tolerances the test states
And a mutation to that voice's specified frequency or duration is detected by the assertion
```

## AC-3: Velocity, VOL, PITCH, DECAY and PAN all do what they say

```gherkin
Given one hit on one lane
When velocity is swept 1..127 with all parameters at default
Then rendered peak level increases monotonically
And raising DECAY lengthens the rendered tail, raising PITCH raises the dominant frequency,
  raising VOL raises the level, and PAN at -100/0/+100 puts the energy left/centred/right
And for the triângulo, velocity 0.55 is the boundary between the closed and open articulation:
  a hit just below it renders a short tail and one just above renders a long one
```

## AC-4: Zabumba plays the embedded one-shots, velocity-layered

```gherkin
Given the four ZAB_LOW one-shots embedded as binary data
When the plugin is prepared at 44100 Hz and a zabumba hit is rendered
Then the sample is resampled to the host rate once during prepare, not during processBlock
And a low-velocity hit selects the quiet layer and a high-velocity hit a loud one, so rendered
  peak level increases with velocity rather than jumping 20 dB between adjacent velocities
And the selection is derived from each layer's measured level, not from a hard-coded assumption
  about file order
```

## AC-5: Mute and solo gate audio, and nothing else

```gherkin
Given a pattern with a hit on every one of the five channels
When channels are muted and soloed across the full truth table
Then a muted channel renders silence; if any channel is soloed only soloed channels render;
  solo overrides mute for the soloed channel; and no combination silences everything unintentionally
And bateria's mute/solo applies to all four of its lanes (BB, CX, HH, TOM) together
```

## AC-6: The audio thread contract still holds

```gherkin
Given the allocation counter from tests/TestHarness.h armed around the render loop
When 2000 blocks are rendered with steps firing, voices stealing and samples playing
Then zero allocations are counted
And no lock is taken except the existing pattern try-lock, which the audio thread never waits on
And rendering with the pattern reader never refreshed still produces defined output
```

## AC-7: Rendering is deterministic

```gherkin
Given identical parameters, pattern and block partitioning
When the same 2 bars are rendered twice
Then the two buffers are sample-identical
And rendering the same musical span in blocks of 32 and of 2048 produces onsets at the same
  sample positions, to the partition-equality standard Phase 2 established
```

  <name>Task 1: VoiceEngine — the persistent shape, plus the seven synthesised voices</name>
  <files>src/VoiceEngine.h, src/VoiceEngine.cpp, src/Voices.h, src/Voices.cpp, src/PluginProcessor.h, src/PluginProcessor.cpp, CMakeLists.txt</files>
  <action>
    Create `forrobox::VoiceEngine` as a PERSISTENT member of `ForroBoxAudioProcessor`, not a
    block-scoped object. Interface:

      void prepare (double sampleRate, int maxBlockSize);   // allocates; called from prepareToPlay
      void reset() noexcept;                                // silences all voices
      void schedule (int lane, std::uint8_t velocity, int sampleOffset) noexcept;
      void render (juce::AudioBuffer<float>& buffer, const ChannelParams& params) noexcept;

    `schedule` places a trigger; `render` produces the block. Both are `noexcept` and allocate
    nothing. Voice storage is a fixed pool sized at `prepare` — pick the size from the worst case
    the grooves actually reach (eight lanes firing on the same step, each voice's longest specified
    duration at maximum `decayScale`, at the slowest supported BPM) and write that arithmetic down
    as a comment next to the constant. On exhaustion, steal the oldest voice on the SAME lane
    before stealing across lanes, so a busy ganzá cannot cut the zabumba.

    Why persistent, recorded at 02-04's altitude review and not to be relitigated: `CACHAÇA` timing
    jitter in 03-02 can place a trigger AFTER the end of the block that scheduled it, and RNG,
    smoothers, the character bus and the limiter are all `prepareToPlay` lifetime. A stack object
    destroyed at block end has nowhere to carry either.

    In `src/Voices.h/.cpp` implement the seven synthesised voices from PLANNING.md's Voice
    Specifications table — triângulo, pandeiro, ganzá, bateria BB, CX, HH and TOM. Zabumba is NOT
    here; Task 2 owns it. Transcribe the numbers from the spec table; do not invent, round or
    "improve" them, and do not read them out of `audio.js` (a sound-design sketch, per PROJECT.md).
    Use `juce_dsp` for the filters (`juce::dsp::StateVariableTPTFilter` or IIR) rather than
    hand-rolling biquads. The triângulo's five detuned squares need a per-hit random detune of
    ±0.5%: take it from an RNG owned by the ENGINE, seeded once at `prepare`, never a static or a
    thread_local — the engine is where per-hit randomness will live in 03-02 anyway.

    The triângulo's velocity split (`v > 0.55` → long, else short) is called "the instrument's
    defining behaviour" by the spec. Implement it as a duration decision at trigger time.

    Then wire it into `processBlock`: reduce `BlockEmitter::stepTriggered` to keeping the existing
    UI atomics (`lastStepVelocities`, `currentStep`, `emittedSteps` — do not change their ordering,
    it is load-bearing and Phase 5 depends on it) plus one `engine.schedule (lane, velocity,
    event.sampleOffset)` call per non-zero lane. `render` is called ONCE per block, after the
    `clock.advance` loop, never from inside `stepTriggered`.

    `event.sampleOffset` has never been exercised by anything — Phase 2 read only `event.step`. Pass
    it through and let AC-1 be the first thing that ever checks it.

    Avoid: DSP inside `stepTriggered` (it interleaves synthesis with step placement and is the shape
    02-03's review already removed once); a mutable member set before `advance` and read in the
    callback (`/simplify` deleted one of those twice); `std::rand`, `juce::Random::getSystemRandom()`
    or any shared RNG; `juce::String` or logging anywhere in `render`.

    Update `CMakeLists.txt` to compile the new sources into both `ForroBox` and the test target.
  </action>

  <action>
    Give the zabumba the sampled voice the hybrid decision chose. Only the four `ZAB_LOW_*.wav`
    one-shots enter the repository — roughly 450 KB total. The four tempo-locked loops
    (`ZABUMBA_BPM_90_4_BARS_01`, `TRIANGULO_BPM_90`, `GANZA 02 104`, `PANDEIRO 01 104 DRY`) stay
    out: they are 9.5 MB of fixed 4-bar performances that cannot carry per-step velocity.

    Extract from `/mnt/d/temp/forrobox/FORRO BOX SAMPLES.zip` into `assets/samples/`. Write
    `assets/samples/README.md` recording provenance (user-supplied 2026-09-07), the measured
    properties of each file, and that the loops were deliberately excluded and why. Embed the four
    via `juce_add_binary_data` and link the resulting target — do NOT load from a filesystem path at
    runtime, which would break the moment the plugin is installed anywhere but this machine.

    Measurement first, then code. These four are NOT interchangeable round-robin variants, which is
    what STATE.md currently records. Measured 2026-09-08, 48 kHz / 24-bit / true stereo (not
    dual-mono):

      | File         | Length  | Peak       | RMS   |
      |--------------|---------|------------|-------|
      | ZAB_LOW_01   | 0.498 s | -3.1 dBFS  | 0.196 |
      | ZAB_LOW_02   | 0.457 s | -2.5 dBFS  | 0.122 |
      | ZAB_LOW_03   | 0.344 s | -2.0 dBFS  | 0.037 |
      | ZAB_LOW_04   | 0.265 s | -23.1 dBFS | 0.018 |

    Peaks cluster within 1.1 dB across 01-03 and then fall 20 dB at 04, while RMS spreads 10x.
    Round-robin across all four would put a 20 dB jump between consecutive zabumba hits. Treat them
    as VELOCITY LAYERS ordered by measured RMS, with `04` as the soft layer that 03-02's ghost notes
    (velocity 0.20-0.32 normalised) will reach for.

    Derive the ordering by measuring RMS at load time, in `prepare`. Do not hard-code a file order:
    that would silently reorder if a sample is ever replaced, and "the measurement is the mapping"
    is the same rule the groove cross-check enforces on `data.js`.

    Resample ONCE in `prepare`, into a member buffer at the host rate, using
    `juce::LagrangeInterpolator` or `juce::ResamplingAudioSource`. Never resample in `render`. At
    48 kHz this is the identity case and must be skipped rather than round-tripped.

    Playback per PLANNING.md line ~730: `PITCH` becomes a playback-rate multiplier
    (`2^(pitch/12)`, so it changes duration too — that is correct and intended for a sampled voice),
    `DECAY` becomes an amplitude-envelope release that can truncate the tail but must never extend
    it past the file. Read the sample with linear interpolation on a fractional read index.

    The files are true stereo, so this voice produces a stereo pair natively while the seven synth
    voices are mono-into-pan. `PAN` on zabumba must therefore be a stereo BALANCE (attenuate the
    opposite side) rather than a mono placement, or the sample's own image collapses. Make that
    distinction explicit in the output stage rather than letting each voice invent its own.

    Avoid: loading a file from disk at runtime; resampling per block; committing the loops or
    anything else from `/mnt`; assuming 48 kHz.
  </action>

    because a note already sounding when its channel is muted should be allowed to finish rather
    than being cut, which is what the prototype does.

    Then build the measuring suite. There is no guaranteed audio device on WSL2 (a standing
    blocker), so every audio claim in this plan is proved by OFFLINE RENDERING plus measurement:

      - onset detection: first sample above a threshold relative to that render's peak, compared
        against the step positions the clock reports, to AC-1's 1-sample tolerance
      - band energy: a Goertzel or small DFT at the specified frequencies to confirm a voice sits
        where the spec says, since a wrong-but-audible voice passes any is-it-silent check
      - duration: last sample above -60 dBFS relative to peak
      - the allocation counter already in `tests/TestHarness.h`

    Register the suite in `tests/TestSuites.h` and `tests/TestMain.cpp` — ONE executable, both
    existing suites plus this one. A second executable re-compiles the whole JUCE module set, and a
    suite that is built but never run reports nothing while looking like coverage.

    Every assertion must be able to fail. Phase 2 shipped five that could not — two `check(true)`,

    idempotent, and one probabilistic detector with a guessed threshold. Before trusting any
    tolerance in this suite, mutate the thing it measures and confirm the assertion goes red;
    where a threshold is needed, MEASURE it rather than guessing, and record the measurement in a

## SCOPE LIMITS

- **No `CACHAÇA`.** No timing jitter, no velocity variation, no ghost notes. 03-02 owns all three,
  and the jitter queue is the reason the engine is persistent. Do not pre-build the queue "since
  it's obvious" — build it when it has a test
- **No character bus, no limiter, no master.** 03-03. Do not add a bypassed stub for them
- **No UI.** Phase 4. Nothing in this plan touches `PluginEditor`
- **No MIDI output.** Phase 7
- **No new third-party dependencies.** `juce_dsp` and `juce_audio_formats` are already available
  through the existing links
- **No sample support for any channel but zabumba.** The library has no coverage for the others,
  and per-strip `LOAD` stays a stub until post-v0.1
- Do not migrate the test harness to `juce::UnitTest` — deferred twice, and a mechanical rewrite
  mid-phase risks silently dropping coverage
