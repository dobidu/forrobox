<objective>
## Goal

`PluginProcessor.cpp:559` does `midi.clear()`, so an instrument that has declared
`wantsMidiInput=true` since Phase 1 throws every note away. This plan makes it play them: a note on
the GM percussion map sounds its lane, at the velocity sent, layered over whatever the sequencer is
doing.

## Purpose

It is the last plan of Phase 9 and the last ⬜ row in the README. It is also the only one whose
behaviour the design source does not describe at all — `PLANNING.md` mentions MIDI input nowhere —
so every decision below is **invented**, sanctioned by the user's explicit request at 09-05
planning, and written down where it can be overturned.

## Output

- `gm::laneForNote` — the inverse of the map the plugin already emits, derived from the same table
- `VoiceEngine::soundVelocity` — the schedule half of `playVelocity`, without the MIDI-out queue
- Incoming note-ons sound their lanes; the buffer is still cleared before the plugin writes its own
</objective>

<decisions>
**All four are invented, because nothing specifies them. Each follows a precedent already in this
codebase rather than a preference, and each is stated here so it can be reversed cheaply.**

## 1. The note map is the one the plugin already emits, inverted

`gm::noteForLane` defines what leaves the plugin (07-01 for the file, 07-03 for live). Accepting the
same notes makes the two symmetric: record this plugin's own MIDI output, play it back in, and the
same lanes fire. Any other map would mean the instrument could not play its own output.

`laneForNote` is **derived from `laneNotes`**, not a second table — the same rule
`read_timbre_index` and `writeLaneForRow` follow. Note 36 maps to two lanes (zabumba and BB, both
`PLANNING.md:815`/`:819`); the inverse resolves to the FIRST, which is zabumba, and says so.

## 2. It layers with the sequencer

A drum machine you play along with. Bypassing the sequencer while a note arrives would mean an
incoming note stops the groove, which nothing asks for and no host expects.

## 3. It follows the mute/solo gate

07-03 settled the analogous question for output: live MIDI taps `playVelocity`, downstream of the
audibility gate, so "what leaves as MIDI is exactly what you hear". Input entering the same path
inherits the same rule. A mute is a mix decision, not an input filter — a muted channel is silent
whoever asked for the note.

## 4. It is NOT humanised

`CACHAÇA` jitters a hit around its STEP (03-02's delayed origin). **A played note has no step.** It
happens when the player played it, and moving it would take it off where they put it. Ghost notes
are likewise a property of a programmed roll, not of a performance.

## And it does NOT echo to MIDI out

`playVelocity` queues a MIDI-out event for everything it sounds. An input note going through it
would be echoed back to the host that just sent it — duplicate notes, and a feedback loop in any
host routing output to input. So `playVelocity` splits: `soundVelocity` schedules, and
`playVelocity` is `queueMidiNote` plus `soundVelocity`. The sequencer keeps the pair; input takes
only the second half.
</decisions>

<acceptance_criteria>

## AC-1: a note sounds its lane
```gherkin
Given the plugin with no sequencer pattern
When a note-on arrives on the GM note for a lane
Then that lane sounds, at a level following the note's velocity
 And a note outside the map sounds nothing
```

## AC-2: it layers rather than replacing
```gherkin
Given a pattern playing
When notes arrive
Then both the pattern and the notes are audible
 And the sequencer's timing is unaffected
```

## AC-3: it respects the gate
```gherkin
Given a channel muted, or another channel soloed
When a note for that channel arrives
Then it is silent, exactly as the sequencer's own hits are
```

## AC-4: it does not echo
```gherkin
Given a note-on arriving
When the block is processed
Then the plugin's MIDI output contains no copy of it
 And the output still carries the notes the SEQUENCER produced
```

## AC-5: the audio thread stays clean
```gherkin
Given a dense stream of incoming notes
When processBlock executes
Then it allocates nothing and takes no lock
 And a note whose sample offset lies outside the block is handled, not trusted
```

<task type="auto">
  <name>Task 2: processBlock reads the buffer before it clears it</name>
  <files>src/PluginProcessor.cpp, tests/VoiceTest.cpp</files>
  <action>
    `processBlock` currently opens with `buffer.clear(); midi.clear();` — the second line is what
    throws input away. Read the incoming note-ons first, then clear, then let `scheduleBlock` write
    the plugin's own output as it does today.

    Take the sample offset from the `MidiMessageMetadata` and **clamp it into the block**: a host
    may hand an offset at or past the block length, and the voice pool trusts its offset
    (`jassert (sampleOffset >= 0)` compiles out in Release).

    Note-offs are ignored — a percussion voice runs its own envelope to completion, which is what
    both the sampler and the synth voices already do and what a drum machine does.

    `processBlock` must stay allocation-free and lock-free: iterate the buffer in place, and read
    the block's settings through the resolution that already exists rather than a second copy.

    Avoid: sounding notes before `midi.clear()` in a way that lets the plugin's own queued output be
    read back as input in the same block.
  </action>
  <verify>
    A block carrying note-ons renders them; the same block's MIDI OUTPUT contains no copy. A pattern
    plus incoming notes yields both. An offset past the block end does not crash and is clamped. The
    allocation counter reports zero across 2000 blocks each carrying notes.
  </verify>
  <done>AC-2, AC-4, AC-5 satisfied</done>
</task>

- `PLANNING.md`, `forrobox.css`, `controls.js`, `app.js` — READ-ONLY. They describe no MIDI input;

## SCOPE LIMITS
- No note-off handling, no choke groups, no MIDI learn, no per-channel MIDI filtering.
- No UI. Nothing in the design source shows a MIDI indicator, and inventing one is forbidden.
- No new parameter.
