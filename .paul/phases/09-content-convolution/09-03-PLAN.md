<objective>
## Goal

A groove carries its **own** `bpm`, `swing` and `cachaça`, so a bank can hold genuinely different
rhythms rather than variations at one tempo. `Profile::bpm`, `::swing` and `::cachaca` become
accessors over `defaultGroove()` — exactly the shape `patterns()` already has — so the numbers are
stored once.

**And nothing changes.** The four existing grooves take their profile's current feel, the velocity
fingerprint must not move, and the four profiles must still report bpm 132/132/128/126 and the
swings and cachaças they report today.

## Purpose

The user's decision at 09-03 planning: a groove is a full feel, not just eight patterns. Without it
a bank named `XOTE LENTO` plays at its profile's 132 bpm, which is not a xote — the name would be a
lie, and this project does not ship those.

It is a schema plan and it is deliberately empty of content, for the reason 09-02 was: if the feel
lands first and lands green with **zero change**, then every groove 09-04 drafts is one JSON object
that six gates check, and the drafting plan's human checkpoint sits behind one task of renderer
rather than three of scaffolding.

## Output

- `Groove` gains `bpm`, `swing`, `cachaca`; `Profile`'s three become accessors
- `assets/profiles.json` moves those three fields into each groove
- `data.js` keeps them at PROFILE level, because `app.js:526-528` reads them there and is read-only
- `validate` refuses a tempo or a feel outside the ranges `Profiles.h` documents
</objective>

<decisions>
## `timbre` and the bateria mute stay on the PROFILE

The user's decision named bpm, swing and cachaça. Those three are **feel**. `timbre` and
`bateriaMuted` are regional **character**: `check_descriptions` ties each profile's prose to them
(`"Timbre LO-FI"`, `"bateria em silêncio"`), `PETROLINA` is LO-FI because the São Francisco forró
eletrônico is, and no groove within a region changes that. Moving them would make every description
claim ambiguous about which groove it describes.

If 09-06's preset system later wants a groove to carry its own timbre, that is its decision to make
with its own caller — the same reasoning that kept `applyGroove` unwritten at 09-02.

## The profile's three fields become ACCESSORS, not a second copy

`Profile::bpm` is read at 19 sites across four files. It stays readable, as
`defaultGroove().bpm` — the identical move `patterns()` made at 09-02, for the identical reason: a
`bpm` member beside `grooveBank[0].bpm` is two numbers that can disagree, and this project keeps
finding exactly that.

The test asserts they agree by construction, not by value.

## `data.js` keeps them at profile level — the SECOND instance of this constraint

`app.js:526-528` is `setBPM(p.bpm)`, `state.swing = p.swing`, `state.cachaca = p.cachaca`, and
`app.js` is READ-ONLY design source. So the generated `PROFILES` block keeps all three at profile
level, rendered from `grooves[0]`, and gains them inside `grooves` beside the patterns.

09-02 established this shape for `patterns`. It is now a pattern with two instances, and the
generator should say so once rather than twice.
</decisions>
