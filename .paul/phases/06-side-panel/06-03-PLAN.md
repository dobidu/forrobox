<objective>
## Goal
Make selecting a regional profile do what `PLANNING.md:612-616` says it does: reload BPM, swing,
cachaça, all five patterns, all four bateria sub-patterns, the mute states and the timbre character —
clear the dirty flag, re-select the profile, and flash every lit pad as confirmation.

## Purpose
This is the phase's goal statement, word for word: *"Selecting a regional profile performs a correct
full state reload without a click, a glitch, or an audio-thread data race."*

Everything it needs now exists. `applyProfile` writes the patterns; `Profile` carries the bpm, swing,
cachaça, timbre index and the bateria mute; 06-02 built the list that will drive it. What is missing
is the **parameter half** — `applyProfile` touches no APVTS parameter at all — and the confirmation.

## Output
- `ProfileButton`, so the click is a control's and not a fifth hand-rolled hit-test
- One reload operation, driven identically from the side panel and the header's `STYLE` control
- Both highlights clearing when the state is dirty, which neither does today
- The pad flash `StepPad` has been reserving room for since 04-03
- `/code-review` after Task 2, and this time it must actually run
</objective>

## AC-1: The profile buttons are a control

```gherkin
Given the four profile buttons
Then each is a ProfileButton component with its own paint, cursor and onClick
And the panel no longer hit-tests rectangles to find which one was clicked
And nothing about their appearance changes — the reference renders are byte-identical
```

**Recorded at 06-02's close as this plan's first task.** 06-02 made `TimbreRow` a control and left
these as four rectangles in a layout struct plus a paint loop; the discriminator was the state SOURCE
(a parameter versus the pattern state), which is not a property of a control. Wiring a click onto the
painted version means a fifth hand-rolled container hit-test, joining `SequencerGrid::rowLabelAt`,
`Chassis::mouseUp`, `Segmented::segmentBounds` and `KitOverlay::mouseUp`.

Doing it first also deletes two things the reload would otherwise inherit: `refreshFromState`'s call
to `resized()`, and `paintProfiles` re-deriving `active` from a member.

## AC-2: Selecting a profile is ONE full reload

```gherkin
Given any regional profile
When it is selected from the side panel OR from the header's STYLE control
Then bpm, swing, cachaça and the timbre character take that profile's values
And every lane and every bateria sub-lane holds that profile's pattern
And the mute states are the profile's, and every SOLO is cleared
And activeProfile names it and the dirty flag is clear
And the two entry points produce a state that is identical, field for field
```

**`applyProfile` writes no parameter.** It fills the lanes, sets `activeProfile` and clears `dirty` —
the bpm, swing, cachaça and timbre that `Profile` carries have never reached the APVTS. That is the
gap this plan closes, and it is why the reload cannot simply be `applyProfile`.

**Solo is cleared and is not in the data.** `app.js:534` clears every solo on load while reading the
mutes from the profile; `Profile::bateriaMuted` is the only mute the tables carry. Both facts belong
in the reload rather than in the tables.

**The pattern is written at the CURRENT step window, not the profile's.** `expandPattern` fills all
32 slots from the 16-step source, which is 02-01's storage model and already agrees with
`buildGroove(id, state.steps)` — assert it rather than assume it.

**Message thread, one gesture each.** Nine `setValueNotifyingHost` calls and one `lockPatternState`
write. `processBlock` stays allocation-free and lock-free; the audio thread picks the pattern up
through the publication it already uses.

## AC-3: A dirty state clears the highlight, in both places

```gherkin
Given a profile is active and the state is then edited
Then the CUSTOM tag appears AND the profile button stops being highlighted
And the header's STYLE control stops showing that profile as selected
Given the profile is reloaded
Then both highlights return and the tag goes
```

**Neither does this today.** `app.js:555` is `pid === state.activeProfile && !state.dirty` and
`PLANNING.md:601-602` says the highlight clears — 06-02 shipped the highlight keyed on
`activeProfile` alone, and the header's `STYLE` control has been keyed on it alone since 04-04.

**"Editing anything marks dirty" is NOT in this plan**, settled with the user: only pad edits set the
flag today, and extending that to 35 channel parameters plus the globals is a different kind of
change. Record it; do not start it here.

## AC-4: The pads flash on reload

```gherkin
Given a reload with at least one lit pad
Then every lit pad flashes — brightness 1.6 falling to 1 over 340 ms (PLANNING.md:615)
And the flash is driven by elapsed time it is TOLD, never by reading a clock
And a test drives it to any point without waiting
```

**`StepPad` has no flash facility.** 04-03 deferred it in as many words — *"NOT here, because both
need Phase 5's trigger FIFO and playhead… a guarantee with no caller is not a guarantee"*. It now has
a caller. Build only the confirmation flash; the per-hit trigger flash the same comment mentions is
still nobody's.
