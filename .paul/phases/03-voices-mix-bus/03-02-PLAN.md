<objective>
## Goal

Make `CACHAÇA` do what it claims. One knob, three effects, taken verbatim from `app.js`'s
`scheduler()` and `scheduleStep()`:

1. **Timing jitter** — `±(cachaça/100) × 22 ms`, uniform and bipolar, **one draw per step** applied
   to that step's time, so every lane of the step moves together
2. **Velocity variation** — `× (1 − (cachaça/100) × 0.25 × random())` per **hit**, so up to 25%
   softer and never louder
3. **Ghost notes** — on any step where a channel has no programmed hit,
   `chance = (ghost/100) × (0.22 + (cachaça/100) × 0.6)`; velocity 0.20–0.32 normalised, offset
   ±10 ms, and HH only for the bateria

And build the thing 03-01 could not: a scheduling origin delayed far enough that a hit placed
*before* its step is representable at all.

## Purpose

`PLANNING.md` calls `CACHAÇA` "the signature control" and says it "is *not* an effect; it is a
humanisation amount". `PROJECT.md`'s core value is grooves that feel human. Ghost notes in
particular are "much of what makes the groove feel human" — they are the difference between a
groovebox and a percussionist.

This is also the plan that repays 03-01's one dishonest claim. 03-01's success criterion said its
shape carries this plan's jitter unchanged; the `/simplify` altitude review proved that true for
late offsets and false for early ones.

## Output

- `kJitterLookahead`, reported to the host with `setLatencySamples`, so bipolar offsets are
  non-negative by construction
- One jitter draw per step, inside `scheduleStep`, where the spec draws it
- Per-hit velocity variation
- Ghost notes, with `cachaca` and per-channel `ghost` reaching the engine for the first time
- A suite that tests distributions, not one seeded outcome

## Specification — the authority, quoted

`PLANNING.md` → **CACHAÇA — humanisation** (~line 556) and **Ghost notes** (~line 575) give the
numbers. `app.js:633-676` is the implementation they describe, and it settles the questions the
prose leaves open — which draw happens per step and which per hit, and in what order:

```js
const jitter = (state.cachaca / 100) * 0.022 * (Math.random() * 2 - 1);   // ONE draw, per step
const t = nextNoteTime + swingDelay + jitter;
scheduleStep(step, Math.max(engine.now(), t));
// inside scheduleStep, per hit:
let v = vel / 127;
v *= (1 - cach * 0.25 * Math.random());
// inside scheduleStep, per silent lane:
const chance = (ch.ghost / 100) * (0.22 + cach * 0.6);
if (Math.random() < chance) {
  const t2 = t + (Math.random() - 0.5) * 0.02;
  engine.trigger(id, sub, Math.max(engine.now(), t2), 0.2 + Math.random() * 0.12, {...});
}
["zabumba","triangulo","pandeiro","ganza"].forEach(id => { v > 0 ? play(id) : ghost(id); });
["bb","cx","hh","tom"].forEach(s => { v > 0 ? play("bateria", s) : (s === "hh" && ghost("bateria", s)); });
```

Four things in there that the prose does not say, and that a reader of `PLANNING.md` alone would
get wrong:

- the velocity multiplier draws **per hit**, so eight lanes of one step get eight different draws,
  while the timing jitter draws **once**
- a ghost's velocity is already normalised (0.20–0.32) and does **not** get the velocity multiplier
- a ghost's ±10 ms is **on top of** the step's jitter, so total deviation reaches ±32 ms
- ghosts respect mute and solo, and read the **bateria channel's** `ghost` for the HH lane

  <files>src/VoiceEngine.h, src/VoiceEngine.cpp, src/PluginProcessor.h, src/PluginProcessor.cpp, src/ParameterIDs.h, tests/VoiceTest.cpp</files>
  <action>
    Add `cachaca` to `VoiceEngine::Settings` (a global, so it belongs on the Settings struct rather
    than per channel) and resolve it in `resolveChannelSettings` from the already-declared
    `ids::cachaca` parameter. Cache its raw pointer at construction alongside the others and extend
    `parametersResolved` to cover it.

    Then build the origin. Define the humanisation bounds once, in `Voices.h` beside `kEnvelopeFloor`
    and `decayScaleFor` — NOT as literals at their use sites, which is the mistake that halved every
    pan in 03-01:

      kMaxJitterSeconds      = 0.022   // PLANNING.md: +/-(cachaca/100) x 22 ms
      kGhostJitterSeconds    = 0.010   // and a ghost's further +/-10 ms
      kVelocityHumaniseDepth = 0.25    // up to 25% softer
      kGhostBaseChance       = 0.22
      kGhostCachacaSpan      = 0.60
      kGhostVelocityMin      = 0.20
      kGhostVelocitySpan     = 0.12

    The lookahead is `kMaxJitterSeconds + kGhostJitterSeconds` — **32 ms, not 22**. A ghost's offset
    is applied on top of a step's already-jittered time (`t2 = t + ...` in the sketch, where `t`
    already contains the jitter), so 22 ms of headroom would still clamp a ghost. Write that
    arithmetic down next to the constant.

    `VoiceEngine::prepare` computes `lookaheadSamples = round(kLookaheadSeconds * sampleRate)` and
    exposes it. `prepareToPlay` then calls `setLatencySamples (engine.getLookaheadSamples())`, so
    the host compensates and a recording stays sample-exact. Report it unconditionally, including at
    CACHAÇA 0: reported latency must be constant, because changing it mid-session forces a host
    re-negotiation that many DAWs handle badly.

    Every trigger gains the lookahead. `scheduleStep` adds `lookaheadSamples` to the offset it was
    given before doing anything else, so `offset = lookahead + jitter` is non-negative by
    construction and NOTHING is clamped. The existing `samplesUntilStart` carry-forward already
    transports an offset past the end of its block — 03-01 verified that in source — so no change to
    `Clock`, `planBlock` or the span planning is needed, and none should be made.

    Finally, per-hit velocity variation, inside `scheduleLane` where the sketch applies it:
    `v *= (1 - cachaca01 * kVelocityHumaniseDepth * rng.nextFloat())`. Per hit means the draw is
    inside the per-lane call, so eight lanes of one step get eight different multipliers — unlike the
    timing jitter, which is drawn once. `juce::Random::nextFloat()` returns [0, 1), so the multiplier
    is (0.75, 1.0] and a hit can never be made louder.

    **03-01's onset assertions must be updated, deliberately.** They assert a hit lands at exactly
    its step position; every hit is now `lookaheadSamples` later. Rewrite them as
    `step position + getLatencySamples()`, and keep the exact "nothing before that sample" claim —
    it is what proves no offset was clamped. Do not weaken either into a tolerance.

    Avoid: applying the lookahead inside `scheduleLane` (it would be added once per lane instead of
    once per step); scaling the lookahead by CACHAÇA; a second RNG; `jmax(0, …)` anywhere on an
    offset — the clamp is what this task exists to remove.
  </action>
  <verify>
    `getLatencySamples()` returns 1536 at 48 kHz and 1411 at 44.1 kHz. A single hit's first non-zero
    sample equals its step position plus the reported latency, with exact silence before it. At
    CACHAÇA 100 a velocity sweep shows every peak in (0.75, 1.0] of the un-humanised peak and never
    above; at CACHAÇA 0 every peak is exactly the un-humanised value. Two lanes on one step measure
    different multipliers. Zero allocations across 2000 blocks. All three compilers green.
  </verify>
  <done>AC-2 and AC-3 satisfied; AC-6's allocation and determinism clauses hold.</done>

      jitterSamples = cachaca01 * kMaxJitterSeconds * sampleRate * (rng.nextFloat() * 2 - 1)

    One draw per step is the whole point of the step-shaped seam 03-01 built. `app.js` computes it
    outside `scheduleStep` and passes one time in, so every lane of the step moves together. A draw
    per lane is not a compile error and not a test failure — it is the whole step breathing against
    the lanes flamming apart — so AC-1 asserts the sameness directly.

    Add a shared measurement helper to `tests/TestHarness.h` for the distribution work: given a
    render and the grid positions, return each hit's measured displacement in samples. `findTailEnd`,
    `firstNonZeroSample` and the band-energy helpers already live there from 03-01.

    Then test it as a DISTRIBUTION, not as one seeded outcome:

      - uniformity: bucket several hundred displacements and check no bucket is empty and none holds
        more than a stated share. Choose the trial count and the share by MEASURING them, and record
        the measurement next to the constant — 02-04's flaky race detector needed a measured 300
        threshold and was green at the author's first guess
      - bipolarity: the mean displacement is near zero, and both signs occur. A one-sided
        implementation passes a bound-only test
      - the bound: no displacement exceeds `cachaca01 * 22 ms`, and at CACHAÇA 50 the spread is
        half what it is at 100 — which catches a jitter that ignores the knob
      - CACHAÇA 0: every hit exactly on its grid position, asserted exactly rather than within a

    prepared instances draw the same sequence. Assert that too — it is what makes every other
    assertion here reproducible.
